# Specification: patch applier

The patch applier builds the organization's model: the shipped `model.yaml` plus the organization's design patches, applied in a fixed order, with a JSON report. When asked, it also compiles the organization's design layer: the shipped layer files plus the entries the patches add or change, minus the entries of parts they retire. The organization's agent runs it after every change to a patch and before the impact report tool and the model checks; the upgrade tool reuses its rules. It applies only patches a person has accepted, unless a proposed patch is named for a preview.

The design layer is the four files beside `model.yaml`: `realization.yaml`, `quality.yaml`, `failures.yaml` and one overlay, `overlay-aws.yaml` as shipped. The AWS overlay is a worked example. An organization may adopt its own overlay file in the same shape once, as its baseline, for whatever cloud or on-premises setup it runs; its version record names that file and its hash, and the compiled layer then carries that overlay in place of the shipped one. One overlay covers every part. After the baseline, every change to placement is a patch. The compiled layer also carries a byte copy of the edition's `modules.yaml` when the edition ships one, so the layer folder is all the model checks need.

## Ideal state

- **PA-1** The shipped `model.yaml` and the shipped layer files are never modified. The output model equals the shipped model plus the applied patches, and nothing else; the compiled layer equals the shipped layer plus the applied patches' layer changes, and nothing else.
- **PA-2** Patches are applied in ascending order of their number, compared as integers, so `O10` follows `O09`. Two files with the same number are an error.
- **PA-3** By default only accepted patches are applied. A proposed patch is applied only when named in the preview option, and the output then says it is a preview and lists the proposed patches it contains. Rejected and withdrawn patches are never applied. An accepted patch named in the preview-withdraw option is left out of that run as if withdrawn, and the output lists it; no file changes.
- **PA-4** Every patch file has a title line whose id matches its file name and all six required sections: Why, Ops, Risk and threat-model delta, Feasibility note, Exceptions needed, Status.
- **PA-5** The Ops section holds exactly one fenced `yaml` block, and that block parses to a mapping with an `ops` list.
- **PA-6** The Status section's first line is `proposed`, `accepted by <who> on <YYYY-MM-DD>`, `rejected by <who> on <YYYY-MM-DD>` or `withdrawn by <who> on <YYYY-MM-DD>`. A withdrawn patch is one that was accepted and later retired. The date is the text after the last ` on ` and holds no spaces, and `who` is everything between `by ` and that last ` on `, so `who` may itself contain ` on `.
- **PA-7** Each op checks its preconditions and fails with the error code given under Behavior when one does not hold.
- **PA-8** After a patch's last op, every reference the patch created or changed resolves in the model as it then stands.
- **PA-9** A patch applies completely or not at all. A failing op discards every change from that patch.
- **PA-10** When any error occurs, no output model is written. The JSON report is always written.
- **PA-11** Every element, relationship, contract, view, trust zone and finding kind a patch adds or modifies records which patch added it, whether it was added or modified, and every patch that touched it, in order.
- **PA-12** A removed element or relationship moves to the `retired` section with the removing patch, and disappears from every view. A removed relationship also leaves every seam that declares it.
- **PA-13** Given the same inputs, two runs produce byte-identical output. Applying patches to a model is never cumulative: each run starts from the shipped model.
- **PA-14** Everything a patch adds carries an organization namespace, so a later edition cannot collide with it.
- **PA-15** A patch that lists `depends_on` applies only when each named patch sorts earlier and is applied in the same run.
- **PA-16** The output model's `meta` names the edition, the organization's version when known, the applied patches, and the patches a preview added or withdrew.
- **PA-17** When a layer is compiled, every organization part can carry its own layer entries, and every part, shipped or the organization's, can have its entries changed by a patch. With no applied patch, each compiled layer file equals its input file byte for byte. A failed patch leaves no layer entry behind, and any error writes no layer.
- **PA-18** Removing an element leaves no active reference to it in the output model or compiled realization, quality, overlay and failure files, the quality layer's critical paths included. Retired snapshots keep their historical endpoints and other fields under PA-12.
- **PA-19** The applier and the upgrade tool find the overlay by one rule (Finding the overlay, below). When the overlay in use is the recorded file, its bytes must hash to the recorded value, or the applier refuses to run. An explicit option selecting a different overlay exempts the recorded file from reading and hashing in that run.
- **PA-20** The account classes the overlay offers change only through patches: `add_account_class` and `modify_account_class` change them, and `set_layers` places a part in one.
- **PA-21** The compiled layer folder holds everything the model checks read: the four layer files and, when the edition ships it, `modules.yaml`. The compiled layer also preserves the supplied `threat-closures.yaml` byte for byte when present, so the next composer receives the design's own closure rules alongside the shared layer's rules. No patch operation changes this file.
- **PA-22** A modify op that carries `expects` applies only when the hash of each field it sets or takes away matches the field's current value. On any mismatch the patch is refused, and the error names the target, the field, the expected hash and the actual one. A modify op without `expects` behaves exactly as it would without this rule.
- **PA-23** The finding-kind registry, the model's `finding_kinds` list, changes only through patches: `add_finding_kind` adds a kind and `modify_finding_kind` changes one. Every kind an organization adds carries every key a kind declares, and its closure check names a part the model holds.
- **PA-24** A view stays with the patch that added it. When a later patch in the same run has an id that the view's id starts with, the later patch is refused and the patch that added the view still applies.
- **PA-25** A modify op can take keys away with `unset`, beside or in place of `set`. It may take any top-level key except the item's identity, its provenance and the keys its kind requires, and it refuses a key the item does not hold. Afterwards the item holds no such key.
- **PA-26** On the command line, `preview` is `--preview` and `preview_withdraw` is `--preview-withdraw`. Each takes one patch id or a comma-separated list of ids and may be repeated. Every id given counts, in the order given, and an id given twice counts once.
- **PA-27** The model's seams, the `seams` list where each pluggable module's boundary declares the relationships that cross it, change only through patches. `add_to_seam` declares crossings on a seam, or adds contracts to a crossing it declares. Removing a relationship takes it out of every seam that declares it, and the seam records the patch, so no seam declares a relationship the model no longer holds.

## Inputs

- `model.yaml` from the edition: its edition (the top-level `edition` field; a model with no `edition` field gives `meta.version` instead, as editions before 3.0.0 did, and a model with neither gives a null `edition` in the report and in `meta`), `systems`, `trust_zones`, `elements`, `relationships`, `contracts`, `views`, `sequence`, `finding_kinds` (the finding-kind registry; an edition that does not carry it has no such key, and the first `add_finding_kind` creates it), and `seams` (the module seams: each with `id`, `crossings` of `{ id, carries, point }` and other keys the applier keeps as they are; an edition that does not carry it has no such key, and no op creates one).
- When a layer is compiled: `realization.yaml`, `quality.yaml` and `failures.yaml` from the edition, the overlay found by the rule below, and the edition's `modules.yaml` when it ships one (copied, never parsed). Each layer file must be a readable YAML mapping. The applier reads the entry maps (`elements` in realization, quality and the overlay; `contracts` in quality; `scenarios` in failures; `account_classes` and `zone_accounts` in the overlay) and the critical paths in quality (`critical_paths.paths`, a mapping from path id to a path whose `must_answer` lists part ids, whose optional `co_deploy` maps a group name to a list of part ids, and whose optional `required_hops` lists `[from, to, note]` entries), and keeps every other key as it is.
- The organization's patch directory: every file whose name matches `O<digits>-<slug>.md`, where digits are two or more and the slug is lowercase letters, digits and hyphens.
- The organization's version record `version.yaml`, when present: its `version` field becomes `meta.organization_version` (the upgrade tool writes the record). Its optional `overlay` field records the organization's baseline overlay as `{ file: overlay-<name>.yaml, sha256: <64 lowercase hex digits> }`, the file sitting in the record's own folder. A record that exists but cannot be parsed, has no `version`, or has an `overlay` of another shape is an unreadable input. The shape is checked on those two keys only: `overlay` must be a mapping, its `file` a bare file name of the form `overlay-<name>.yaml` (lowercase letters, digits and hyphens in the name, never a path), and its `sha256` 64 lowercase hex digits; other keys in it are ignored.
- Options: the shipped model path, the patch directory, the version record path, the output model path, the report path, `preview` (a list of proposed patch ids to include) and `preview_withdraw` (a list of accepted patch ids to leave out of this run). On the command line these two are `--preview` and `--preview-withdraw`, as PA-26 gives them; the other options' command-line names are the tool's own. Three more options govern the layer: `layer_out` (the output layer directory; the layer is compiled only when it is given), `layer` (the directory holding the shipped layer files; default, the shipped model's directory) and `overlay` (an overlay file named `overlay-<name>.yaml`, used in place of the one the lookup rule would find, for example to preview a candidate baseline). The output model path may not be the shipped model's path, and no output may be written inside the patch directory. The output layer directory may not be the shipped layer directory or the overlay file's directory. `layer` or `overlay` without `layer_out`, and an overlay file name of another form, are invalid. Each of these is an invalid option.

### Finding the overlay

The applier and the upgrade tool find the overlay by this one rule:

1. An explicit overlay option wins. The upgrade tool has none, because its output becomes the organization's state, and a new baseline is a decision, recorded by the organization's own process.
2. Otherwise the file the version record names under `overlay.file`, in the record's folder.
3. Otherwise the shipped example, `overlay-aws.yaml`, beside the shipped layer files.

Whenever the overlay in use is the recorded file, whether found by the record or named by the option, its bytes must hash (SHA-256, lowercase hex) to `overlay.sha256`, or the tool refuses with `overlay.unrecorded-change`: the placement changed without a patch. The check runs whether or not a layer is compiled. It does not run when the overlay in use is some other file: an option naming a different file wins over a stale record. A recorded file that cannot be read is an unreadable input. The record's folder is the folder of the version record path option, whether or not a record file exists there, so the scan below runs with no record too. Any other `overlay-<name>.yaml` in the record's folder, except the recorded file and the overlay in use however it was found (so the shipped `overlay-aws.yaml` is never reported while it is the one in use), is read by no rule; when the record's folder is the shipped layer directory (the `layer` option, by default the shipped model's directory), compared as absolute paths, no file there is reported; when it compiles a layer, the applier reports each as warning `overlay.unrecorded-file`, whose `file` is that overlay's file name alone (`overlay-old.yaml`, never a path), instead of ignoring it silently. The report's `overlay` names the file used, by its file name alone (`overlay-candidate.yaml`), and how it was found (`option`, `record` or `shipped`), or is null when no overlay was read. A recorded overlay read only for its hash, with no layer compiled, is named too, as `{file, found_by: record}`.

Every matching patch file is parsed and checked for file-level errors and warnings before selection by status or preview; proposed, rejected and withdrawn files can therefore report file-level findings. After applying a patch, reference validation of an extended seam checks every crossing it then declares, not just crossings named in that patch.

### The organization patch file

````markdown
# O03: Approvals for production-effects runs need two approvers

## Why
Two to five sentences: the problem, the evidence, and the part of the design it changes.

## Ops
```yaml
depends_on: [O01]
ops:
  - op: modify_element
    id: s3.approval-console
    set: { responsibility: "..." }
  - op: add_relationship
    relationship: { id: o03-r1, from: org.second-approver, to: s3.approval-console, label: "...", carries: [], kind: control, optional: false }
  - op: add_element
    element: { id: org.sbom-store, name: SBOM evidence store, system: S5, level: store, kind: store, responsibility: "...", role_class: evidence, trust_zone: control }
    layers:
      realization: { plane: evidence, class: "...", examples: [], swap_point: false, existing_tool_default: false }
      quality: [T1, queue-and-retry, "..."]
      overlay: { services: ["..."], fit: managed-open, account: evidence, portability: open, keeps: "..." }
```

## Risk and threat-model delta
Written from the impact report tool's output.

## Feasibility note
What it costs, who builds it, and what must exist first.

## Exceptions needed
Should-never rule codes this patch needs an exception for, or "None".

## Status
accepted by <role or person> on <YYYY-MM-DD>
````

For the toy fixture input, `meta.version` supplies the edition when top-level `edition` is absent; the toy person system is `shared:PEOPLE`. These are literal input identities, not values a runner substitutes from this example.

Headings are level 2 and match case-insensitively. Other level 2 sections are ignored. `depends_on` is optional.

## Outputs

1. The organization's model as YAML at the output path, with the shipped model's key order kept and added items appended to the end of their list in op order. Recorded fields on a changed item:

```yaml
elements:
  - id: s3.approval-console
    # ...shipped fields, with the patch's set values...
    patch: O03          # first organization patch that added or modified it
    patch_op: modified  # added when an organization patch added it, else modified
    patches: [O03, O07] # every organization patch that added or modified it, in apply order
retired:
  elements: [ { id: s2.old-part, "...": "...", retired_by: O05 } ]
  relationships: [ { id: r034, "...": "...", retired_by: O05 } ]
meta:
  edition: "2.1.2"                       # the shipped model's edition
  organization_version: "2.1.2+example.3" # null when no version record exists
  basis: "2.1.2 plus organization patches O01, O03"
  organization_patches: [O01, O03]
  preview_patches: []                     # proposed patches included, when any
  preview_withdrawn: []                   # accepted patches left out by preview-withdraw, when any
```

The output model has a `retired` key only once a patch removes something. The first removal adds it as a new top-level key, after the keys the model then has, holding both lists, `elements` and `relationships` (one stays `[]` when nothing of that kind is removed); each removed item is appended in apply order, as it stood, with `retired_by`. A run that removes nothing writes no `retired` key.

The output `meta` keeps the shipped `meta` keys in their order and sets these six; a shipped model with no `meta` gets one, appended after its last key. With no applied patch, `basis` reads `"2.1.2 with no organization patches"`. The applier writes no timestamp into the model.

2. When a layer is compiled, the organization's layer in the output layer directory: the four files under their input names (`realization.yaml`, `quality.yaml`, `failures.yaml`, and `overlay-aws.yaml` or the organization's `overlay-<name>.yaml`), plus `modules.yaml` with its input bytes when the edition ships it. A file no applied patch changed is written with its input bytes. Whether a patch changed a file is judged on the parsed document, never on the bytes a writer would produce: a file is unchanged when its document after every applied patch holds the same keys, in the same order, with the same values as the document read from the input, so a `set_layers` that writes a value equal to the one already there changes nothing. A changed file is written as the input's leading comment lines followed by the document as YAML, with the input's key order kept and new entries appended in op order. Ordinary layer entries carry no provenance keys because their shape checks refuse stray keys. Organization failure scenarios are the PA-32 exception and carry ordinary patch provenance in the failure layer. The report records which patch changed ordinary layer entries.

3. A JSON report:

```json
{
  "edition": "2.1.2",
  "organization_version": "2.1.2+example.3",
  "applied": ["O01", "O03"],
  "preview": [],
  "preview_withdrawn": [],
  "overlay": { "file": "overlay-aws.yaml", "found_by": "shipped" },
  "skipped": [{ "id": "O02", "status": "proposed" }],
  "changes": [
    { "patch": "O03",
      "added":    { "elements": ["org.sbom-store"], "relationships": ["o03-r1"], "contracts": [], "views": [], "trust_zones": [], "finding_kinds": [] },
      "modified": { "elements": ["s3.approval-console"], "relationships": [], "contracts": [], "finding_kinds": [], "views": [], "seams": [] },
      "removed":  { "elements": [], "relationships": [] },
      "views_extended": [],
      "seams_extended": [],
      "layers":   { "added": ["org.sbom-store"], "modified": [], "removed": [], "retired_scenarios": [],
                    "account_classes": { "added": [], "modified": [] } } }
  ],
  "retired":  { "scenarios": [] },
  "errors":   [{ "code": "op.target-missing", "file": "O04-example.md", "op": 2, "text": "modify_element: no element s9.gone" }],
  "warnings": [{ "code": "section.empty", "file": "O02-example.md", "op": null, "text": "Risk and threat-model delta is empty" }],
  "model_written": false,
  "layer_written": false
}
```

`op` is the zero-based index of the op in the patch, or null for file-level messages.

`applied` lists the patches that applied, in apply order, previewed ones included. `preview` lists the previewed proposed patches that applied. `preview_withdrawn` lists the accepted patches the preview-withdraw option left out, in apply order. `skipped` lists patches left out for their status or by preview withdrawal, in patch order (ascending number), a preview withdrawal listed with status `withdrawn`; a patch that fails a check appears in `errors` and nowhere else. A run that ends with errors still lists in `applied` every patch that passed, though it writes no model. `changes` holds one entry per applied patch and none for a failed one. Within an entry, an id appears at most once per list (`finding_kinds` lists finding kind ids), an item the patch added is listed under `added` only, and `views_extended` names the existing views the patch extended with `add_to_view`. `modified.views` names the existing views a `remove_element` or `remove_relationship` took a member out of, in the order the patch first changed them; a view the patch added is never listed there, and a view both extended and emptied of a member appears in both lists. Seams follow the same pattern: `seams_extended` names the seams the patch extended with `add_to_seam`, and `modified.seams` the seams a `remove_relationship` took a crossing out of, each in the order the patch first changed them; a seam both extended and emptied of a crossing appears in both lists.

`layers.added` lists an added element only when its `layers` holds at least one entry; adding an element without layer entries lists it nowhere in that layer list. `layers` names the element ids and contract names whose layer entries the patch changed, each list in the order the patch's ops first changed them (never sorted): `added` for entries an `add_element` or `add_contract` wrote, `modified` for entries a `set_layers` wrote (an id the same patch added stays under `added`), `removed` for an element whose entries, scenario memberships or critical-path memberships a `remove_element` dropped, and `retired_scenarios` for the failure scenarios it left empty. `account_classes` names the overlay account classes the patch added (`add_account_class`) or changed (`modify_account_class`; a class the same patch added stays under `added`). `added`, `modified` and `account_classes` are filled whether or not a layer is compiled; `removed` and `retired_scenarios` need the layer, so they stay empty when none is compiled. `retired.scenarios` lists every dropped scenario as `{ "id", "retired_by" }` in apply order. `layer_written` is true only when a layer was compiled and written.

## Behavior

### Reading patches

1. List the patch directory. A file starting with `O` that does not match the name pattern is skipped with warning `file.name`. Files that do not start with `O` are ignored.
2. Sort by the integer value of the number. When two or more files share a number, each of them gets one `file.duplicate-id` error, located at that file, and none of them applies.
3. For each file, parse the title line `# O<digits>: <title>`. A missing title or an id that differs from the file name is error `patch.title`.
4. Find the six required sections. A missing section is error `section.missing`. A section with no text is warning `section.empty` for a proposed, rejected or withdrawn patch, and error `section.empty` for any other (accepted, or with an invalid Status, or with no Status section). An empty Status section is both: `status.invalid`, since it has no Status line, and error `section.empty`. A missing Status section is `section.missing` alone, never `status.invalid` too, and with no Status line the patch's empty sections are errors. "None" counts as text. Sections out of the listed order give warning `section.order`.
5. Parse the Status line. Anything other than the four forms in PA-6 is error `status.invalid`. `who` is free text; the date must be a valid calendar date.
6. In the Ops section, count fenced blocks whose info string is `yaml`. Zero or more than one is error `ops.block-count`. A block that fails to parse as YAML, or parses to something other than a mapping with a list under `ops`, is error `ops.parse`. The block is parsed as YAML 1.2, and the applier never repairs it: a block a conforming parser rejects, such as one whose key sits deeper than its sibling under a list item or whose flow mapping is never closed, is `ops.parse`, never a guess at what the author meant. The fixture's malformed block has both of those faults, and a parser that rejects either one refuses it. Keys other than `ops`, `depends_on` and `acceptance` give warning `ops.unknown-key`.
7. A patch with any file-level error is not applied.

### Selecting patches

8. Apply accepted patches and the proposed patches named in `preview`. Skip other proposed patches and all rejected and withdrawn patches, listing them in `skipped` with their status. Naming an accepted, rejected or withdrawn patch in `preview`, or a patch id with no file, is error `preview.invalid`. An accepted patch named in `preview_withdraw` is skipped as if withdrawn, listed in `skipped` with status `withdrawn` and in `preview_withdrawn`; the patch file is not touched. Naming a proposed, rejected or withdrawn patch in `preview_withdraw`, or a patch id with no file, is error `preview.invalid`. Together the two options preview a replacement with the withdrawals it implies. A patch whose Status is invalid is never `preview.invalid` under either option: its `status.invalid` already stops it. `preview.invalid` is a run-level message (`file` and `op` null) even when the named patch has a file, and it does not stop the run: the other patches still select and apply, and the run ends with exit 1.
9. For each id in `depends_on`: if no such patch exists, if it sorts at or after this patch, or if it is not applied in this run, raise error `depends.unmet` and skip this patch. The patch raises one `depends.unmet` however many ids are unmet, located at the depending patch's file with `op` null, its text naming every unmet id. A patch that depends on a withdrawn patch, or on one withdrawn for a preview, therefore fails.

### Applying ops

10. Start from a fresh copy of the shipped model, and of the shipped layer when one is compiled. Apply each selected patch to a working copy of both; on any error, discard both copies, record the error and continue, so the report lists every error.
11. Ops run in listed order, and the first failing op ends its patch: later ops in that patch are not run, so a patch reports at most one op error. Each op is checked in this order: op type (`op.unknown` for a type outside the list below, or an op that is not a mapping with an `op` key), required keys, key shapes and the shape of `expects` (`op.malformed`), provenance keys (`op.provenance`), identity keys (`op.identity`), keys an `unset` may not take (`op.unset-required`), namespace (`op.namespace`), then the preconditions in the table, `expects` last.
12. Provenance keys `patch`, `patch_op`, `patches` and `retired_by` may never appear in an added object (a finding kind's `kind` included), a `set`, an `unset`, an account class op, or a crossing an `add_to_seam` lists; error `op.provenance`. Each modify op names its target by one identity key: `name` for `modify_contract`, `id` for the other three. A `set` that holds that key, or an `unset` that lists it, is error `op.identity`; renaming is never a modify. Only the target's own identity key counts: a `set` that gives a contract an `id` key sets an ordinary key. An `unset` that lists a key the target's kind requires (PA-25, Taking a key away) is error `op.unset-required`.
13. Namespace rules (PA-14): an added element id starts with `org.`; an added relationship id starts with the patch id in lowercase and a hyphen (`o03-`); an added view id starts with the patch id (`O03`, `O03-approvals`); an added trust zone id starts with `org-`; an added contract name starts with `Org`; an added account class name starts with `org-`; an added finding kind id starts with `org-`. A violation is error `op.namespace`.
13a. View ids and later patches (PA-24). After the `depends_on` check of step 9 and before a patch's first op, the applier looks in the model as it then stands for a view that an earlier patch of this run added and whose id starts with this patch's id. When there is one, the patch is refused with error `op.namespace`, located at the patch's file with `op` null, its text naming that view and the patch that added it, each as a whole token; none of the patch's ops run. Only the patches this run applies count: the accepted patches not named in `preview_withdraw`, and the proposed patches named in `preview`. A proposed, rejected or withdrawn patch file refuses nothing. A longer patch id that starts with a shorter one either sorts after it (`O100` after `O10`, `O0100` after `O010`) or has the same number (`O010` beside `O10`); two files with the same number are both `file.duplicate-id` (step 2) and neither applies. So the patch refused is always the later one, and an accepted patch is never refused because of a patch accepted after it. The outcome, for patch `O10` adding view `O100`:

| Patch `O100` in this run | Outcome |
|---|---|
| no file, or proposed and not named in `preview`, or rejected, or withdrawn (a preview withdrawal included) | `O10` applies with view `O100` |
| accepted, or proposed and named in `preview` | `O10` applies with view `O100`; `O100` is refused with `op.namespace`, whatever its own ops |

A view id that does not start with the later patch's id (`O10a`, `O10-approvals` beside patch `O100`) refuses nothing. Name a new view with a hyphen or an underscore after the patch id (`O10-approvals`), which no longer patch id can begin.

| op | required keys | preconditions (error code) | effect |
|---|---|---|---|
| `add_element` | `element` with `id`, `name`, `system`, `level`, `kind`, `responsibility`; optional `layers` (see below) | no element has the id (`op.exists`); `system` names an entry in `systems` (`op.bad-reference`) | append, with `patch`, `patch_op: added`, `patches: [<patch id>]` (the id of the patch, never the element's); write each `layers` entry under the element's id |
| `modify_element` | `id`, and `set` (a mapping), `unset` (a list of key names) or both, at least one of them non-empty; optional `expects` | element exists (`op.target-missing`); the element holds every key `unset` lists (`op.unset-absent`, whose text names each missing key as a whole token); with `expects`, every hash matches (`op.expects-mismatch`) | merge `set` over the element's top-level keys and remove each key `unset` lists; set `patch` if absent; keep `patch_op: added` if already added, else `modified`; append the id to `patches` once |

The `layers` mapping on `add_element` takes up to three keys: `realization` (a mapping in the shipped realization entry shape: `plane`, `class`, `examples`, `swap_point`, `swap_kind`, `existing_tool_default`), `quality` (a list, the shipped `[tier, failure_mode, note]` entry) and `overlay` (a mapping in the shipped overlay entry shape: `services`, `fit`, `account`, `portability`, `keeps`, `residency`, `note`). On `add_contract` it takes only `quality` (the shipped contract quality list). Any other key, a `realization` or `overlay` that is not a mapping, or a `quality` that is not a list, is `op.malformed`. The applier checks keys and value types only; the model checks judge the content. `layers` is optional: an organization part added without it still applies, and the model checks then report its missing entries. The keys a new entry needs for `op.layer-incomplete` are `plane`, `class`, `examples`, `swap_point`, `existing_tool_default` for realization and `services`, `fit`, `account`, `portability` for the overlay. `set_layers` works on shipped and organization parts alike, which is how an organization records that it swapped a shipped part for a tool it already runs, or placed a part in a different account.

A crossing in an `add_to_seam` holds only `id`, `carries` and `point` (and the four provenance keys, which pass this check so that step 12 reports them as `op.provenance`); any other key, an `id` that is not a non-empty string, a `carries` that is not a list of strings, a `point` that is not a non-empty string, a crossing listed twice, or `crossings` that is not a non-empty list is `op.malformed`. The applier checks shapes and references only; the model checks judge whether the relationship crosses the seam and what it may carry (MC-108).

The account class ops take their shape from the overlay's own entries: a class is a description under `account_classes`, allowed in the zones whose `zone_accounts` list names it. Any key other than `name`, `description` and `zones` (and `op`, and the four provenance keys, which pass this check so that step 12 reports them as `op.provenance`), a non-string description, a `zones` that is not a list of strings, or a `modify_account_class` with neither `description` nor `zones` is `op.malformed`. They work on shipped classes and the organization's alike, so a hybrid estate keeps the example's classes and adds its own. Placing a part in a class is a `set_layers` overlay entry; a part placed in a class its trust zone does not allow is left for the model checks to report. The compiled overlay keeps its `account_classes`, `zone_accounts` and `elements` maps, creating an empty one only when a patch writes into it and the input lacked it.

A finding kind says how a finding of that kind closes. `id`, `name` and `kept_gate` are non-empty strings, and an optional `description` is one too; `closure_check` is a mapping of three non-empty strings, `check_type`, `judged_by` (the id of the part that judges the check) and `expected_outcome`; `recovery_measure` is a mapping of two non-empty strings, `name` and `definition`; `never_closes` is a non-empty list of strings; an optional `held` is a mapping of three non-empty strings, `kept_test`, `judged_by` (the id of the part that judges the kept test) and `converts_when`. Any other shape, in an added kind or in a `set`, is `op.malformed`. The applier checks shapes only; the model checks judge the content (that a kind whose id is `path` is registered, and that each judging part is model-free).

When no layer is compiled, an op's layer keys are still checked for shape, `set_layers` still checks its target in the model, the account class ops still check their zones, and nothing is written to a layer; `op.layer-incomplete`, and `op.exists` and `op.target-missing` for an account class, need the overlay and are checked only when a layer is compiled.

### Declaring what a modify replaces (PA-22)

The bundle includes `ratchet-tools-expects.ts`. Run `bun upstream/ratchet-tools-expects.ts --file build/base/model.yaml --collection elements --id s3.approval-service --fields owner,responsibility` on the compiled full record immediately before the operation. It prints an expects mapping using the algorithm below. It reads exact ids or names from list collections and exact keys from mapping collections; nested collection paths use / with JSON Pointer escaping. An absent field hashes as absent; a missing or ambiguous record refuses with exit 2. See workflow-change-design.md for full-model, layer and shared-claim examples and for taking a baseline after preceding operations. The helper's fixtures are fixtures-expects.yaml. The helper supplies no acceptance or evidence of the proposed replacement's correctness.

Because a `set` replaces a whole value, a patch written against one value of a field silently overwrites whatever a newer edition or an earlier patch has put there since. `expects` turns that overwrite into a refusal. `modify_element`, `modify_relationship`, `modify_contract` and `modify_finding_kind` may carry it; no other op does.

```yaml
- op: modify_element
  id: s3.approval-console
  set: { responsibility: "Approvers approve or deny one exact action, and see its consequence tier." }
  expects: { responsibility: "b6ac893bc4c7" }   # the hash of "Approvers approve or deny one exact action."
```

`expects` is a mapping with one entry for each key the `set` names and each key the `unset` lists, and no others; each value is a string of exactly 12 lowercase hex digits. Any other shape (not a mapping, a key the op neither sets nor unsets, a key of the `set` or the `unset` with no entry, a value of another form) is `op.malformed`. For a key the op takes away, the entry is the hash of the value it takes away.

The hash of a value, which a builder computes from this text alone:

1. Take the value as a YAML 1.2 parser using the core schema reads it from the model: `1.0` is the number 1, `2026-10-19` is a string, and a folded block is one string.
2. Write it as canonical JSON (RFC 8785): no whitespace anywhere; object keys sorted by their UTF-16 code units; in strings, escape `"` and `\` with a backslash, write U+0008, U+0009, U+000A, U+000C and U+000D as `\b`, `\t`, `\n`, `\f` and `\r`, write any other character below U+0020 as `\u00` and two lowercase hex digits, and write every other character as itself (non-ASCII included, never as a `\u` escape); numbers in the shortest form that reads back as the same number (`1`, `0.5`, `1e+21`); `true`, `false` and `null` as written.
3. Take SHA-256 over the UTF-8 bytes of that text, written as lowercase hex, and keep the first 12 digits.

A field the target does not have hashes the empty byte string, `e3b0c44298fc`; no canonical JSON text is empty, so an absent field never matches a present one. A field whose value is null hashes the text `null`, `74234e98afe7`. For a string a person can check a hash in a shell: `printf '%s' '"Approvers approve or deny one exact action."' | shasum -a 256 | cut -c1-12` prints `b6ac893bc4c7`.

Each hash is compared with the field's value in the model as it stands when the op runs: after every earlier patch and every earlier op of the same patch. When one or more differ, the op fails with `op.expects-mismatch` and the patch is not applied (PA-9). Its one error names the target and, for each differing field, the field, the expected hash and the actual hash, as whole tokens; the wording around them is free. An op without `expects` is not checked this way.

`expects` is optional for an organization's patches, and recommended: when an earlier patch of the organization's, or a newer edition, has changed a field a held patch sets or takes away, the patch stops loudly at apply time instead of dropping what changed. To fix a refused patch, read the field's current value, restate in the `set` whatever of it should survive, and hash the current value.

### Taking a key away (PA-25)

A `set` can give a key a new value, and a null value is still a key. `unset` takes a key off the item, so the item holds no such key afterwards. `modify_element`, `modify_relationship`, `modify_contract` and `modify_finding_kind` may carry it, beside `set` or in its place. The organization scenario modify op also uses this rule under PA-32.

```yaml
- op: modify_element
  id: jig:stop-gate
  unset: [not_harness]
  set: { harness: { stop_gate: true, telemetry_export: full, version_pinning: true, blocking_hooks: true } }
  expects: { not_harness: "<hash of the reason it holds>", harness: "e3b0c44298fc" }
```

The op above redraws a part that declared why it is no harness as a harness, in one op, so no state between the two ever applies. Each rule follows from the op table and steps 11 and 12:

- `unset` is a list of key names, each a non-empty string, with no name twice. A modify op takes `set`, `unset` or both, and at least one of them is non-empty. A key may not be in both. Any other shape is `op.malformed`.
- `unset` may list any top-level key of the item except its identity (`op.identity`, step 12), its provenance (`op.provenance`, step 12) and the keys its kind requires (`op.unset-required`): an element's `id`, `name`, `system`, `level`, `kind` and `responsibility`; a relationship's `id`, `from`, `to` and `kind`; a contract's `name` and `description`; a finding kind's `id`, `name`, `closure_check`, `kept_gate`, `recovery_measure` and `never_closes`.
- An element's optional `role_class` is fixed on add. Setting it later is `op.malformed`, and unsetting it is `op.unset-required`. Its omission on add remains allowed.
- Every key `unset` lists must be a key the item holds when the op runs, after every earlier patch and every earlier op of the same patch, or the op fails with `op.unset-absent`, whose text names the target and each missing key as whole tokens. A key that holds null is a key the item holds, so an `unset` takes it away. A misspelled key therefore stops the patch instead of applying as nothing.
- With `expects`, each key the op takes away has an entry, the hash of its value as the op finds it (a null value hashes `74234e98afe7`). After the op the key is absent and hashes `e3b0c44298fc`, so a later op of the same patch that sets it again expects that hash.
- The item is recorded as modified, exactly as a `set` records it (PA-11).

A key inside a list or a mapping is not a top-level key, and an `unset` cannot name it. Change it by restating the whole list or mapping in a `set`.

### Checking references at the end of a patch (PA-8)

16. After the last op of a patch, check every item the patch added or modified, every view it added or extended, and every seam it extended:
    - a relationship's `from` and `to` name existing elements;
    - each name in a relationship's `carries` names an existing contract;
    - an element's `trust_zone`, when not null, names an existing zone; its `parent`, when present, names an existing element; its `system` names an existing system;
    - a view's `elements` and `relationships` name existing items;
    - a finding kind's `closure_check.judged_by` names an existing element, and so does its `held.judged_by` when the kind has one;
    - in a seam the patch extended, each crossing's `id` names an existing relationship and each name in its `carries` an existing contract.
    Each unresolved reference is one error `ref.dangling` with `op` null, naming the item, the key and the missing value, each as a whole token (the wording around them is free). An item the patch removed again is not checked. Checking at the end lets a patch add a contract after the relationship that carries it.

### Known limitations

- A `set` replaces whole top-level values and an `unset` removes them, so a patch cannot edit or remove one entry inside a list without restating the list. `expects` detects that a value changed; it never merges the change.
- Step 6 asks only that the YAML parser refuse what YAML 1.2 refuses. YAML 1.2 also refuses a mapping that repeats a key and indentation by tabs; no fixture exercises either, and a lenient parser may accept them, so an ops block should hold neither.
- An organization patch cannot add a system or change the shipped `systems` list.
- Organization failure scenarios change through PA-32.
- `modules.yaml` is copied as shipped. A patch cannot change a module declaration. Removing a relationship a module's interface point names leaves the point naming it; the model checks read the relationship as removed, since the output model lists it under `retired`.
- No op takes a crossing or a contract off a seam, adds a seam, or changes a seam's other keys except exposure through PA-30: removing a relationship takes its crossing away, and the edition's authors change the rest. So a `modify_relationship` that moves an end of a declared relationship until it no longer crosses the seam leaves the seam naming it, which the model checks report as `seam-ref`; to move a relationship off a boundary, remove it and add it again under a new id.
- An account class cannot be removed by a patch; `modify_account_class` with an empty `zones` list leaves it allowed nowhere.
- No op renames or removes a view. A view id with no separator after its patch id (`O100` on patch `O10`) keeps patch `O100` from applying for as long as `O10` applies, so the organization gives its next patch another number. Naming views with a hyphen after the patch id avoids this.

## Errors, warnings and exit status

Each message has `code`, `file` (patch file name, or null for run-level messages), `op` (index or null) and `text`.

Errors: `file.duplicate-id`, `patch.title`, `section.missing`, `section.empty` (accepted patch), `status.invalid`, `ops.block-count`, `ops.parse`, `preview.invalid`, `depends.unmet`, `op.unknown`, `op.malformed`, `op.provenance`, `op.identity`, `op.unset-required`, `op.namespace`, `op.exists`, `op.target-missing`, `op.unset-absent`, `op.still-referenced`, `op.bad-reference`, `op.layer-incomplete`, `op.expects-mismatch`, `ref.dangling`, `overlay.unrecorded-change`, `shared-acceptance-required`, and the run-level `options.invalid`, `input.unreadable` and `output.unwritable` described below.

Warnings: `file.name`, `section.empty` (proposed, rejected or withdrawn patch), `section.order`, `ops.unknown-key`, `overlay.unrecorded-file`.

Run-level checks run in this order, and the first that fails stops the run: the options, the shipped model, the patch directory, the version record, the recorded overlay (read and its hash compared), the layer files. So a run with invalid options reports `options.invalid` alone, even when the patch directory is missing. One option check waits for the overlay: an output layer directory that is the found overlay's folder is `options.invalid` once the overlay is found.

Run-level errors that stop the run: `options.invalid`, `input.unreadable` (the shipped model, the patch directory, a present version record, the recorded overlay, or a layer file when a layer is compiled), `output.unwritable` (the output model or the output layer), and `overlay.unrecorded-change` (the recorded overlay's hash differs from the record; no patch is applied, nothing but the report is written).

Exit 0 when the report holds no errors and the model (and the layer, when compiled) was written. Exit 1 when any error was reported, `overlay.unrecorded-change` included: the input is readable, and the fix is a patch or a recorded baseline, never a path. Exit 2 when an input cannot be read, an output cannot be written, or the options are invalid; the report is still written when its path is writable.

## Not in scope

- Producing the risk and threat-model delta (the impact report tool), or judging whether a patch is wise.
- Accepting a patch: a person writes the Status line.
- Checking the output model against the should-never rules and consistency checks.
- Moving patches to a new edition, renaming identifiers or recording the organization's version (the upgrade tool).
- Editing patch files. The applier never writes to the patch directory.

## Namespace targets and shared outputs

- **PA-28** An existing target may be bare, `jig:<id>` or `shared:<id>`. Match the whole identity, including its namespace. An organization addition keeps the existing addition grammar after its namespace prefix. A removal cleans contract membership, views, seams and compiled layers across every loaded namespace under the existing removal rules. A missing namespaced target fails atomically with `op.target-missing`.
- **PA-29** With `--shared <seams.yaml>`, also require `--shared-out <path>` and `--org-out <path>`; `--org <org.yaml>` optionally loads existing root exceptions. Import shared parts, systems, zones, contracts and whole crossings before applying any op. When the input model's `composition` is set and is not `full` (a lone composition), import only incident crossings: those not listed in `composition_omitted.relationships`, with at least one endpoint that is a non-boundary element of the model, and with an endpoint in the own namespace or both endpoints shared; also leave out the contracts listed in `composition_omitted.contracts`. A model with no `composition` key, or `composition: full`, imports every crossing and contract. An `add_relationship` whose id is `shared:oNN-...` writes a whole shared crossing, preserving namespaced design endpoints in the root file. A `set_seam_exceptions` op has `seam: shared:<id>` and `exceptions: []` or a list of records with non-empty `contracts`, `accepted_by`, `until` and `why`. It replaces that seam's organization list in `org.yaml`; an empty list declines the shipped default. Refuse a missing seam with `op.target-missing`, unknown contracts with `op.bad-reference`, and malformed records with `op.malformed`. The model checks judge the exception's end and scope. Write shared and organization outputs only when the run has no errors. Source files remain untouched.

Read the own namespace and composition from the input model's `namespace` and `composition` keys. A missing namespace defaults to ratchet. PA-29 adds no option that changes these model fields.

The adopter-facing tool specified here applies organization patches only. Author source-series compilation belongs to the edition authoring pipeline and is outside this tool's inputs, outputs and acceptance claim: this suite supplies no standalone author-compiler interface or fixture. No author-compiler implementation is required to pass this specification.

Import root `systems`, `zones`, `parts`, `crossings`, `contracts`, `seams` and `views` into the corresponding model lists (zones become `trust_zones`, parts become `elements`, crossings become `relationships`). Bare shared identities gain `shared:` once; existing qualified identities remain qualified; own `<namespace>:` references become bare in the model. Keep an already composed record rather than importing a duplicate whole identity. On shared export, shared record ids/names become bare and bare own design references gain `<namespace>:`; other prefixes stay intact. Export the entire shared document, keeping its other keys, with updated lists, attached tests and seam exposure. Namespace conversion rewrites identity/reference fields, never typed `fields` vocabulary or owner records. Check the organization addition grammar after removing its namespace prefix. The organization output is a mapping with `seam_exceptions`, keyed by complete seam identity; retain an explicit empty exception list as `[]`.

The fixtures file's `namespace_model`, `namespace_shared` and `namespace_fixtures` exercise the same core directly. Every case supplies `ops`; `error` must equal `report.errors[0].code`, and `shared_crossings` and `exception_key` assert the root output. Cases require unchanged inputs on success and refusal.

Removing a part also removes it from each loaded shared agreement test's `elements` list and from declared exposure. A test left with no part is retired under the existing retired-scenario report. A typed field's name is schema vocabulary, so namespace conversion never rewrites the contents of `fields`.

Namespace fixture keys are `name`, `ops`, `error`, `shared_crossings`, `exception_key`, `absent_consumer`, `acceptance`, `composition`, `missing_owner_identities`, `missing_owner_records`, `exposure`, `outsider_field`, `claim_owners`, `claim_expects`, `bound_claim`, `bound_contract_owners` and `role_copied_identities`. Clone `namespace_model` and `namespace_shared` per case, write the supplied ops and acceptance into one accepted organization patch, and run with shared and organization outputs. `composition: jig` sets namespace jig, keeps only `jig:receiver` and makes its id bare `receiver`; the complete shared owners remain loaded. `missing_owner_identities` sets each first-contract owner identity to null; `missing_owner_records` deletes that owners list. `role_copied_identities` sets each first-contract owner identity to that row's role. `shared_crossings` compares the exact root crossing ids; `exception_key` requires one stored exception under that key; `absent_consumer` requires that no contract of the root shared output lists that qualified id in its `consumed_by`; owner rows are not compared. Cleanup entry keys are `name`, `removed`, `remaining`, `field_name`. For removal, attach `failure_scenarios: [{id: shared-test, elements: [ratchet:sender, <removed>]}]` to the first shared contract and `exposure: {jig: [{part: <removed>, agent_reachable: true}]}` to the first shared seam; remove the part with the two fixture owner acceptances. For `field_name`, attach `fields: [{name: <field_name>, type: id}]` to that contract and apply empty ops, preserving that entire field record. These controls are fixture setup, never tool options.

The fixtures file's `namespace_cleanups` uses the same namespace model and shared base. With `removed` and `remaining`, attach a shared test naming both parts and an exposure record for the removed part, remove that part, and require the test's `elements` to equal exactly `[ratchet:<remaining>]` (the bare `remaining` value with the `ratchet:` prefix an own reference gains on export) and the seam to keep no exposure record. ## Bind shared claim owners

**PA-31** A `bind_claim_owners` op changes only owner identities and their basis on an existing shared claim. The root shared document stores a bare claim id, such as `SH-1`. Match each binding to the claim's exact shipped side and role. Side, role and identity are nonblank strings. Basis is confirmed or provisional. A binding whose identity equals that row's shipped role, compared trimmed and case-insensitive, fails as `shared-acceptance-required` with a message saying an identity names a person or team, not the role (MC-114). Each side and role pair occurs once. Preserve other owner rows, claim content and shipped sides and roles. Optional `expects: {owners: <hash>}` compares the entire current owners list by PA-22. It has no other key. A missing shared input or claim is `op.target-missing`. An unknown side and role pair is `op.bad-reference`. A stale hash is `op.expects-mismatch`. Bad shapes and extra op or binding keys are `op.malformed`. Record normal modification provenance on the shared claim. Export it in the shared document's claims list.

MC-114 requires acceptance from every newly bound identity for initial identity-only binding. Reassignment needs former and new identities. Changing provisional to confirmed remains an identity-only change and needs the recorded identity's acceptance. `bindings` may name only some of a claim's rows. The others stay role only, name pending (MC-114): they need no acceptance and authorize nothing. A later binding of a further row is identity-only too, and needs every identity recorded on the claim. The first run needs no binding. A row with an identity and either basis is filled. ## Declare organization failure scenarios

**PA-32** `add_failure_scenario` takes one `scenario` mapping. `modify_failure_scenario` takes `id` and the usual `set`, `unset` and optional `expects` fields. These ops require a compiled failure layer. They edit only organization scenarios with stable ids of the form `org.<slug>`, optionally qualified with ratchet or jig. Slug starts with a lowercase letter or digit and continues with lowercase letters, digits, dots or hyphens. A shared prefix or shipped scenario id is `op.namespace`. A duplicate add is `op.exists`. A missing modify target or failure layer is `op.target-missing`. A modify cannot rename the id, write provenance, or unset a required field. PA-22 hashes apply to every set or unset field.

A scenario requires nonblank `id`, `title`, `trigger`, `required_behavior`, `invariant`, `detection` and `runbook`, a non-empty string list `elements`, and `test: {kind: pipeline|game-day, steps: <nonblank text>}`. It may carry a nonblank module tag already present in the loaded model or its known omitted module inventory. An unknown module is op.bad-reference and a malformed tag is op.malformed. No other scenario or test fields are accepted. These are declarations of tests and responses. They never attest that a test ran. Invariant must name the loaded failure layer's invariant registry. Runbook must be `RB-<scenario id>` within the same namespace. This declares that scenario's runbook identity. Invalid invariant or runbook references are `op.bad-reference`. After the last op, every named element must resolve in the model or its known omitted inventory, otherwise `ref.dangling` with op null. A prefix alone resolves nothing. Unknown shapes are `op.malformed`. Append an added scenario in op order, replace a modified scenario in place, and record ordinary patch provenance. Atomicity covers the model, shared document and entire layer together.

The composer projects scenario and runbook identities with their design, preserves mixed scenarios whole and omits scenarios whose named parts are all omitted. The impact report includes every added or modified scenario even if no model element changed. The threat grid reads the compiled failure layer and traces control actions through these scenarios by its existing element rules. ModelResponse E keeps its existing closure requirement.

## Exact patch and fixture contracts
