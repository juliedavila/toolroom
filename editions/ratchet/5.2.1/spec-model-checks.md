# Specification: model checks

The model checks read the organization's compiled design (the shipped `model.yaml` after the organization's patches are applied) together with its design layer, and fail the build when the design breaks a structural safety property. They answer one question before anyone builds or changes a part: does the design, as drawn, still keep the four rules? The organization's platform team runs them on every patch, in the same pipeline that applies the patch, and nobody merges a patch that leaves an error. They take the organization's compiled model and layer (the patch applier's outputs), so an organization's own parts, roles, contracts and overlay are judged by the same rules as the shipped design.

## Ideal state

- **MC-1** Every element names a known system, a known parent (when it has one), a known trust zone (when it has one) and one of the six role classes. Element and relationship ids are unique.
- **MC-2** Every id referenced by a relationship, view, sequence step or contract names an element (or, for a view, a relationship) that exists.
- **MC-3** In core-only mode, elements tagged with a pluggable module and everything that touches them, and relationships and contracts tagged with a module, are removed before any model rule runs, and the shipped model passes.
- **MC-4** A producer that holds untrusted content, holds non-public data and has an outbound path sends every outbound request through the load-bearing request-data gate on a non-optional edge. A relationship with no `optional` field is non-optional.
- **MC-5** Such a producer reaches nothing in the execution zone directly, and sends proposals only to authorization (system S3). This is rule 1, a proposal is never permission, applied to routes.
- **MC-6** The request-data gate is marked load-bearing whenever any producer route holds all three legs.
- **MC-7** Untrusted content propagates only along data, inference, feedback and observation edges, and stops at an edge marked as structured.
- **MC-8** The part that builds test-drafting context never receives untrusted content.
- **MC-9** No part in the control or execution zone touches the model path or sits on an inference edge (the AI-free control plane rule). For this rule the model path is the fixed list that the table of shipped ids under Inputs names, less any part with `model_boundary: true`; it is not the realization's `model-access` plane.
- **MC-10** Every model-boundary gate sits in the control zone, decides deterministically and sends nothing into the control or execution plane.
- **MC-11** No part that decides (authorization, coverage, verdict, closure, promotion, tier attestation) takes a typed model decision or model-derived output as input, except a proposal into authorization.
- **MC-12** Exploitability is never a typed decision type, whether the types are declared as a list or in prose.
- **MC-13** Every tier-zero part (fail closed) sits in the control or execution zone.
- **MC-14** A part marked as an isolated draft sends only to people and to the request-data gate, and never receives test-drafting context. This is rule 2, proof conditions stay out of the testing agent's reach, applied to the drafter.
- **MC-15** `realization.yaml` covers exactly the model's elements, with valid planes, keys, examples and swap kinds.
- **MC-16** `quality.yaml` covers exactly the model's validation parts and contracts (the organization's own included), with known tiers and failure modes, and every control part in the control zone fails closed or marks unknown.
- **MC-17** Every failure scenario names real elements and its own runbook.
- **MC-18** Every relationship that joins two planes carries a contract, or records in `no_contract` a one-line reason it needs none (a plain information feed), and every contract a relationship carries exists. A part with no plane counts as a plane of its own, so the rule never skips it.
- **MC-19** Every critical path names real or declared external parts, and every required hop is a modeled relationship.
- **MC-20** Each overlay file covers exactly the model's elements, with valid fields, an account its trust zone allows, and a statement of what the organization keeps for every rule-enforcing part. The shipped `overlay-aws.yaml` is a worked example; an organization's own overlay in the same shape (its own account classes, zone placements and services) is judged by the same rules.
- **MC-21** The bare edition passes every check with zero errors in all four compositions; its null-ended seam exception warns that it is awaiting the organization's end date and covers what it names. In any organization composition, a null end is an error and covers nothing until the organization layer supplies a calendar date; a past date is expired. MC-111 defines the four compositions. The full composition uses the released pinned edition.
- **MC-22** Every error and warning carries a stable code from the lists below, a location and a message. An unknown trust zone or an unknown overlay account yields one error, with no second error for the zone's account placement. A code is an error or a warning by the lists alone: a finding on an item an organization's patches added or changed has the same code and severity as the same finding on a shipped item.
- **MC-23** A part marked as agent-reachable (a system where coding agents run, such as the secure-creation loop) receives no relationship that carries a proof condition (`OracleSpec`), a kept regression (`RegressionSpec`), or a contract with verdict, fixture-set or member references (`FailureClass`, `RoadAssurance`, and the full result of a class test, `ClassTestResult`), is never listed as a consumer of any of those five contracts, and never receives untrusted content, directly or by propagation. A kept regression reaches it only through the separate `shared:DerivedCheck` contract, which reports pass or fail with a fixed message and carries no expected-outcome hash; failure classes and road assurance reach it only through their projections `shared:ProvenClass` and `shared:RoadAssuranceStatus`, and a class test's result only through its projection `shared:ClassTestCount`, which carries the rule id, rule version and a binary pass or fail result, with no member counts. This is rule 2 and the quarantine applied at the boundary with a coding agent's loop.
- **MC-24** When `modules.yaml` is present, every pluggable module is declared in it with a name, a category from the four (signals-in, stakes, reach, prevention-out), interface points (what crosses, in which contracts, over which relationships, with a target on the wiring ladder), a switch-on test, how it inherits each of the four rules, the ownership separations it needs, the existing practice it wires in, and its dependencies. Every module tag on an element, relationship or contract names a declared module.
- **MC-25** Every interface point names relationships that exist and touch its module, contracts that exist, a direction, and a target on the wiring ladder (none, connected, conformant, aligned). A relationship the organization's patches removed, which the compiled model lists under `retired`, no longer counts against a point that names it. A point whose contracts differ from what its relationships carry is a warning: the declaration lags the model. Each module seam's module side names a declared module, and each crossing a seam records at an interface point names one `modules.yaml` declares. Whether a relationship across a module's boundary is declared is MC-108's.
- **MC-26** Every part that lets an agent act, or a judgment stand, without a person approving each instance (a part marked `grants_authority`, or any producer of the `AutonomyGrant` contract) receives the design limit (`DesignLimit`) on a non-optional relationship from a part in the control zone. Every relationship that carries a `DesignLimit` comes from the security risk owner, and every one that carries the consequence line (`ConsequenceLine`) from the business risk owner, or else from a part in the control zone that grants no authority itself (the dial register that holds and forwards them). The design caps what an agent may touch, and nothing, promotion review included, can widen a grant past a limit it never reads or that anyone but its owner could write. This is rule 1, a proposal is never permission, applied to grants that run without a per-action approval.
- **MC-86** The outsider label is inherited: anything a model writes after reading outsider text keeps the label until a person or a model-free check clears it. Every relationship marked as structured whose source is exposed to untrusted content names its clearing (`cleared_by`), and the part it names sits on the relationship (its source or target) and is a person or a model-free part.
- **MC-87** A fixing agent's description of a weakness (`shared:FixBrief`), including the `PersonWrittenBrief` submitted to its builder, comes only from a person or a model-free part that is not exposed to untrusted content: it is person-written, or derived by rule from the proof condition and the model-free reproduction. A brief may pass through an exposed part, such as an issue tracker, when the relationship that delivers it names the part whose signature the receiver verifies (`verified_from`), and that part may write a brief itself: the model shows who wrote the brief, and the signature shows it arrived unchanged.
- **MC-88** A part marked as a learning store (what the loop learns from its own validations) is written by no producer and no part on the model path, and everything it releases along a propagating relationship passes its own retrieval check: the relationship is structured and names the store as its clearing. Provenance set when an item is stored is checked again when it is read. A person may read learned items as free text, and a replica that is itself marked as a learning store is judged by this rule in turn, so neither needs the retrieval check.
- **MC-89** A part that drafts a fix takes no free text from a candidate finding or a disposition. Every relationship to such a part that carries `CandidateFinding` or `FindingDisposition` is marked as structured and names its clearing (`cleared_by`), and the part it names sits on the relationship and is a person or a model-free part, so the drafter receives identifiers, statuses, enumerated fields and references, and its description of the weakness is the fix brief (`shared:FixBrief`). A part drafts a fix when it is listed among the producers of `PatchCandidate` or `FixPath` and is not a person.
- **MC-90** The restore of an attack injection never depends on the control plane. A part marked as applying injections receives a restore grant (`RestoreGrant`) on a non-optional relationship, so it holds the restore before any injection starts. The rule judges only what the restore uses, in both directions: nothing the restore runs through waits, on a required relationship (non-optional and synchronous), on a part in the control zone for the restore grant or for a relationship marked as one the restore uses, and no credential or key the restore needs flows into it at run time from the control zone, unless the same contract arrived with the restore grant before the injection started. The restore runs at expiry in the cell under the credential issued with its grant, and the control plane only records it afterwards.
- **MC-91** When the model holds the finding-kind registry (`finding_kinds`), it registers `path`, since a finding with no kind is a path finding; no id appears twice; every kind declares its closure check (a check type, the part that judges it and the expected outcome), its kept gate, its recovery measure (a name and a definition) and at least one thing that never closes it; and the part that judges each closure check exists and is model-free. A kind may declare `held`, which admits findings a control stopped in the reproduction; a kind that does names the kept test that exercises that control, a model-free part that judges it, and what converts the finding, so no finding is held by a control that no test checks. No model closes a finding of any kind. The organization's kinds are judged the same way.
- **MC-92** Every part in the control zone is administered only under dual control: it receives a non-optional administrative session (`AdminSession`, kind control) from a broker, directly or through one of its ancestors. The brokers are the shipped privileged access broker and any control-zone part the organization declares as one (`admin_broker: true`), such as its own privileged access tool; a broker itself is exempt (break-glass only). A model whose control zone has parts and no broker is an error, so removing the broker never switches the rule off.
- **MC-93** Every store (an element of kind store or registry) states its partitioning: partition keys (`partitioned_by`, a non-empty list), or a reason it holds no evidence content (`unpartitioned`, a non-empty string), and never both.
- **MC-94** The JSON report lists, for MC-86 to MC-93, MC-95 to MC-102, MC-91's held check and MC-104 to MC-108, what each rule judges (`judged`): the parts, relationships, contracts, contract fields and finding kinds in its scope. A rule that passes because nothing is in its scope looks the same in the errors as a rule that passes on every item, so these sets are compared between the shipped model and the organization's patched model: MC-109 refuses a patched model that takes a shipped item out of one, and the upgrade blocks the patch that does.
- **MC-95** A store that states a reason it holds no evidence content, and states no partition keys, receives no evidence content. Every relationship into it that carries an evidence-content contract (the seven named under Inputs, and any contract marked `evidence_content: true`) lists that contract in `by_reference`, which says the relationship delivers ids or references to those records, never their content.
- **MC-96** No model in the orchestrator. A part marked as orchestrating (`orchestrator: true`: what decides which task runs next, leases and retries tasks, and holds a run's state) is not on the model path and is not a model-boundary gate, and no relationship that touches it is of kind inference or joins it to a part on the model path. Model output reaches the orchestrator only as typed records sent by a part off the model path, so an agent's reply never steers the workflow directly.
- **MC-97** Agent memory is a learning store. A store or registry that a model caller writes in free text, and that a producer that calls a model, or a part that builds test-drafting context, reads, is marked `learning_store: true`, so the learning-store rules (MC-88) judge who writes it and what it releases. A replica of a learning store carries the mark itself (MC-88).
- **MC-98** Every person who issues a control or authorization action hears the measured outcome of those decisions. Each element with role class human that is the source of a relationship of kind control or authorization receives a non-optional relationship of kind feedback, from another element, that carries a contract declaring the quantity it measures (`measures`). A person who approves, decides or sets a limit can only correct their own drift when the part that knows how their decisions turned out tells them, so the organization's own roles are held to this rule too.
- **MC-99** Every coding harness states its parity: whether it has a stop gate, what session telemetry it exports, whether its version can be pinned and whether its hooks can block. A harness with no stop gate names the part that runs the same suite in its place and sends to that part on a non-optional relationship, so the suite still runs on every change from that harness before the change leaves the developer's machine.
- **MC-100** Every declared assumption (an entry in an element's `assumptions` list) states what it assumes, the parts and relationships that rely on it, a fallback, and the parts that carry the fallback, and no part that carries a fallback relies on the assumption it falls back from, itself or through a part that contains it. A premise the design leans on is then a checked declaration with a way out when it fails.
- **MC-101** A part that routes by rule (`routes_by_rule: true`) calls no model, and every relationship into it from a model caller is marked add-only (`add_only: true`): a model may add items to a route that sends them to a person, and no relationship lets it take one off. This is rule 4, acceptance is independent, applied to the choice of what a person reviews.
- **MC-102** A contract that declares typed fields (`fields`) declares each one with a name no sibling field uses, a known type, values for an enumeration, an item type for a list and fields for an object, and marks with `untrusted: true` every field an outsider can write. No relationship into an agent-reachable part carries a contract with such a field. Both sides of an interface then build and validate against the same schema, and outsider-writable text stays out of a coding agent's reach field by field.
- **MC-104** Every evidence record lands in a partitioned store. Each evidence-content contract (the seven named under Inputs, and any contract marked `evidence_content: true`) whose `produced_by` names an element that exists is carried by at least one relationship whose target is a store or registry with a non-empty `partitioned_by`. The rule judges the property, so an organization's own partitioned store passes in place of a shipped one, and a contract with producers that no relationship carries fails.
- **MC-105** Evidence into a store names what it brings. Every relationship of kind evidence whose target is a store or registry names at least one contract in `carries`, so the evidence rules can follow what lands there.
- **MC-106** A restricted contract reaches only its listed consumers. A contract may declare `audience: restricted`; every relationship that carries it ends at an element its `consumed_by` lists. An organization widens the shipped restricted readers only with an audience exception in force naming that contract. The exception flags the audience finding as a warning and changes no other rule; there is no warning stage.
- **MC-107** Every part that steers a coding agent says whether it is a harness. A part whose role class is not human and that is the source of a non-optional relationship of kind control to an agent-reachable model caller (an element with `agent_reachable: true` that is the source or target of an inference relationship) declares exactly one of the `harness` key, which MC-99 then judges, and `not_harness`, a non-empty string saying why it is no harness.
- **MC-108** Every relationship across a seam that carries a security-relevant contract, or carries no contract, is declared on that seam. A seam is a boundary the model declares in its `seams` list, between a pluggable module and the rest of the design, or between design namespaces for a shared seam under MC-113. A relationship crosses a seam when its two ends sit on different sides, and the seam declares it by naming it with every contract it carries. An undeclared crossing whose contracts are all not security-relevant is listed as a warning. A contract is security-relevant when a check reads it, by the tests under Behavior (its floor, derived on every run), or when a person raised its mark; nobody may lower one. While an organization's strictness exception holds, with a named risk acceptor and an end, an undeclared crossing that carries only contracts the exception names is flagged as a warning instead of refused. The edition ships one such exception with a null end, awaiting the organization's end date. In a bare edition it warns and covers what it names. In any organization composition it is an error and covers nothing until the organization layer supplies a calendar date; an organization may also decline it. No relationship across a seam carries a contract the seam says never crosses, declared or not, and no exception changes that or any other rule.
- **MC-109** No patch takes a shipped item out of a rule's scope. Given the shipped model, every item of a judged set (MC-94) of the shipped model that the checked model still holds is in the same set of the checked model, whatever took it out: a key taken away, a key set to null, a value or a kind changed, a relationship made optional. An item the checked model no longer holds was removed, and this rule does not judge it. This is the upgrade's switch-off guard (spec-upgrade.md, UP-27) run when a patch is first checked, so the refusal comes at once.
- **MC-110** Every relationship ends at a part that each contract it carries lists in `consumed_by`. A violation is an error in every composition, on a shipped item or on one an organization's patches added or changed. MC-106 alone reports an unlisted restricted delivery.

## Inputs

### Namespace compositions

- **MC-114** Every shared contract, shared part assumption and shared claim carries `owners`, a list of `{side: <qualified part or relationship>, role: <shipped owner role>, identity: <organization-assigned identity>}` records in the dependency layer. A contract includes every producer and consumer; an assumption includes its holding part, relied-on parts or relationships and fallback parts; a claim includes its rests_on parts and relationships. A relationship includes the owner roles of both endpoints. Ship roles with null identities; the organization fills identities in its own layer, including owners for absent designs. Keep qualified sides unchanged in every projection. For any changed agreement or shared contract quality entry, read the before and after owners records in every composition, including lone ones; validate each side has records and every present side's actual owner roles are covered. Boundary declarations do not supply identities. Require `acceptance: [{owner: <assigned identity>, accepted: true}]` from every recorded identity, deduplicated across both inputs, so removal or reassignment still needs the former owners. Missing records, sides, roles, identities or acceptance, false or malformed entries and role-only acceptance fail as `shared-acceptance-required` before any output. An initial identity-only binding can be accepted by the newly assigned identities; it cannot also edit agreement content or quality. No agreement change requires no acceptance entries. A row whose `identity` is null, absent or blank is role only, name pending. An identity names a person or team. An identity equal to its row's shipped role, compared trimmed and case-insensitive, is the role copied and is no identity: an after record carrying one fails as `shared-acceptance-required` with a message saying an identity names a person or team, not the role, and a before record carrying one counts as pending. That is the shipped state, and a first run may keep it: the first run needs no identity binding. A pending row supplies no identity, so it never accepts or authorizes anything. An identity-only change may bind some rows of an agreement and leave others pending; a row pending in both inputs needs no acceptance. A later binding on a partly bound agreement is identity-only too, and needs every identity recorded on that agreement in either input. Any other change to an agreement or its quality entry fails as `shared-acceptance-required` while any of its rows is pending. The compiler and organization patch applier enforce this rule.

- **MC-115** In organization context, as MC-108 establishes it (`--org`, or the compiled model's `meta.organization_version` or `meta.organization_patches` key), each shared agreement with at least one pending owner row is one `shared-owner-pending` warning at the agreement, whose message names the side and role of each pending row. The agreements are the contracts and part assumptions with an `owners` list in the model being checked, in the mode being checked, and the shared claims with an `owners` list in the layer folder's `seams.yaml`, when that file is present. A row is an entry of an `owners` list that is a mapping; any other entry is neither warned nor counted here. The warning never becomes an error. A bare edition, which ships every identity null, reports none. In every context, `summary.pending_owners` counts the pending rows of those agreements, so the size of the binding work comes from the tool. Pending rows block no check: every other rule runs on the same inputs.

- **MC-111** Check four compositions: Ratchet with its pinned Jig and shared layer; Ratchet with shared alone; Ratchet core without modules or Jig with shared core crossings; and Jig with shared alone. The engineering system and its premises remain in every composition. Core filtering in MC-3 also removes module-tagged relationships whose endpoints remain. The full pinned composition is the release gate. A working Jig composition is advisory and is reported separately. An absent released pin cannot be reported as a successful pinned composition.
- **MC-112** A lone composition retains whole shared crossings incident on its own design. Every crossing endpoint must declare all five marks even in a full composition; silence is never a negative mark. For each absent endpoint, read the shared seam's declared exposure, including `agent_reachable`, `exposed`, `model_free`, `role_class` and `kind`. A boundary represents that declaration, never the absent design's implementation. Missing exposure refuses composition with `composition-exposure-missing`. Before filtering any composition, compare all declarations with the complete current endpoints: agent reach, propagated exposure, model freedom, role class and kind. An unknown endpoint or differing mark is `composition-exposure-stale`. These refusals belong to the composition loader, the step that composes the source sets into a model, and it judges them on the shared layer's own records in its source `seams.yaml`: every row of each `seams[].exposure` list, and the `from` and `to` of every top-level `crossings` entry, where a bare id means `shared:<id>`. The model checks on a compiled model and layer folder do not run these refusals and never compare a model relationship's endpoints with the exposure rows, so an edit that points a model relationship at an undeclared part draws only model findings. Judge protected feeds and typed fields at the local edge, including outgoing feeds into an absent agent-reachable receiver. Boundary parts have no local storage, harness or controller obligations. The shared engineering premise retains its declared far-side reliance and fallback references. Such references resolve only when declared in shared data. Keep every listed seam check's full judged set non-empty.
- **MC-113** Own ids are bare. Imported ids keep `jig:` or `shared:` in a Ratchet composition, and `ratchet:` or `shared:` in a Jig composition. Resolve bare vocabulary in the own design first, then shared. The checks resolve each name in the table of shipped ids, and each contract a rule names, this way: the name itself when the model holds an element, relationship, contract, system or trust zone with exactly that id; otherwise the first id, searching those five lists in that order, that ends with a colon followed by the name, whatever its prefix; and in a model whose `namespace` is `jig`, `OracleSpec`, `RegressionSpec`, `FailureClass`, `RoadAssurance` and `ClassTestResult` with no such id resolve to `ratchet:<name>`. A part is a person when the text after the last colon of its `system` is `PEOPLE`. Thus `shared:EXT`, `shared:PEOPLE`, `shared:S4` and `shared:existing`, when present, have the rule meaning of EXT, PEOPLE, S4 and existing while keeping their full identities in findings. For an absent trust zone, overlay lookup tries `existing` and then `shared:existing`. Relationships, contracts, layers, units and report locations use the same identity. Shared crossings are whole relationships in `seams.yaml`; they declare themselves on a shared seam. Module seams stay in the own design and are derived anew from current interface points on every compile. A shared seam replaces the corresponding module boundary. Preserve non-module seams; organization `add_to_seam` operations run after this derivation. A shared contract with producers in more than one namespace is refused as `shared-writing-side`. Root exceptions for shared seams use their bare or `shared:` key, while own module seams use `<namespace>:<id>`.

Composition inputs are the full composed `model.yaml`, its layer files, `modules.yaml`, `units.yaml` and `seams.yaml`. A released edition must supply the portable dependency at `pins/jig/`; a draft that lacks it has no successful released-pin attestation. The frozen fixture dependency described below is test input and never attests the draft pin. A full model can be decomposed by id namespace: own bare records belong to its namespace, prefixed records to that prefix, and shared records are supplied by `seams.yaml`. Keep own and shared units/capabilities, filter views and sequence steps to retained parts and relationships, use shared `names` for boundary display, and place absent endpoints in `shared:EXT` and `shared:existing`. Before materializing fixture inputs, verify the SHA-256 of the exact `fixtures-model-inputs.yaml` bytes against its comment record in `fixtures-model-checks.yaml`; this binds the additional vectors to the fixture suite. The self-contained `fixtures-model-inputs.yaml` supplies `compositions`, keyed by full, ratchet, core and jig, each a map from edition-relative file name to a complete parsed YAML document. Write those documents into an isolated folder; no builder reconstructs the composed inputs or reads another edition. `sources` additionally supplies complete accepted source documents by portable `ratchet/<file>`, `jig/<file>` and `shared/seams.yaml` keys for the composition loader's declaration-refusal cases and source-patch cases. The composition fixtures select these supplied inputs: `composition` selects `full`, `ratchet`, `core` or `jig` from the edition's two own source sets and shared data. `remove_exposure` removes one declared endpoint record before loading; `remove_mark: {part, mark}` removes one required mark from its declaration. Both must refuse even in a full composition. `error_code` requires that refusal. The bare full, Ratchet and Jig editions have zero errors and report `seam-exception-awaiting-end` for the null end; core excludes the idle exception. An organization composition, full or lone, refuses a null end as `seam-exception-invalid`, with no coverage. Its organization layer must replace a shipped null end with a calendar date, never a milestone; a milestone replacement is `seam-exception-invalid` and supplies no coverage. A past date gives `seam-exception-expired`. Each of the four `fixture-mc-composed-<composition>.yaml` fixtures also pins every `judged` set to its exact ids, including empty sets, using the same order-independent comparison as other fixtures. A draft with no released pin reports these four working-source checks as advisory.

For lone projections, keep whole incident shared crossings and create boundaries only for their absent endpoints. Seed exposure from declared exposed boundary endpoints as well as untrusted relationships, and honor declared model freedom for local feed checks (MC-23 and MC-102). Boundary declarations do not enter local implementation sets, including `cannot_clear`, stores, harnesses and controllers; they can enter `exposed` and relationship sets such as `agent_reach_inputs`. Resolve far-side references only through the shared declarations of contract producers/readers, assumption reliance/fallback, claim dependencies, attached failure-scenario elements and seam `never_cross`. Retained assumption references resolve as MC-100 states: an element of the model as checked, after any core filter, a relationship for `relied_on_by`, or an outside reference (see Composition and acceptance fixture details). Layer element/contract entries follow retained local identities and view/sequence memberships follow retained graph records. Jig projects its own ids and runbooks to bare, Ratchet ids to `ratchet:`, and has no Ratchet finding-kind registry.

All four compositions run both the structural model checks and the design-layer checks (realization, quality, failures, plane joins, critical paths and, where applicable, module interfaces), plus every overlay check, with zero errors on the bare edition. Run this assertion separately on working inputs and the released pinned dependency. Each lone build judges a crossing at its own edge using the far side's declared exposure. A part with `boundary: true` represents that exposure and is not owned by the loaded design: it needs no realization, quality or overlay entry. Every retained own or shared implementation part keeps its coverage and field checks. Layer keys equal the complete ids in the model. Only the validation-part recognition test for an `s<digit>.` local id strips an imported `ratchet:` or `jig:` prefix. Namespacing never removes a quality obligation. Jig's own edition has no module declaration file, so its standalone run skips those checks and reports the absent file. A precomposed Jig input that supplies `modules.yaml`, including the supplied layer fixtures, runs the declaration checks on that file. The other structural, design-layer and overlay checks run in both cases.

The loader records `model.composition_omitted`, with `elements`, `relationships` and `contracts` lists containing only known source identities excluded by the selected composition (absent designs or switched-off modules), plus `modules` listing known modules with no retained implementation part. These lists are supplied fixture input too; they are not inferred from a failed lookup. Before judging a module interface point, prune relationships and contracts on these lists; a point left with no relationships is outside this composition and is not judged. A partly retained point judges its retained references normally. Only for a module on that omission list, a retained shared crossing touching a boundary may establish its module interface through the model's own declaration on a seam whose id starts with `shared:`: a crossing entry with that relationship's id and a `point` equal to `<module>.<point id>`, without inventing a module tag or implementation for the boundary. This exemption never applies to a loaded module, even if a patch removes a local endpoint's module tag. Module dependency ids (`depends_on` and `requires_module`) remain module vocabulary in every namespace. An unknown relationship or contract not on an omission list still fails, as does a local relationship that no longer touches its module. Organization retirement remains the separate `retired.relationships` rule.

Load own failure scenarios and scenarios attached to shared contracts or shared part assumptions; no free-floating shared scenario is introduced. A scenario whose non-empty element list consists entirely of known omitted parts is not loaded. Keep a mixed scenario whole: a retained element resolves locally, a known switched-off own module part is context from the unfiltered input, and an absent far-side element resolves only through the shared declarations, including attached scenario elements. The loader admits those shared references only after resolving them against known source parts. A namespace prefix alone never resolves a missing part. Every loaded scenario still checks its elements and runbook; an unknown local or far-side name remains `failure-unknown-element`.

**The null rule.** A seam exception's explicit `until: null` is the exception to this rule: it means awaiting the organization's end date, as specified under Seams. Every rule below that asks whether the model, an element, a relationship, a contract, a contract field or a finding kind has a key reads a null value as no key, so a null value and a removed key give the same result in every check. Rules that read a key's value already find no value in null: a null `measures` declares no measure, and a null `partitioned_by` or `unpartitioned` states no partitioning. Taking a key off an item this way, or with a patch's `unset`, can take the item out of a rule's scope; the judged sets (MC-94) show it, and MC-109 refuses it on a shipped item. The layer files keep the rules stated for them, and a separation's `enforced_by` in `modules.yaml` may hold null.

## Behavior

**Loading.** Parse all inputs, and confirm each layer file holds its required top-level entries (see Inputs); exit 2 otherwise. Every layer file except `modules.yaml` is required: a missing `realization.yaml`, `quality.yaml` or `failures.yaml` cannot be read, so the run exits 2 with no report, the same as a file that does not parse. The layer folder holds at least one overlay file (`overlay-<name>.yaml`) and may hold several, each checked; a folder with none exits 2 with no report. Quality coverage (MC-16), critical paths (MC-19) and the tier-zero rule all read `quality.yaml`, so none of them runs on a partial layer. When `modules.yaml` is absent, the module declaration checks (MC-24, MC-25) do not run and one `modules-absent` warning at `modules.yaml` says so, and every other check runs, core-only mode included (it drops whatever carries a `module` tag).

**Core-only mode.** Drop every element with a `module` key (the null rule: `module: null` is no tag, and the element stays). Drop every relationship whose `from` or `to` was dropped, and every relationship and contract with a `module` key of its own. Filter view element and relationship lists, contract `produced_by` and `consumed_by`, and sequence steps to what remains. Then run the referential and model rules (MC-1 to MC-14, MC-23, MC-26, MC-86 to MC-102, MC-104 to MC-110). A finding kind whose judging part was dropped with its module is not reported as missing in this mode, since the kind is idle while its module is off, and a seam whose module side holds no part is not judged (MC-108). A structural check's core-only flag does not change the model and layer supplied separately to the layer checker. For a loaded core composition, supply its projected model and layer, and run all layer checks on that scope under Namespace compositions; a retained own part still needs every applicable layer entry.

**Referential integrity.** Report duplicate element ids and duplicate relationship ids: one `duplicate-id` error for each occurrence after the first, located at the id, so an id written twice gives one error and an id written three times gives two. For each element: `system` must be a system id; `parent`, when set, an element id, and a part whose parent chain returns to itself, directly or through other parts, is one `parent-cycle` error at it (every part on the cycle gets one, and a part whose chain only leads into a cycle is not on it and gets none); `trust_zone`, when set and not null, a trust zone id; `role_class` one of producer, control, evidence, evaluation, existing, human. A relationship's `from` and `to`, each view's elements and relationships, each sequence step's `from` and `to`, and each contract's `produced_by` and `consumed_by` must resolve. Each id that does not resolve is one error at the item that holds it, so a relationship whose `from` and `to` are both unknown gives two `unknown-endpoint` errors, and a view naming two unknown ids gives two `unknown-view-ref` errors.

**Untrusted content.** Seed the exposed set with the target of every relationship whose `content` is `untrusted`, whatever its kind. Repeat to a fixed point: a relationship of kind data, inference, feedback or observation, whose source is exposed and whose `content` is not `structured`, exposes its target. Evidence, control, authorization, proposal and change relationships never propagate, because controls and independent verification sit on them.

**Non-public data.** An element holds non-public data when it, or any element on its `parent` chain, is the target of a relationship carrying `ContextSnapshot` or has `holds_nonpublic: true`. The chain runs from the element's parent to that parent's parent and on to the top, where an element has no parent or its parent names no element, and both tests apply to every element on it: a producer whose grandparent holds non-public data holds it too. Each element is visited once, so a chain that returns to an element already on it stops there.

**Lethal-trifecta routes.** For each element with role class producer, its outbound relationships are those it sends to an element in system S4 or EXT, plus any of kind inference. A route exists when the producer is exposed, holds non-public data and has at least one outbound relationship. For each route:
1. Each outbound relationship passes the gate when `optional` is not `true` (a relationship with no `optional` field is non-optional), the request-data gate has `load_bearing: true`, and the target is the request-data gate, or the target is the model-data gateway and the request-data gate's parent is the model-data gateway. Each failure is one `trifecta-ungated` error.
2. Each relationship from the producer to an element in the execution zone, or to an element of kind runner, is one `trifecta-execution` error. The producer reaches execution directly, and effects go only through authorization (system S3).
3. Each relationship of kind proposal from the producer to an element outside authorization (system S3) is one `trifecta-proposal` error.

Record every route in the `trifecta` list with `ok` false when any of these fired. After all routes, when at least one route exists and the request-data gate is not load-bearing, add one `trifecta-gate-not-load-bearing` error.

**Quarantine.** The parts that build test-drafting context are the `produced_by` list of the `ContextSnapshot` contract plus the context builder. Each such part that exists and is exposed is one `quarantine` error, naming the incoming relationships that expose it (marked untrusted, or propagating from an exposed source). Free text goes only to a quarantined, tool-less model; the context builder takes structured fields.

**AI-free control plane.** The model path for this rule is the model path list minus any element with `model_boundary: true`. For each relationship with both endpoints known, check each endpoint that sits in a control plane and is not a model-boundary gate (count each such check). The check fails when the other endpoint is on the model path or the relationship kind is inference. Each failing check is one `ai-free-control-plane` error at the relationship, so an inference relationship between two control-plane parts gives two. The route qualification registry is not on the model path: it records decisions about routes and calls no model, so a control-plane part may write to it under this rule like any other part off the path. There is no separate exemption; an inference relationship to it still fails.

**Model-boundary gates.** For each element with `model_boundary: true`: `trust_zone` must be control; `decision` must be `deterministic`; and each relationship from it to an element in a control plane that is not itself a model-boundary gate is an error. Model-derived output never reaches authorization or execution.

**Advisory model judgments.** Here the model path is the full list, gates included. A model consumer is the target, off the model path, of an inference or proposal relationship whose source is on the model path. For each relationship whose target has a `decides` value (count each): an error when it carries `TypedDecision`; and an error when its source is a model consumer, unless the kind is proposal and the target decides authorization. Then read the `TypedDecision` contract's decision types. When the contract has a `decision_types` list, use that list and ignore the description. Otherwise use the parenthesized list after `decision_type` in its description, split on `|` and trimmed. An entry matching "exploitab", ignoring case, is one error. A model may rank, route or flag; it never authorizes, counts as coverage, sets a verdict, closes a finding or attests a tier.

**Tier-zero placement.** For each `quality.yaml` element whose tier is T0 and which exists in the (possibly core-only) model, the element's trust zone must be a control plane. A part that fails closed is deployed and administered outside the zone it guards.

**Isolated drafts.** For each element with `isolated_draft: true`: each relationship from it must end at the request-data gate or at an element with role class human; no relationship to it may carry `ContextSnapshot`.

**Agent-reachable parts.** For each element with `agent_reachable: true`: an error when it is exposed to untrusted content under the propagation rule above (an edge marked untrusted ends at it, or untrusted content reaches it along a propagating edge); an error for each relationship to it that carries `OracleSpec`; an error for each relationship to it that carries `RegressionSpec`; an error (`agent-reach-verdict-ref`) for each relationship to it that carries `FailureClass`, `RoadAssurance` or `ClassTestResult`, one per contract; and an error (`agent-reach-consumer`) for each of `OracleSpec`, `RegressionSpec`, `FailureClass`, `RoadAssurance` and `ClassTestResult` whose `consumed_by` lists it. The check is by contract type: a kept regression crosses only as a `shared:DerivedCheck` (static or in-process, pass or fail with a fixed message, no expected-outcome hash and no outsider text), and a class test's result only as a `shared:ClassTestCount`, neither of which any rule here refuses.

**The inherited outsider label.** A model-free part is an element whose role class is neither producer nor human and that meets the test for its kind. A model-boundary gate (`model_boundary: true`) is model-free when its `decision` is `deterministic`, whatever relationships touch it and whether or not it is on the model path list, since a gate sits inline on the model path to check what passes and its deterministic decision is what makes it a control; a gate with any other `decision` is never model-free, wherever it sits. Any other element is model-free when it is off the model path (the full list) and is the source or target of no inference relationship. A part may clear the outsider label when its role class is human or it is model-free. For each relationship whose `content` is `structured` and whose source is exposed (count each, as `label_clearings_checked`): an error (`label-uncleared`) when it has no `cleared_by.by`; otherwise an error (`label-cleared-by-model`) when `cleared_by.by` is neither its source nor its target, or names a part that may not clear the label. The `check` text is not judged. A model-free check clears only the fields it constrains to a closed set or resolves against a store, and free text keeps the label until a person clears it; the model cannot show which fields an edge carries, so that half of the rule is the clearing part's duty, recorded at run time with each item it clears: the person, or the check and its version, the time, and the fields cleared.

**Fix briefs.** For each relationship that carries `shared:FixBrief` or `PersonWrittenBrief` (count each, as `fix_brief_edges`) and whose source exists: when it has a `verified_from` key (a relay whose receiver verifies the brief's signature; under the null rule, `verified_from: null` is no key), an error (`fix-brief-author`) unless the part it names exists, is not exposed, may clear the label (a person or a model-free part), is listed in the carried brief contract's `produced_by`, and is the source of some relationship that carries that contract; the relay's own source is then not judged. Otherwise, an error (`fix-brief-author`) when the source is exposed, or when its role class is not human and it is not model-free. A brief written by a model, even one that never read outsider text, fails. The check does not judge the signature; that the receiver verifies it, against the signer's key reference, is the receiver's duty at run time.

**Learning stores.** For each element with `learning_store: true` (count each, as `learning_stores`): an error (`learning-writer`) for each relationship to it whose source has role class producer or is on the model path (the full list); and an error (`learning-unchecked`) for each relationship from it of kind data, inference, feedback or observation, whose target is neither a person (role class human) nor an element marked `learning_store: true`, unless its `content` is `structured` and its `cleared_by.by` is the store itself. Evidence, control, authorization, proposal and change relationships from it are not checked, as in the propagation rule. A person may read learned items as free text, and a replica marked as a learning store is judged as a store of its own.

**Fix drafters.** A part drafts a fix when it is listed in the `produced_by` of the `PatchCandidate` or `FixPath` contract, exists, and its role class is not human. For each relationship to a part that drafts a fix that carries `CandidateFinding` or `FindingDisposition` (count each, as `drafter_inputs_checked`): an error (`drafter-free-text`) unless its `content` is `structured` and its `cleared_by.by` is its source or its target and names a part that may clear the label (a person or a model-free part, as defined for the inherited outsider label). This holds whatever the relationship's kind and whether or not its source is exposed: a disposition reaches a drafter on an evidence relationship, and its free text may have been written by a producer, a model or a reviewer. The `check` text is not judged. A person who drafts a fix is not checked, since a person may read free text; the person's description of the weakness is still the fix brief.

**Finding kinds (MC-91).** When the model has no `finding_kinds` key (the null rule: `finding_kinds: null` is no key), it holds no registry and nothing here runs. Otherwise count each kind (as `finding_kinds`). An error (`finding-kind-path-missing`, at `finding_kinds`) when no kind has the id `path`. An error (`finding-kind-duplicate`) for an id that appears again. An error (`finding-kind-incomplete`) when a kind lacks a non-empty string `name` or `kept_gate`, a `closure_check` with non-empty strings `check_type`, `judged_by` and `expected_outcome`, a `recovery_measure` with non-empty strings `name` and `definition`, or a non-empty `never_closes` list; one error per kind, naming what it lacks. An error (`finding-kind-judge`) when `closure_check.judged_by` names no element, or names one that is not model-free by the definition above (in full mode, using every relationship). For each kind that has a `held` key (a kind without one, `held: null` included under the null rule, is not judged here): an error (`finding-kind-held-untested`) when `held` is not a mapping with non-empty strings `kept_test`, `judged_by` and `converts_when`, naming what it lacks; otherwise the same error when `held.judged_by` names no element (in full mode only; in core-only mode a part dropped with its module is not reported), or names one that is not model-free by the definition above. A kind gets at most one `finding-kind-held-untested` error, for the first of these conditions that holds. This error is independent of the kind's `finding-kind-incomplete` and `finding-kind-judge` errors: a kind can have all three. The texts of the check, gate, measure, never-closes and held entries are not judged.

**Organization changes.** Every rule judges an item an organization's patches added or changed exactly as it judges a shipped item, with the same code and severity (MC-22); the provenance the patch applier writes (`patch`, `patch_op`, `patches`) changes no result. A finding can sit on a shipped relationship although only an organization's relationship brings it about (an organization's untrusted feed that exposes the source of a shipped structured relationship, for instance); it is still an error, located where the rule fires. A removal is judged the same way: when an organization removes the protected evidence store, with the relationships that name it, `VerifiedObservation` reaches no partitioned store and MC-104 reports `evidence-unpartitioned` at it. Which organization patch brought an error in is the upgrade's to say: it runs these checks after each patch and attributes each new error to the patch that introduced it (spec-upgrade.md, UP-18). A patch that takes a shipped item out of a rule's scope draws no error from that rule, since the rule no longer sees the item; MC-109 reports it as `judged-set-shrunk`, and the upgrade blocks it (spec-upgrade.md, UP-27).

**Injection restores (MC-90).** For each element with `applies_injection: true` (count each, as `injection_appliers`): an error (`restore-not-held`) unless some relationship to it carries `RestoreGrant` and has `optional` not `true`. That the grant arrives before the injection starts is the part's duty at run time; the model cannot show order. Its restore path starts as the element itself, whatever its zone, and grows to a fixed point: a relationship of any kind that carries `RestoreGrant`, from an element on the path to an element that exists and whose trust zone is not `control`, adds that target, followed from its source to its target only. An element in the control zone is never added, so the walk never continues through one; a relationship that carries the grant into the control zone is itself the error below. A relationship is required when its `optional` is not `true` and its `timing` is neither `async` nor `cached`. Each required relationship is judged once, against the restore paths of all appliers together, however many paths reach it (count each, as `restore_edges_checked`) when either holds:
1. It leaves a path element and carries `RestoreGrant` or has `restore_use: true` (the restore calls out along it). An error (`restore-needs-control`) when its target's trust zone is `control`.
2. Otherwise, it enters a path element, does not carry `RestoreGrant`, and carries `CredentialLease` or `KeyReference` (a credential or key the restore needs) or has `restore_use: true`. An error (`restore-needs-control`) when its source's trust zone is `control`, unless it has no `restore_use: true` and every one of those two contracts it carries is also carried by a non-optional relationship that carries `RestoreGrant` to the same element: the restore then runs under the credential issued with its grant and held in the cell, and this relationship serves the element's other work.

A relationship into a path element that carries `RestoreGrant` delivers the grant before the injection starts and is not judged. Any other relationship of a path element is not judged: the runner and the enforcement point run every effect, so a dependency the restore never uses is the part's business, and an organization marks a relationship `restore_use: true` when the restore does use it. Evidence and observation relationships that report the restore afterwards are judged only when so marked, and the execution zone, though a control plane for the AI-free rule, is where the restore runs.

**Design limits.** A part grants authority without a per-action approval when it has `grants_authority: true` or is listed in the `AutonomyGrant` contract's `produced_by` (count each such part once, as `limit_bound_parts`). For each such part that exists, an error (`limit-unbound`) unless some relationship to it has `optional` not `true`, carries `DesignLimit`, and comes from an element whose trust zone is `control`. A person sending a limit straight to the part does not bind it: the limit is read from the control zone, where it is signed and versioned. Then, for each relationship whose source exists, once for each of the two contracts it carries, `DesignLimit` (owner `people.security-risk-owner`) and `ConsequenceLine` (owner `people.risk-acceptance-owner`, the business risk owner): an error (`limit-writer`) when the source's role class is `human` and the source is not that contract's owner; or the source is not a person and its trust zone is not `control`; or the source is not a person and grants authority itself (as defined above: `grants_authority: true`, or a producer of `AutonomyGrant`). A relationship carrying both contracts from a wrong source gives two errors at the same location. The check reads contract names, element ids, role classes, trust zones and the one element field; it does not judge what the limit says.

**Ratchet's own control plane (MC-92, MC-93).** The brokers are the elements in trust zone `control` whose id is the broker's or that have `admin_broker: true`; an element marked `admin_broker: true` outside the control zone is not a broker. The administration rule runs in every edition and composition, including a model with no edition metadata or an older edition marker; changing a version marker never switches it off. When it runs and the model has no broker but has an element in trust zone `control`, one error (`admin-broker-missing`, at the broker's id), and no `admin-unbrokered` error. Otherwise, for each element in trust zone `control` that is not a broker (count each, as `admin_checked_parts`, in both cases): an error (`admin-unbrokered`) unless some relationship from a broker to it, or to an element on its `parent` chain, has kind `control`, `optional` not `true`, and carries `AdminSession`. For each element of kind `store` or `registry` (count each, as `stores_checked`): an error (`store-partition`) when it has neither a non-empty `partitioned_by` list nor a non-empty `unpartitioned` string, or has both. The check reads the keys' presence, never their values or the reason's wording, so a tool that fixes these findings never writes a reason on an organization's behalf. Both rules run in both modes, on the elements that remain.

**Store reasons (MC-95).** For each element of kind `store` or `registry` with a non-empty `unpartitioned` string and no non-empty `partitioned_by` list (a store with both is already a `store-partition` error and is not judged here), and for each relationship to it that carries at least one evidence-content contract (the seven in the table under Inputs, plus every contract with `evidence_content: true`; count each, as `reason_store_inputs`): an error (`store-reason-contradicted`) when any evidence-content contract it carries is missing from its `by_reference` list. A `by_reference` entry the relationship does not carry is ignored. The rule reads the marks, never what flows at run time; that the relationship delivers only ids and references is the receiving store's duty, checked by its own tests. A tool that fixes these findings writes neither a reason nor a `by_reference` mark: the fix is partition keys on the store, or a person's statement that the relationship carries references.

**The orchestrator (MC-96).** For each element with `orchestrator: true` (count each, as `orchestrators`): an error (`orchestrator-on-model-path`) when it is on the model path (the full list) or is a model-boundary gate; and an error (`orchestrator-model-call`) for each relationship whose `from` or `to` is the element and whose kind is `inference` or whose other end is on the model path (the full list). Relationships of any other kind to and from parts off the model path, typed decisions included, are not judged: a producer's typed record reaches the orchestrator as data, and only a model call inside the workflow is refused.

**Agent memory (MC-97).** For this rule a model caller is an element on the model path (the full list), or an element off the model path whose role class is `producer` and that is the source or target of an inference relationship or the source of a relationship to a part on the model path. An element off the model path with any other role class is never a model caller here, whatever relationships touch it; MC-101 and MC-107 define their model callers without reading the role class, and their definitions do not apply here. A context-building part is the context builder or any part in the `ContextSnapshot` contract's `produced_by`. For each element of kind `store` or `registry` without `learning_store: true` that is the target of a relationship from a model caller and the source of a relationship, of any kind, to a model caller off the model path (so an element whose role class is `producer`) or to a context-building part (count each, as `memory_stores`): an error (`memory-unflagged`) when at least one relationship to it from a model caller has a `content` other than `structured`. A write marked structured carries only fields constrained to a closed set or resolved against a store, and when its source is exposed MC-86 judges its clearing. Once the store is marked, MC-88 judges it: a producer or model-path part writing it is `learning-writer`, and what it releases passes the retrieval check.

**Human controllers (MC-98).** A human controller is an element whose role class is `human` (in any system, the organization's own roles included) and that is the source of at least one relationship of kind `control` or `authorization` (count each, as `controllers`). A contract declares a measured quantity when it has a `measures` field holding a non-empty string that names the quantity, for example a seeded catch rate with its interval and sample size; an absent, null or empty `measures` declares none. For each controller: an error (`controller-feedback-missing`) unless at least one relationship to it has kind `feedback`, `optional` not `true`, a source that is an element other than the controller itself, and a `carries` list naming at least one contract that declares a measured quantity. A relationship of any other kind carrying such a contract (an evidence relationship that delivers seeds, for instance) does not count, and neither does a feedback relationship that carries only contracts with no `measures`. The rule reads relationship kinds, the `optional` mark and the contracts' `measures` field; it never judges what the measure says or whether it arrives at run time.

**Harness parity (MC-99).** An element is a coding harness when it has a `harness` key, whatever its value (count each, as `harnesses`); under the null rule, an element with `harness: null` is no harness. An error (`harness-parity-undeclared`, at the element) when `harness` is not a map, or `stop_gate`, `version_pinning` or `blocking_hooks` is not a boolean, or `telemetry_export` is not one of `full`, `partial` and `none`: one error per harness naming every field that fails, and its stop gate is then not judged. For a harness whose `stop_gate` is false, an error (`harness-stop-gate-uncompensated`, at the element) unless `stop_gate_compensated_by` is a string naming an element that exists, has no `harness` key (`harness: null` is none, the null rule), and is the target of a relationship from the harness whose `optional` is not `true`. The rule reads telemetry export, version pinning and blocking hooks for presence only: what follows from them (changes from a harness with no telemetry count as unlabeled; the server-side run is the version of record where a harness cannot pin) is the loop's duty at run time.

**Declared assumptions (MC-100).** An element declares assumptions when it has an `assumptions` key (under the null rule, `assumptions: null` declares none). An error (`assumption-incomplete`, at the element) when the value is not a non-empty list, and nothing else in it is judged. Otherwise judge each entry, elements in model order and entries in list order (count each, as `assumptions_checked`). An entry's location is its `id` when that is a non-empty string, and `<element id>.(no id)` otherwise. An error (`assumption-incomplete`) when the entry lacks a non-empty string `id`, or an earlier entry anywhere in the model used the same id, or it lacks a non-empty string `statement` or `fallback`, or `relied_on_by` or `fallback_by` is not a non-empty list, or an entry of `relied_on_by` is neither an element id, a relationship id nor an outside reference, or an entry of `fallback_by` is neither an element id nor an outside reference (an outside reference is defined under Composition and acceptance fixture details; a model with no `composition` key has none): one error per entry naming everything it lacks, and its fallback is then not judged. Otherwise, an error (`assumption-fallback-relies`) when any element in `fallback_by`, or any element on its `parent` chain, is listed in `relied_on_by`. The rule reads the declarations, never whether the premise holds.

**Rule-first routing (MC-101).** For this rule a model caller is an element on the model path (the full list), or the source or target of any relationship of kind inference, whatever its role class. For each element with `routes_by_rule: true` (count each, as `rule_routers`): an error (`route-model-in-router`, at the element) when it is itself a model caller; and, for each relationship to it whose source is a model caller (count each, as `router_inputs_checked`), an error (`route-model-removes`, at the relationship) unless the relationship has `add_only: true`. The rule reads the mark: that the router lets an add-only input do nothing but add an item to the route toward a person is the router's duty, tested at run time.

**Typed contract fields (MC-102).** For each contract with a `fields` key (count each, as `typed_contracts`; under the null rule, a contract with `fields: null` has no typed fields), judge the list: it is a non-empty list, and each field in it, and in any nested `fields` list, has a non-empty string `name` that no earlier field of the same list used; a `type` from string, text, integer, number, boolean, date, date-time, id, hash, reference, enum, list and object; for a list, an `of` from those types other than list; for an enumeration (type enum, or a list of enum), a non-empty `values` list of non-empty strings; for an object (type object, or a list of object), a nested `fields` list judged the same way; and `required` and `untrusted`, when present, true or false (a null value is not present, the null rule). A field whose type, or whose list's item type, fails is not judged further. Any failure in a contract is one error (`contract-field-invalid`, at the contract name) naming every problem. Then, for each element with `agent_reachable: true`, each relationship to it, and each contract that relationship carries that has a field with `untrusted: true` at any depth: one error (`agent-reach-untrusted-field`, at the element). A contract with no `fields` key keeps a prose field list in its description and is not judged.

**Evidence custody (MC-104, MC-105).** A partitioned store is an element of kind `store` or `registry` with a non-empty `partitioned_by` list. For each contract that is evidence content (named in the table under Inputs, or marked `evidence_content: true`) and whose `produced_by` names at least one element that exists (count each, as `evidence_contracts`): an error (`evidence-unpartitioned`, at the contract name) unless some relationship that carries it has a partitioned store as its target. A contract with producers that no relationship carries fails too, so removing the only store a record reaches, together with the relationships into it, leaves the record with no home and the rule fires. A contract whose `produced_by` names no element that exists is not judged. Then, for each relationship of kind `evidence` whose target is an element of kind `store` or `registry` (count each, as `evidence_store_inputs`): an error (`evidence-into-store-unnamed`, at the relationship) when its `carries` list is absent or empty. A `no_contract` reason does not excuse it, since evidence into a store is never a plain information feed.

**Restricted audiences (MC-106).** A contract is restricted when its `audience` is the string `restricted`. For each relationship that carries a restricted contract (count each, as `restricted_deliveries`), and for each restricted contract it carries: an error (`audience-outside-consumers`, at the relationship) when the contract's `consumed_by` does not list the relationship's target. Also report that error when an organization's new delivery reaches a reader outside the shipped contract's restricted `consumed_by`, even when its patch lists the reader in the checked contract. With a shipped model given, a restricted contract's baseline readers are the shipped contract's `consumed_by` when the shipped model holds a contract of that name with `audience: restricted`, and otherwise the checked contract's own `consumed_by`. A delivery widens the audience when its target is not a baseline reader and either the checked `consumed_by` lists the target (a reader added to the permission list, even when a delivery to it already existed) or the shipped model has no relationship that carries the contract to that target. Each relationship and each restricted contract it carries gives one `audience-outside-consumers` finding when the checked `consumed_by` does not list the target or the delivery widens the audience, and only a finding from a widening can be excepted. So an organization's own new restricted contract delivered to a reader it does not list is a widening too. A renamed or duplicated delivery to a reader the shipped model already reached widens nothing, so it cannot except a shipped finding. Without a shipped model nothing widens. A reader newly added to a shipped restricted contract's `consumed_by` with no relationship delivering that contract to that reader gives the same finding at the contract's name, one per added reader. A relationship carrying two restricted contracts is judged for each separately.

The organization's optional `audience_exceptions` in `org.yaml` is a list. A value that is not a list, including null, gives one `audience-exception-invalid` error at `org.yaml:audience_exceptions`. Each record uses the seam exception shape: a non-empty `contracts` list of non-empty strings naming contracts the checked model holds, and non-empty strings `accepted_by`, `until` and `why`. The acceptor and end have exactly the seam exceptions' validation below, including real dates, design milestones and comparison against the run date. Each invalid record gives one `audience-exception-invalid` at `org.yaml:audience_exceptions[<index>]`, naming every problem, and covers nothing. A valid record with a date end before the run date gives one `audience-exception-expired` there and covers nothing. An end on the run date still holds; a milestone is in force here because the checks hold no milestone status. An exception may name a contract the widening did not touch, but then covers nothing.

For a finding caused by an organization's widening, the first exception in force whose `contracts` names that contract replaces only that `audience-outside-consumers` error with one `audience-widening-excepted` warning at the same location. Its message names the contract and reader, the exception's location, its acceptor and end, and says every other rule still applies. A new unlisted delivery can qualify too. Without a shipped comparison, no finding is excepted. An unchanged shipped delivery's finding is never excepted, even when an exception names its contract. An exception needs no seam crossing and covers only the audience rule: `fix-brief-author`, every agent-reach rule and seam checks retain their errors. Zero errors exits 0, including a run whose only audience findings are excepted; any remaining error exits 1. This is recorded risk acceptance, with no warning stage for any rule.

**Contract readers (MC-110).** After the core-only filter, in either mode, check each relationship and each contract name in its `carries` that the model holds. When the contract's `consumed_by` does not list the target, skip a restricted contract because MC-106 already reports the pair once. Otherwise report `contract-reader-unlisted` once per unlisted contract as an error at the relationship. Two such contracts on one relationship produce two errors at that location. Its message is `contract readers: <r.id> carries <c> to <r.to>, which its consumed_by does not list; list the receiver as a reader of the contract, or carry something the receiver is listed for`.

An organization that wants another reader lists it in the contract's `consumed_by` with its own patch; a delivery its patches add to an unlisted reader is the same error. MC-110 adds no judged set and no summary counter.

**The harness key (MC-107).** An agent-reachable model caller is an element with `agent_reachable: true` that is the source or target of a relationship of kind `inference`. For each element whose role class is not `human` and that is the source of at least one relationship of kind `control`, with `optional` not `true`, to an agent-reachable model caller (count each, as `coding_agent_controllers`): an error (`harness-key-missing`, at the element) when it has a `harness` key and a `not_harness` key, when it has neither, or when it has only `not_harness` and its value is not a string with at least one character other than whitespace. One error per element. Both keys are read under the null rule, so a part that declares a `harness` map beside `not_harness: null` has only the `harness` key. An element with only the `harness` key passes this rule whatever the key holds, and MC-99 judges its parity.

**Seams (MC-108).** The rule reads the model's `seams` list, each contract's `security` key and, when one is given, the organization's exceptions file. A `seams` key whose value is null declares no seam (the null rule); a value that is not a list is one `seam-declaration` error at `seams`.

*The floor.* A contract's floor is the set of rule codes whose tests read it, taken from the model in the mode being checked. A relationship counts only for the contracts in its own `carries`. A contract gets:

1. `MC-23` when it is `OracleSpec`, `RegressionSpec`, `FailureClass`, `RoadAssurance` or `ClassTestResult`, or when a relationship that carries it ends at an element with `agent_reachable: true`;
2. `MC-102` when it has a field with `untrusted: true` at any depth, or when it has a `fields` key and a relationship that carries it ends at an element with `agent_reachable: true`;
3. `MC-7` when a relationship that carries it carries untrusted content: its `content` is `untrusted`, or it is of kind data, inference, feedback or observation, its source is exposed (see Untrusted content) and its `content` is not `structured`;
4. `MC-86` when a relationship that carries it is in `label_clearings`;
5. `MC-98` when its `measures` is a non-empty string and a relationship that carries it is in `controller_feedback`;
6. `MC-95` and `MC-104` when it is evidence content (named in the table under Inputs, or `evidence_content: true`);
7. `MC-106` when its `audience` is `restricted`;
8. the codes of the rules that name it: `MC-4`, `MC-8`, `MC-14` and `MC-97` for `ContextSnapshot`; `MC-11` and `MC-12` for `TypedDecision`; `MC-26` for `DesignLimit`, `ConsequenceLine` and `AutonomyGrant`; `MC-87` for `shared:FixBrief` and `PersonWrittenBrief`; `MC-89` for `CandidateFinding`, `FindingDisposition`, `PatchCandidate` and `FixPath`; `MC-90` for `RestoreGrant`, `CredentialLease` and `KeyReference`; `MC-92` for `AdminSession`;
9. `MC-108` when the `never_cross` list of an entry of the model's `seams` list names it: every entry that is a mapping counts, whether or not its seam is judged (an idle seam's included) and whatever MC-108 finds wrong with the rest of its shape.

*Marks.* A person may raise a contract's mark by writing `security: { raised: { by, why } }` on it, each a non-empty string; nobody may lower one. A contract is security-relevant when its floor holds a code or it carries a raise, and a name in a relationship's `carries` that is no contract counts as security-relevant. Authored security marks hold only a raise. Released shared contracts also carry derived `floor` and `relevant` annotations; full mode verifies them against derivation. Lone modes preserve the verified full floor, read from the model alone: for a contract whose name starts with `shared:`, in a model whose `composition` is set to anything other than `full` (`ratchet`, `jig` or `core`, including a composed model that `--core` filters), a `security.floor` that is a list of strings is the reported floor and decides relevance. A malformed floor is `seam-mark-invalid` and supplies no derived relevance; it does not suppress a separate `seam-mark-lowered` when the actual derived floor is non-empty and `relevant` is false. Only a raise with nonblank `by` and `why` raises relevance; an incomplete raise reports invalid and raises no relevance. Removing a shipped valid raise also reports `seam-mark-lowered`. A floor differing from the full composition is `seam-mark-stale`. Lone modes use the full composition's verified floor annotation for the reported floor and security relevance, while deriving their own local verdicts. The composition tool copies that annotation from the shared layer's contracts onto the composed contracts, Jig alone included, so the checks never read it from `seams.yaml`. No full source tree or re-derivation from absent edges is required. After a design change, use the verified full floor report as spec-compose.md defines. A `relevant: false` beside a non-empty floor is one `seam-mark-lowered` error at the contract, which stays security-relevant. Any other problem with the key is one `seam-mark-invalid` error at the contract naming every problem: a value that is not a mapping; a key other than `raised`, `relevant` and `floor`; a raise without a `by` or a `why`; a `relevant` that is not true or false; `relevant: false` beside a raise; and `relevant: true` with no raise and an empty floor. `relevant: false` beside an empty floor and no raise agrees with the derivation and is not reported, and so does `relevant: true` beside a non-empty floor. The key is read under the null rule, so `security: null` is no key.

*Namespace seam sides.* For a `shared:` seam in a namespace composition, a part's side is the prefix before its colon, or the model's `namespace` for a bare id. Its `between` names design namespaces, for example `[ratchet, jig]`, and need not include core. Judge all retained relationships with different endpoint sides. A shared seam remains judged even in core mode; its crossing entries, `never_cross` list and exceptions are pruned as Composition inputs supplied by the composition tool states. This leaves the core shared crossings judged without the dormant exception. A module seam is idle when no local implementation belongs to that module. Resolve a crossing's `point` against any declared module's interface points. In core-only mode, check declaration references against the full input model; judge crossing sides only for relationships that remain.

*Seam declarations.* The module/core shape in this paragraph applies to module seams; shared seams use the namespace shape above. Each entry of `seams` is a mapping with a non-empty string `id` that no earlier entry used; a `between` of exactly two non-empty strings, one of them `core` and the other, a string other than `core`, the module's id (whether a module of that id is declared is MC-25's); `crossings`, a list of mappings, each with a non-empty string `id`, a `carries` list of strings and an optional non-empty string `point`, no `id` listed twice; an optional `never_cross` list of non-empty strings; and an optional `default_exceptions` list. An entry that fails any of these is one `seam-declaration` error at its id (at `seams[<n>]`, counting from 0, when it has no id string) naming every problem, and nothing else about it is judged. A seam's sides are its module, every element whose `module` is that module, and `core`, every other element. A seam whose module side holds no element in the model being judged is idle, and nothing about it is judged: core-only mode drops every module, so every module seam is idle there. For each other seam, one `seam-ref` error at its id names every crossing entry whose `id` is no relationship of the model or names a relationship whose ends do not sit on different sides, every name in an entry's `carries` that is no contract, and every name in `never_cross` that is no contract.

*Crossings.* A relationship crosses a seam when both its ends are elements and they sit on different sides. Each one is in `seam_crossings`, and counts once for each seam it crosses as `seam_crossings_checked`. The seam declares it when a crossing entry has its id and that entry's `carries` lists every contract the relationship carries (a relationship that carries no contract is declared by an entry with its id alone). An entry that names the relationship without some contract it carries does not declare it, and a contract the entry lists that the relationship does not carry is not judged. For each relationship across a seam:

1. one `seam-never-cross` error at the relationship when it carries a contract the seam lists in `never_cross`, declared or not, naming each such contract;
2. when the seam declares it, nothing more;
3. otherwise, when it carries no contract, one `seam-crossing-undeclared` error at the relationship;
4. otherwise, when a contract it carries is security-relevant, one `seam-crossing-excepted` warning at the relationship if an exception in force on the seam names every contract it carries, and one `seam-crossing-undeclared` error otherwise;
5. otherwise (every contract it carries is not security-relevant), one `seam-crossing-unlisted` warning at the relationship.

A relationship between two modules crosses both their seams and is judged on each, so it can draw one finding from each at the same location.

*Exceptions.* The organization's exceptions file is the design engine's `org.yaml`, which every design in the organization's root shares. The engine keys a design's own seam `<namespace>:<seam id>` and reads a bare key, or one written `shared:<id>`, as a seam of the shared layer. For own Ratchet module seams the checks use `ratchet:<id>`; shared seams use the shared keys below. Judge the keys as follows, whether or not the seam they name is judged:

- a key written `ratchet:<id>` that names no seam of the model is one `seam-exception-invalid` error at the key;
- a bare key that names an own module seam of the model is one `seam-exception-invalid` error at the key, since the engine would read it as a shared seam, and its list is not read;
- for own module seams, other designs' keys are not read; a shared seam instead reads its own `shared:<id>` key, falling back to its bare key, before its defaults.

The exceptions that govern an own module seam are the organization's list under `ratchet:<id>`, when the file has one (an empty list declines the ones the model ships), and otherwise the seam's `default_exceptions`. A value under `ratchet:<id>` that is not a list is one `seam-exception-invalid` error at its key when the seam is judged, and a `seam_exceptions` that is not a mapping is one at `org.yaml:seam_exceptions`. The exceptions of an idle seam are not judged.

Each exception that governs a judged seam is a mapping with a non-empty `contracts` list of strings, and non-empty strings `accepted_by` and `why`. It also carries `until`, a non-empty string or explicit null. `accepted_by` names the risk acceptor, a role or a person; the checks do not resolve it. `until` is the exception's end: a date (`YYYY-MM-DD`), or a milestone written as the design engine writes one in a design, `<namespace>:<id>` or `<namespace>:phase/<id>`. The namespace is one to 24 lowercase letters, digits and hyphens, starting with a letter, and is neither `shared` nor `org`; the id is not empty and holds no space or `/` (`jig:PH-2`, `ratchet:PH-3`). An exception has one `seam-exception-invalid` error, naming every problem, when it:

- is not a mapping;
- names no contract;
- names a contract that is no contract of the model, that the seam lists in `never_cross`, or that no relationship across the seam carries and no crossing entry of the seam lists;
- names no risk acceptor, omits its end, has a blank end or gives no reason;
- has an end written as a date that is no real date, or an end that is neither a date nor a milestone.

An explicit null end means "awaiting the organization's end date". With no organization layer, report `seam-exception-awaiting-end` as a warning with that wording and let the exception cover the contracts it names. With any organization layer present, including an empty layer and full or lone compositions, report `seam-exception-invalid` and cover nothing until the organization supplies a real calendar date in its layer. A milestone cannot resolve a shipped null end: in organization context, an exception in the organization's file, on a seam whose `default_exceptions` holds a record with a null end that names at least one of the same contracts, must end at a calendar date, and any other end there, a milestone included, is `seam-exception-invalid` and covers nothing. Organization context is established by `--org` or the compiled model's `meta.organization_version` or `meta.organization_patches` key, even when null or empty. Other malformed fields still make the exception invalid in a bare edition.

An invalid exception is not also judged for its end. A valid exception whose end is a date earlier than the date the checks run on (`--date`) has one `seam-exception-expired` error; an end on that date still holds. An exception with either error does not apply, and every other one is in force. Outside that null-end replacement, a milestone end is in force here: the checks hold no work-unit status, and the design engine judges whether a milestone is reached. No exception covers a contract the seam says never crosses, and no exception changes any other rule: a crossing it flags is still judged by every other rule.

**Judged sets (MC-94).** Build the thirty-seven sets of `judged` (see Outputs) while the rules above run, in the same mode: each holds exactly the items named in its row, using the definitions of the rule it belongs to. `exposed` holds every exposed id that names an element (a relationship to an unknown id adds nothing to it), and `cannot_clear` covers every local implementation element that is not model-free, excluding absent boundary implementations; `learning_releases` holds the relationships the retrieval check judges (from a learning store, of a propagating kind, to an element that is neither a person nor a learning store), whether or not they pass; `restore_grants` holds every non-optional relationship that carries `RestoreGrant` to an applier; `admin_sessions` holds the sessions from every broker; `admin_parts` holds the parts counted when the rule runs, including when it reports `admin-broker-missing`; `seam_crossings` holds each relationship across a judged seam once, declared or not. `held_kinds` holds a kind only when its `held` key passes the held check, so a kind whose `held` is malformed or names a judging part that is not model-free leaves the set; in core-only mode a kind whose judging part was dropped with its module is in neither the errors nor the set. A set holds every item in scope, whether the rule passes it or reports it, except `held_kinds`, which holds only what passes.

**Judged sets kept (MC-109).** Build every set of `judged` for the shipped model too, by the same rules and in the same mode: core-only mode drops the shipped model's module items as it drops the checked model's. Then, for each set and each item in the shipped model's set that the checked model's set lacks, one error (`judged-set-shrunk`, at the item) when the checked model still holds the item. Its message names the set and the rules the table under Outputs gives for it. The checked model holds an item as the upgrade reads one (spec-upgrade.md, UP-28): an element or a relationship by its id, a contract by its name, a finding kind by its id, and a field path while the model holds the contract it names, the text before its first dot. In core-only mode the checked model is the one the rules judge, with its module items dropped. An item that leaves two sets gives two errors at its location. An item the checked model no longer holds was removed by a patch, and MC-109 does not judge it; the upgrade lists it on that patch (`removed_from_judged`). What took an item out does not matter: an `unset` of a key, a key set to null, a value or a kind changed, a relationship made optional or a part recast all leave the same trace in the sets. When the checked model is the shipped model itself, nothing leaves a set. The shipped model is read like the checked one, so a shipped model that cannot be read exits 2 with no report.

**Realization coverage.** Under the composition scope above, the keys of `realization.yaml` elements equal the model's non-boundary element ids (report each missing and each unknown). Each entry's `plane` is a key of `planes`; its keys are limited to plane, class, examples, swap_point, swap_kind, existing_tool_default (a stray key usually means an unquoted comma in a flow map); `examples` is a list of zero to three; a swap point has `swap_kind` free or requalify; a non-swap point has no `swap_kind`.

**Quality coverage.** Under the composition scope above, the keys of `quality.yaml` elements equal the model's non-boundary validation parts (strip an imported `ratchet:` or `jig:` prefix before matching): ids that start with `s`, a digit and a dot, plus every organization element (id starting with `org.`) whose role class is neither `human` nor `existing`. External systems, people and the organization's own existing systems and roles are excluded. The keys of `quality.yaml` contracts equal the model's contract names, the organization's `Org` contracts included. Each element entry's tier is a key of `tiers` and its failure mode a key of `failure_modes`. A contract entry has another shape (`[kind, note]`) and is checked only for its key. An element in the control zone with role class control must have failure mode fail-closed or mark-unknown.

**Failure scenarios.** Load and resolve scenarios under Namespace compositions above. Each loaded scenario's elements resolve, and its `runbook` equals `RB-` followed by the scenario id. For an imported record the namespace precedes `RB-`, as in `jig:RB-F128`. An attached premise test whose local scenario id ends in `-premise` retains its source runbook without that suffix.

**Plane joins.** Skip relationships with an endpoint that is no element (they are `unknown-endpoint` errors) and relationships that touch an element in system `PEOPLE`, shipped or the organization's own. Map both endpoints to planes through `realization.yaml`. An element with no realization entry, or an entry with no plane, has a plane of its own, `unmapped:<id>`, distinct from every other plane and from every other unmapped element, so a relationship into it, or between two such elements, needs a contract or a `no_contract` reason like any other join (the element also fails realization coverage). Skip when both endpoints share a plane. Group by ordered plane pair. A relationship with an empty `carries` and a non-empty `no_contract` string is a plain information feed and needs no contract. A pair where no relationship carries any contract, and at least one relationship has neither a contract nor a `no_contract` reason, is one `plane-join-no-contract` error naming the relationships. In a pair that passes, each relationship with an empty `carries` and no `no_contract` reason is one `plane-join-uncovered` error. Separately, on any relationship, a `no_contract` key present with a value that is not a string, or that sits on a relationship whose `carries` is not empty, is a `plane-join-marked` error. Under the null rule, `no_contract: null`, an empty string and a string of only whitespace are no key and are not judged here, so a blank reason is no reason: the relationship counts as unmarked in its plane pair, and every name in any relationship's `carries` must be a contract name.

**Critical paths.** Every id in a path's `must_answer` and in its `co_deploy` groups is an element id or a key of `critical_paths.external`. Every `required_hops` entry `[a, b, note]` has a relationship from a to b; the note is not checked.

**Overlay coverage.** These checks run on each overlay file in the layer folder. The account classes, zone placements and services are the overlay's own; the field values `fit` and `portability` are fixed. Each overlay element key that is no model element is one `overlay-unknown` error, and its fields are not judged; each non-boundary model element missing from the overlay is one `overlay-missing` error. Boundary declarations have no overlay checks. For each non-boundary element: `services` is a non-empty list; `fit` is one of managed-open, managed, self-run, existing; `portability` is open or proprietary; `account` is a key of `account_classes`; and `account` appears in `zone_accounts` for the element's zone. The zone is `people` for an element in system `PEOPLE` (allowed: the overlay's `zone_accounts.people`, or `identity` when it has none), otherwise the element's trust zone, or `existing` when it has none. Check zone placement only when the account is a known account class and the zone is `people`, `existing` or a model trust zone: an unknown account already has its `overlay-account` error, and an unknown trust zone its `unknown-zone` error. A rule-enforcing part needs a non-empty `keeps`. A part enforces a rule when it is a named rule enforcer, has role class control, sits in the control zone, has tier T0, or has `load_bearing: true`.

**Module declarations.** `categories` and `wiring_ladder` are maps, and their keys are what is checked, in file order: the keys of `categories` must be exactly signals-in, stakes, reach, prevention-out, in that order (else one `module-category` error at `categories`), and the keys of `wiring_ladder` exactly none, connected, conformant, aligned (else one `module-declaration` error at `wiring_ladder`). The reference reads only map keys, so either field written as a list fails its check. For each module: one `module-declaration` error listing every missing item among `name`, `category`, `existing_practice` (non-empty strings), `interface_points` (a non-empty list), `switch_on` (a non-empty `evidence` list and a non-empty `test`), `rules.<key>` for each of the four rule keys, `separations` (a non-empty list whose entries each have `between` and an `enforced_by` key, which may be null) and `depends_on` (a list); a category outside the four is `module-category`; each `depends_on` entry or point `requires_module` that is not another declared module (a module naming itself included) is `module-interface-ref`, located at the module, never at the point. For each interface point retained under Namespace compositions (location `<module>.<point>`): a point missing `id`, `direction`, `crosses`, `target`, a `contracts` list or a non-empty `relationships` list is one `module-declaration` error, and its other checks are skipped; a duplicate point id, a direction other than in, out or both, a target off the ladder, an unknown relationship, a relationship that does not touch the module (neither endpoint is in it and it is not tagged with it), and an unknown contract are each `module-interface-ref`. A named contract none of the point's relationships carries, and a contract its relationships carry that the point does not name, are `module-interface-drift` warnings. Every element, relationship and contract that has a `module` key naming no declared module is `module-unknown-tag`, located at its id or name; under the null rule, `module: null` is no tag. A relationship the compiled model lists under `retired.relationships` (an organization's patch removed it) is no unknown relationship here: the point names one relationship fewer, and the patch applier has already taken it out of every seam. Then, for each entry of the model's `seams` list that is a mapping with a non-empty string `id`, whatever else MC-108 finds wrong with its shape: a `between` whose side other than `core` is no declared module is one `seam-ref` error at the seam's id (not judged for a seam whose id starts with `shared:` in a model with a `composition` key, since its `between` names design namespaces), and so is each crossing whose `point` is not `<module>.<point id>` for an interface point `modules.yaml` declares. An entry with no id string is MC-108's `seam-declaration` alone. Whether every relationship across a module's boundary is declared is MC-108's.

**Warnings.** These never change the exit status: `orphan` (an element whose `level` is anything but `container` and that is the source or target of no relationship), `unviewed` (in no view), `independence` (one owner holds producer and control, evidence or evaluation elements, when owners are present), `effect-without-control` (a producer relates directly to an execution-zone or runner element), `judgment-on-untrusted` (a producer sends a disposition contract to an evidence element), `contract-no-producer`, `contract-no-consumer`, `overlay-proprietary-swap` (a proprietary choice at a swap point), `overlay-residency` (a part that can move data across regions), `module-interface-drift` (see module declarations), `seam-crossing-unlisted`, `seam-crossing-excepted` and bare-edition `seam-exception-awaiting-end` (see seams), and `shared-owner-pending` in organization context (MC-115).

**Known limitations.** The rules key on the shipped ids in the table above. Without a `decision_types` list, the exploitability check reads prose in a contract description. Removing the gate's load-bearing mark yields one error per route plus the gate error. The restore rule follows the restore by the `RestoreGrant` contract, the two contracts named for what it needs and the `restore_use` mark: a dependency the restore uses that carries neither contract and is not marked is not reported, and a restore that runs through a part reached by some other contract is outside the path. The broker rule reads the `admin_broker` mark, never what the declared tool does. The relay rule for fix briefs reads `verified_from`, never the signature. The store-reason rule reads `by_reference` and the contract list, never the records: a contract of evidence content the organization has not marked is not judged. The orchestrator rule reads the `orchestrator` mark and the model path list: a model reached through a part off the list that is not drawn with an inference relationship is not seen. The agent-memory rule follows one hop from the store to its reader, so a store read back through a part that neither calls a model nor builds context is not judged, and a write marked structured is trusted as far as MC-86 trusts it. The controller rule reads the `measures` field and the relationship kind: a contract that declares a measure it never carries, or a person who decides through a relationship drawn as data or evidence, is not seen. The harness rule reads the declared parity and the presence of the compensating relationship, never whether that part runs the same suite. The assumption rule reads declarations, so a premise nobody declared is not seen. The routing rule sees a model only through the model path list and inference relationships, so a model reached through a part drawn without an inference relationship is not seen, and it reads the `add_only` mark, never what the router does with the input. The typed-field rule judges the declared shape, never the records that cross. The evidence-custody rule reads `partitioned_by` and the relationships' targets, never what the store keeps or whether its keys are the profile's; an evidence record drawn under a contract nobody marked as evidence content is not judged. The restricted-audience rule reads only the value `restricted`, so a misspelled value leaves a contract unrestricted, and it judges where a relationship ends, never who reads a store the contract lands in. The harness-key rule finds a coding agent only through `agent_reachable` and an inference relationship: an organization's coding agent drawn without either is not seen, and the rule reads the presence of the reason, never whether the part really runs no agent session. A producer in system EXT, such as a coding agent drawn inside the secure-creation loop, counts every relationship it sends to another EXT part as outbound under MC-4, the loop's own checks included, so the trifecta rule is stricter there than the loop's real egress. The seam rule judges names, never what crosses at run time. A contract none of its tests reads is not security-relevant until a person raises its mark, whatever it carries: an exact execution grant or a release attestation crossing a seam undeclared is listed, not refused, unless its mark is raised. A shipped raised mark cannot be removed: the patch applier and the model checks with the shipped baseline refuse its removal as `seam-mark-lowered`, even when the derived floor is empty. A seam may declare a crossing that carries no contract, by naming it alone. A milestone end is never judged here, since the checks hold no work-unit status, and a milestone that no design holds is the design engine's to find. The checks set no limit on how far away an end may be. The edition's seams are its pluggable modules' boundaries, each between a module and the rest of the design.

## Errors, warnings and exit status

Exit 0 when there are no errors, 1 otherwise, and 2 when an input cannot be read or parsed, including a layer file that lacks a required top-level entry. Each error and warning has `code`, `location` and `message`. The location is the element for element, trifecta, quarantine, boundary, tier-zero, isolated-draft, agent-reach, `limit-unbound`, `restore-not-held`, `admin-unbrokered`, `store-partition`, `orchestrator-on-model-path`, `memory-unflagged`, `controller-feedback-missing`, `harness-parity-undeclared`, `harness-stop-gate-uncompensated`, `route-model-in-router`, `agent-reach-untrusted-field`, `harness-key-missing`, realization, quality-element and overlay codes; the relationship for `unknown-endpoint`, `ai-free-control-plane`, `advisory-typed-decision`, `advisory-model-derived`, `limit-writer`, `label-uncleared`, `label-cleared-by-model`, `fix-brief-author`, `learning-writer`, `learning-unchecked`, `drafter-free-text`, `restore-needs-control`, `store-reason-contradicted`, `orchestrator-model-call`, `route-model-removes`, `evidence-into-store-unnamed`, `contract-reader-unlisted`, `unknown-contract`, `plane-join-uncovered`, `plane-join-marked` and relationship warnings; the view, the sequence step, the contract name, the scenario id or the critical path id for their codes; the request-data gate for `trifecta-gate-not-load-bearing`; `TypedDecision` for `advisory-exploitability`; the ordered plane pair (`a->b`) for `plane-join-no-contract`; the module, `categories` or `wiring_ladder` for `module-declaration` and `module-category`, `<module>.<point>` for point findings, and the tagged id for `module-unknown-tag`; the owner for `independence`; the finding kind's id for `finding-kind-duplicate`, `finding-kind-incomplete`, `finding-kind-judge` and `finding-kind-held-untested`; the assumption's location (its id, or `<element id>.(no id)`) for `assumption-incomplete` and `assumption-fallback-relies`, and the element for an `assumption-incomplete` whose `assumptions` is not a non-empty list; the contract name for `contract-field-invalid` and `evidence-unpartitioned`; the item that left its set for `judged-set-shrunk` (an element or relationship id, a contract name, a field path or a finding kind id); and `finding_kinds` for `finding-kind-path-missing`; the broker's shipped id for `admin-broker-missing`; `modules.yaml` for `modules-absent`; the relationship for `seam-crossing-undeclared`, `seam-never-cross`, `seam-crossing-unlisted` and `seam-crossing-excepted`; the contract name for `seam-mark-lowered` and `seam-mark-invalid`; the seam's id for `seam-declaration` and `seam-ref` (`seams` when the `seams` key is not a list, and `seams[<n>]` for an entry with no id string); and, for `seam-exception-invalid`, `seam-exception-expired` and `seam-exception-awaiting-end`, the exception: `<seam id>.default_exceptions[<n>]` for one the model ships, `org.yaml:seam_exceptions.<key>[<n>]` for one of the organization's, `org.yaml:seam_exceptions.<key>` for a key that names no seam, names a seam of the model bare or holds no list, and `org.yaml:seam_exceptions` when it is not a mapping, where n counts from 0. For `shared-owner-pending`, the location is the agreement: a contract by its name, a part assumption as `<holding part id>.<assumption id>` with the holding part written as the model writes it (`shared:ext.engineering-workflows.<assumption id>` for the shared engineering system, and `(no id)` in place of a missing assumption id, as for `assumption-incomplete`), and a shared claim as `shared:<claim id>` (the shared layer stores the bare id, such as `SH-1`, so its location is `shared:SH-1`). For `audience-outside-consumers` and `audience-widening-excepted`, the location is the relationship, or the contract name when an added reader has no delivery. For `audience-exception-invalid` and `audience-exception-expired`, it is `org.yaml:audience_exceptions[<n>]`, or `org.yaml:audience_exceptions` when that value is not a list. Locations are written exactly as follows: an element, relationship, view, scenario or critical path by its id; a contract by its name; a sequence step as `step <n>`; a plane pair as `<from plane>-><to plane>` with no spaces, where an element with no realization entry is the plane `unmapped:<id>`; an interface point as `<module>.<point id>`. The acceptance fixtures match findings by code and location, so a tool that keeps these two exact can run them whatever its messages say. The message is readable text that names the location.

`composition-exposure-stale` is an error at the qualified endpoint (and differing mark), `shared-writing-side` an error at the shared contract name, and `seam-mark-stale` an error at the contract name. ## Acceptance fixtures

Delete each fixture scratch folder with whatever deletion the environment allows. If the environment refuses the deletion, report the refusal and the retained path separately from fixture assertions. Preserve the fixture result and exit status based on assertions, and never count a skipped case as passed.

The fixtures ship as one file, `fixtures-model-checks.yaml`, with one entry per row below. MC-110 fixtures cover listed and unlisted readers in both modes, an organization's delivery to a reader it did or did not list, and a restricted contract an organization widens. Each entry has these fields. Optional `shipped_edits` applies model edits to both the shipped comparison and the checked model before `edits`, to plant a shipped finding. Each expected warning may include `message_includes`, a list of text its message must contain:


```yaml
- name: fixture-mc-tri-optional.yaml
  target: model.yaml          # the file the edits change unless an edit names its own target: model.yaml,
                              # quality.yaml, realization.yaml, failures.yaml, overlay-aws.yaml or modules.yaml
  mode: full                  # full runs every check; core runs core-only mode
  edits:                      # applied in order to the parsed document of their file
    - op: replace
      path: /relationships/[id=r082]/optional
      value: true
  expect:                     # every error the checks must report, by code and location; empty means pass
    - code: trifecta-ungated
      location: s2.producer-adapters
```

Nine optional fields serve fixtures that change more than one file or check more than errors. An edit may carry `target`, naming its own file, so one fixture can add an organization part to `model.yaml` and its entries to the layer files. `rename` maps an old file name to a new one and is applied first (an organization's `overlay-onprem.yaml` in place of `overlay-aws.yaml`). `absent` lists files removed before the checks run (a layer with no `modules.yaml`). `warnings` lists warnings, by code and location, that must each be reported; other warnings are not checked. `unwarned` lists warnings, by code and location, that must not be reported. `judged` maps names of sets in the report's `judged` (MC-94) to the exact list of ids each must hold, in any order; sets it does not name are not checked. `org` is the organization's exceptions file (MC-108), written as `org.yaml` beside the layer files and given with `--org`. `marks` maps contract names to the mark each must hold in the report's `marks`: its `floor`, compared as a set of codes, and, when given, `relevant`; contracts it does not name are not checked. `summary` maps keys of the report's `summary` to the exact value each must hold, a regression pin of a count such as `pending_owners`; keys it does not name are not checked. `exit: 2` marks a fixture whose input must be unreadable: its `expect` is empty, and it passes when the checks exit 2 with no report.

To build a fixture, parse the shipped files, apply `rename`, `absent` and the edits, and run the checks on the result with every other shipped file unchanged (the layer folder holds the shipped `seams.yaml` beside the other layer files, so an edit may name it as its `target`), giving the model and the folder of layer files the way an organization gives its compiled model and layer (`--model` and `--layer`), the shipped `model.yaml` as it stood before the edits as `--shipped`, and `--date 2026-12-01`, so a dated exception in a fixture never expires as the calendar moves. So a fixture whose edits take a shipped item out of a judged set also expects MC-109's `judged-set-shrunk` at that item. Edits are JSON Patch operations (add, remove, replace, as in RFC 6902) with two extensions: the per-edit `target`, and a path segment written `[key=value]`, which selects the single array item whose `key` field equals `value`, for example `/elements/[id=s4.request-data-gate]/load_bearing`. Several conditions are joined with commas, for example `/relationships/[from=s1.tool-lead-store,to=s1.context-compiler]/content`. A selector that matches no item, or more than one, is a defect in the fixture. A final `-` appends to an array. Map keys such as quality element ids are plain segments, for example `/elements/s1.context-compiler/0`.

Apart from those marked `exit: 2`, a fixture passes when the reported errors and the `expect` entries match one to one by code and location, every `warnings` entry is reported, no `unwarned` entry is reported, every set `judged` names holds exactly its listed ids, every contract `marks` names holds its listed mark, and every key `summary` names holds its listed value. Behavior fixtures' expected results are written from this specification first and then confirmed by running the reference checks; a disagreement is resolved in the specification or the checks, never by copying the run. The four composition regression pins are generated from a real reference report and reviewed set by set against the definitions above.

For each set above, `fixture-mc-pin-<set>.yaml` supplies a small independent model and an exact `judged` list derived from that set's definition. Its YAML comment explains the included ids and the exclusions. These fixtures use RFC 6902's empty pointer (`path: ""`) to replace a whole document. `shipped_edits` replaces the baseline model before both the comparison and the checked model are built; `edits` supplies the matching small layer documents. Thus these pins do not depend on the shipped graph or its counts. The composition pins provide the separate regression check on the real graph, in all four compositions.

### The full composition reads the frozen pin

For MC-111, read Jig's files from the release tag named by the pin. Verify the hash of its edition record, its namespace, released flag and version, every frozen file's hash, and the manifest digest. Sort manifest entries by path in code-unit order, then hash the concatenation `<sha256>  <path>\n` with two spaces and a final newline for every entry; do not sort the hash-prefixed lines. Require the frozen shared layer to equal the shared bytes Ratchet builds. Read Jig's model, layers, units, phases and premises from that frozen record; do not substitute the working Jig tree. Descriptive tables absent from the edition folder are read from the same frozen tag. Reject a missing pin as `pinned-composition-unavailable`, a changed hash as `pinned-composition-hash`, an invalid edition as `pinned-composition-edition`, an invalid file list or digest as `pinned-composition-manifest`, and a different shared layer as `pinned-composition-shared`. A draft reports an unavailable released pin as blocked, never passed.

**The pin command.** `pin --edition <folder> [--jig <folder> | --snapshot <folder>] [--out <dir>]`. The recorded pin is the entry with `namespace: jig` in the `pins` list of `<edition>/edition.yaml`, with `tag`, `version` and `sha256`; no entry is `pinned-composition-unavailable`. The Jig release is the flat folder `<edition>/pins/jig/` unless `--jig` names another; `--snapshot <folder>` instead reads a release layout whose files sit under `export/jig-skill/` in that folder, and giving both options cannot be read. The command reads the shipped Ratchet documents from the edition folder (`model.yaml`, `seams.yaml`, `units.yaml`, the layer files, `modules.yaml` and `threat-closures.yaml`), verifies the release as above, and composes the full model with the frozen Jig. On success it exits 0 and prints one JSON object, `{ ok: true, pin, model, quality }`, where `model` is the composed full model and `quality` its composed `quality.yaml`. With `--out` it also writes the composed `model.yaml`, `realization.yaml`, `quality.yaml`, `failures.yaml`, `overlay-aws.yaml`, `modules.yaml`, `units.yaml`, `seams.yaml` and `threat-closures.yaml` into that folder, plus a copy of the edition's `rules.yaml` when present. Any refusal or unreadable input exits 2 and prints `{ error: <message> }` on standard error. A pin refusal's message begins with its `pinned-composition-*` code; a file that cannot be read or parsed gives the reader's own message, with no code.

The fixtures file's `pin_case` reads `frozen_pin` in `fixtures-model-inputs.yaml`: `pin` is the recorded pin, `files` maps paths relative to `pins/jig/` to exact UTF-8 file-content strings, and `shared_bytes` is the exact shared document to compare. Materialize those strings unchanged; do not construct a model, record, manifest or hash. The valid case requires the element name `Pinned check suite` and the quality note `Pinned contract quality` supplied by those bytes. `valid` requires the supplied frozen element name and quality note; `missing` omits the recorded pin, `hash` replaces its sha256 with 64 zeroes, `file` replaces only the frozen model bytes with `elements: []` followed by a newline, and `shared` supplies the string `different` as the current shared bytes. Leave every other byte and recorded hash unchanged. Each `error_code` names the required refusal. The runner writes the supplied full composition documents, `shared_bytes` as `seams.yaml` (with a newline appended in the `shared` case, so those bytes differ from the frozen ones) and an `edition.yaml` whose `pins` holds the recorded pin (empty for `missing`) into an edition folder, writes the `files` strings under `export/jig-skill/` of a snapshot folder, and runs `pin --edition <edition folder> --snapshot <snapshot folder>`. A valid case passes when the reported `model` names the element `jig:check-suite` `Pinned check suite` and the last item of the reported `quality.contracts` entry for `jig:` followed by the `quality_contract` name is `Pinned contract quality`; a refusal case passes on exit 2 with its code in the message.

## Composition inputs supplied by the composition tool

Use `spec-compose.md` to produce the four organization compositions and the complete layer folders. A checker consumes these projected documents. The layer folder includes `seams.yaml` and `units.yaml`. Jig alone uses the vocabulary merged from its shared layer and the shared contracts' full floor annotations. In full mode compare an annotation with the current full derivation. In lone modes use a valid shared floor annotation as the reported floor and for relevance. Malformed annotations remain errors and do not hide local findings.

Core exception pruning has two steps. First, when `--core` filters a model that has a `composition` key, each seam whose id starts with `shared:` keeps only the crossing entries whose relationship remains, `never_cross` keeps only contracts the filtered model holds, and each `default_exceptions` record keeps only contracts carried on its retained crossing entries; a default record left with no contract is dropped. A supplied core composition arrives already pruned this way. Second, in core mode (`--core`, or a model whose `composition` is `core`), the exception list that governs each judged seam, the organization's or the defaults, loses the pruned contract names: the names in `composition_omitted.contracts` when the supplied model's `composition` is `core`, plus, under `--core`, every contract with a `module` key. A record that is a mapping with a non-empty `contracts` list and loses every name is dropped. Any other record, one whose list started empty included, is kept and judged under the existing validity and expiry rules. Unknown contract names still fail. The organization's input file stays unchanged and is passed to all four runs.

Composition fixture controls also accept `marks`, a mapping of contract identity to the exact expected `{floor, relevant}` report, `floor_annotations`, a mapping of contract identity to the security annotation attached to that contract before checking, `core`, which requests the ordinary core-only switch, and `untrusted_field`, which marks the first field of shared:DerivedCheck untrusted before checking. The latter requires MC-102 to refuse a delivery even when its endpoint exposure declaration is complete. A fixture with a supplied nonempty full floor whose triggering edges are absent locally must preserve that floor in its marks report. Re-deriving an empty floor cannot pass it.

## Composition and acceptance fixture details

The composer validates available implementations before projection under CO-5. When the model checker receives an already lone projection, it uses the absent side's declaration through the boundary parts the loader created, and runs no exposure refusal of its own; the loader has already judged the declarations, and the checker cannot compare them with an implementation it did not load. A loader declaration refusal occurs before result files. The fixture runner accepts a nonzero exit with the refusal code in a JSON errors list. CLI input failures with exit 2 have empty standard output.

An outside reference is an id that a model with a `composition` key lists in its `outside_references` list and that carries a namespace prefix (the text before its first colon) other than the model's `namespace`; the loader writes that list from the shared layer's declarations. A contract's `produced_by` and `consumed_by` entries resolve to an element of the model as checked, boundaries included, or to an outside reference. A name in a seam's `never_cross` resolves to a contract of the model or an outside reference. A name in a crossing entry's `carries` resolves only to a contract of the model. Unknown identities still fail. A namespace seam assigns sides by the complete prefix, including shared. `unlist_crossing` removes a model seam entry. An omitted module's boundary exemption reads the model's shared seam crossing entry under MC-25, and a `composition` fixture never runs that check.

Boundary parts stay out of implementation-only sets: cannot_clear, stores, controllers, harnesses and assumption holders. A boundary may enter exposed and relationship sets. Its declared model freedom governs local feed checks, with producer and human roles never model-free. People also stay out of cannot_clear. The exposure seed includes every boundary declared exposed.

For a newly listed contract reader, an existing delivery widens the audience when the shipped consumed_by list did not name that reader. Other seams retain the existing milestone-end rule.

In lone modes a valid model contract `security.floor` annotation supplies the verified full floor; the layer folder's `seams.yaml` is not read for it. Local edges still receive their own checks. Full mode derives the floor and flags a differing annotation as seam-mark-stale. Failure scenario elements may resolve through outside and the known omitted inventory.
