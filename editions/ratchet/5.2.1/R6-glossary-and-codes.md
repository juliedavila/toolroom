# Reference R6: Glossary and codes

*Ratchet: closed-loop security validation for AI-assisted engineering. Reference R6. Edition 5.2.1, Thesis 1.4.3, 2026-10-31, build 2b8e8a14+local.*

<a id="r6-terms"></a>
## Terms

- **authorization service** (also: external authorization service, action control service, exact-action authorization): The service outside every agent that turns a proposed action into either a denial or a short-lived grant for that exact action. It checks the target, identity, action, environment, time window and approval immediately before anything runs, and stops on any gap.
- **policy decision point** (also: PDP): The part of the authorization service that decides. It reads current facts, the required human approval, the data and environment scope and the exact effect allowed, and answers allow or deny for one action.
- **identity** (also: test identity, scoped identity): The account an action runs as. Every run gets a scoped, short-lived test identity whose permissions cover only the granted action on the granted target; its secrets go to the runner and never to an agent.
- **action** (also: action spec, ActionSpec): One exact operation a test wants to perform: which primitive, against which target, with which parameters. Agents write actions as typed proposals; only a grant lets one run.
- **time window** (also: grant expiry): The period during which a grant is valid. Outside it the grant is refused, so an approval given last week cannot authorize a run today.
- **scenario owner** (also: scenario owners): The person who owns one scenario: chooses it, by hand, from a lead or from the organization's existing discovery practice; names who owns its scope, fix and acceptance; and writes and signs its proof condition. Sometimes in security, sometimes the service or business owner, never the team that drafts the scenario's tests.
- **proof condition** (also: proof conditions, answer key): What the running system must show for a weakness to count as real, and what would show it is not, including what must still work for legitimate users. The scenario owner writes it, often from a language model's draft, and the agent that proposes and runs the test never sees it. Proof conditions are kept with the protected fixtures.
- **protected fixtures** (also: fixture and oracle registry, oracle, proof conditions, expected answers, protected oracle): The known test setups and their expected outcomes, owned by someone independent of the agents and kept out of every agent's reach. A finding counts only when an independent verifier reproduces it against these.
- **context assembly** (also: context compiler, scoped context compiler): Building the task-sized view of trusted facts an agent may read: access policy applied before joins, sources and freshness declared, and anything missing or unknown stated as such.
- **context service** (also: trusted context, context and intent service): The system that holds observed facts about the estate (owners, identities, boundaries, sources) separately from intended behavior, and hands out versioned context snapshots.
- **telemetry integrations** (also: enterprise adapters, CI/CD and telemetry integrations): The connectors to the organization's existing tracker, CI/CD, IAM, change management and SIEM. They carry accepted regressions into each owning pipeline and bring delivery and detection data back.
- **regression promotion** (also: advisory to blocking, promoted to rejecting): Turning a confirmed reproduction into a versioned regression test in the owning service's pipeline: it starts advisory and becomes blocking after a run of clean passes, so a reintroduced defect is rejected.
- **walking skeleton**: The thinnest version of the whole loop that works end to end: one seeded path through all eleven activities, done by hand wherever possible, on tools the organization already has. It proves the loop can close and times every handoff.
- **claim** (also: claims): One of the graded statements the design rests on (CL-01 onward), each with its evidence, strength, what would prove it wrong, and the work units that measure it.
- **phase** (also: phases): A stretch of the work that ends when the evidence lets the organization say something new, such as "the evidence can be trusted", decided by a test written in advance. There are five; working records code them PH-1 to PH-5, so PH-1 is phase 1. Phases are planned in weeks, and each reports green (on course), yellow (behind by days or a week, or an early warning moving) or red (a stop condition has fired). Releases run on their own rhythm: units ship continuously within and between phases.
- **unit** (also: work unit, units): One step up the fidelity ladder at one activity (for example, manual stand-in to existing tool) that keeps the loop closing and carries a check that runs. Units declare what they provide and what they need, so a team takes whichever ones are ready.
- **seam** (also: backbone activity): One of the eleven steps of the validation loop (STEP-1 to STEP-11) plus STEP-12, hardening the road. Each is defined by the contract that crosses it, so its implementation can change while its neighbours stay the same.
- **frontier** (also: pullable, pulled at once, ready to start): The units whose prerequisites have all landed, so any team can start them now. The reference plan counts how many become ready once the walking skeleton works, then how many open in each following wave.
- **fidelity ladder** (also: fidelity rung): The steps a part of the loop climbs: none, a manual stand-in, the organization's existing tool, then a built component. Every unit moves one part up one rung.
- **stand-in** (also: stand-ins): A temporary manual or borrowed version of a component, such as a spreadsheet for the cost ledger or a tracker ticket for the run record. It can be swapped out cheaply only if it already produces the shape the real component's contract requires.
- **self-contained**: Said of the walking skeleton: none of its units needs anything from a later claim, so it can be finished first on its own.
- **crown jewel** (also: crown jewels, crown-jewel): The highest consequence tier for an asset, set by its business owner after the testing team drafts it from existing business-impact and data-classification material. Gates that protect a path to a crown jewel block deploys by default when they are down.
- **consequence tier** (also: tier (consequence), consequence register): Each asset's attested importance: crown-jewel, critical or standard, with an optional impact score. The tier, plus a demonstrated path, decides what a gate does when it fails.
- **posture** (also: gate posture, gate failure posture, fail closed, fail open): What a gate does when it is unavailable: hold the deploy (fail closed) or let it through and record it (fail open). It is set when the finding is accepted, from the consequence tier the demonstrated path reaches.
- **ship-through** (also: ship through): Deploying past a gate that would otherwise hold, under an attributed, expiring acceptance by the business risk owner with security concurrence. A replay runs automatically once the gate recovers.
- **cadence ladder**: How often a regression replays: with the periodic assessment cycle, on a schedule under a batch approval, or continuously under a standing permission. A test steps up only through a trust gate and steps down automatically.
- **trust gate**: The evidence a test needs before it moves up the cadence ladder: clean runs, no false failures, no out-of-scope attempt, no harmful run and a stable target.
- **design limit** (also: design limits, agent limit): The cap the design sets on what one agent route or one kind of judgment may touch without a person approving each action: the highest consequence tier, the environments and the action classes, set by the security risk owner. Standing permissions, earned-autonomy grants and dials all sit inside it, and the record never widens it; widening one is a recorded change by the role that owns it.
- **consequence line**: The consequence tier at or above which a person approves every action, whatever any design limit says. The business risk owner sets it.
- **dial register** (also: dial, dials): One versioned record of every setting Ratchet can turn (cadence step, posture thresholds, sample rates, reviewer limits), each with a floor, who may turn it and the evidence for the last change. Going below a floor is a recorded risk acceptance.
- **independent verifier** (also: verifier): The person or service, separate from whoever proposed the test, that reproduces a finding against the protected fixtures before it can be accepted.
- **disposition** (also: dispositions): The recorded decision on a finding: confirmed, rejected, unresolved or held, with who decided, the evidence and an expiry. A model's negative judgment never counts as coverage. A failed reproduction leaves a finding unresolved and never refutes it, because a reproduction can fail on a condition the report left out; the record keeps that reason.
- **closure** (also: path broken, constraint enforced): Proof that a fix works in the deployed system: two human acceptances (review and retest) by different people plus a machine record naming the deployed artifact, labeled with its environment. "Path broken" means the demonstrated path is denied; "constraint enforced" means varied paths are denied too.
- **false closure**: A finding recorded as closed while the weakness is still exploitable. It is the loss closure records, retests in the deployed system and kept tests exist to prevent, and a threat model can produce it too: a candidate threat marked handled because a contract states a guarantee the running code does not honor.
- **self-graded evidence**: A phase gate, or any other go or stop decision, made on numbers the system under evaluation produces. It is why phase exits are judged against criteria written beforehand by people outside the team that runs the agents, and why the evaluation group, independent of the team that generated a threat model, grades it.
- **canary** (also: seeded canary): The walking skeleton's seeded scenario, run against the live loop on a schedule. Each run either closes or names the first activity that failed, so Ratchet tests itself the way it tests services.
- **no-agent arm** (also: scripted comparator, no-LLM baseline): A scripted run with no model in it, done beside the agent on every seeded case from the start. It is the honest baseline for whether the agent is worth its cost, and the bottom working rung of the degradation ladder.
- **producer** (also: producers): Anything that proposes tests or findings: an agent, a scanner, a human tester. Producers only propose; their proposals carry no authority.
- **model gateway** (also: AI gateway, model/data gateway): The single path between producers and any model. It checks which models a task may use, limits what data leaves, records usage, and returns model output marked untrusted.
- **request-data gate**: The part of the model gateway that minimizes and classifies what a request sends and blocks unauthorized export. It is load-bearing: for producers that read untrusted text, it is what stands between that text and data leaving.
- **lethal trifecta**: Simon Willison's name for an agent that has private data, untrusted content and a way to send data out, all at once. Prompt injection cannot be reliably prevented, so the design forbids the combination unless effects need exact approval and outbound requests pass the request-data gate. Phase 1 comes before that gate, so it keeps two of the three out: the independent reviewer confirms a team-written target, no outsider text and a synthetic context.
- **exception** (also: exceptions): The recorded, expiring decision to break one should-never rule. It names the rule, the reason, the compensating controls and the roles that discussed the trade-off card. The business risk owner accepts and the security risk owner concurs; before they are named, a phase 1 only exception is accepted by Ratchet decision owner with the independent reviewer concurring. Without one, the checker refuses the profile.
- **lead** (also: tool lead, tool leads): Output from an existing security tool (scanner alert, bug bounty report, pentest note) stored as a labeled hypothesis. Leads help agents choose what to test; they never count as facts, coverage or decisions.
- **quarantine** (also: quarantined lead reader): Reading attacker-writable text only with a separate model that has no tools and no data access, and passing on just its validated, structured summary.
- **degradation ladder**: The order Ratchet falls back through when model access fails: frontier route, self-hosted open-weight route, the no-agent arm, then manual. The authorization and evidence systems use no model at any rung.
- **failover drill**: A scheduled run of the seeded cases on the self-hosted fallback route, so the fallback is qualified before it is needed. A route past its drill interval counts as unavailable.
- **promotion** (also: promotion review, promotion authority): The accountable decision that lets a new model, route or producer configuration into use. Evaluation recommends; someone outside evaluation decides.
- **paved road** (also: paved-road catalog, paved roads): The shared platform engineers build on: portal templates, base images, libraries, gateway policies and secure defaults. Each road entry declares which failure classes it reduces and is itself vetted and tested.
- **covered-by-road** (also: covered by road): A label on a code location that provably uses a vetted road entry (checked at each call site). Scanner rules for the classes that entry handles are downgraded there, and a sample of covered code is still tested.
- **failure class** (also: failure classes): A group of accepted findings that share a cause, such as the same mistake across services or the same weakness in a shared component. A class exists only when reproduced findings sit under it.
- **value ledger**: For each business unit, what Ratchet cost it, what risk went down on its assets and what friction went away, so the people who pay can see the return.
- **swap point** (also: swap points): A place where the design expects to substitute one product for another behind a stable contract, such as the model gateway or the message broker.
- **existing tool first**: An element the organization's current tool usually serves before anything is built, such as the tracker standing in for the findings ledger.
- **profile** (also: organization profile): The blanks an organization fills in (existing tools, jurisdictions, cadence, ownership, crown jewels, model eligibility, risk appetite). Model plus profile gives the fitted architecture and the work list; the profile checker refuses choices that break the four rules.
- **core and modules** (also: core loop, core platform, pluggable module, optional module, modules): The core platform every adopter needs (the loop, its four rules and the record), plus five pluggable modules that an organization switches on only when its entry evidence exists: existing security tools as leads (signals in), consequence-informed gates (stakes), production effects (reach), and the paved road and secure creation (prevention out). Most organizations already run some version of several modules; a module mainly wires that practice in, and is built only where nothing exists.
- **wiring ladder** (also: connected, conformant, aligned, interface point): How far a module's interface point is wired, lowest first: none (nothing crosses), connected (data crosses through whatever the existing system allows), conformant (what crosses matches the module's contract) and aligned (the practice keeps the four rules and the module's separations, or carries a recorded exception). Each point declares its target; the organization records where it stands today.
- **trust zone** (also: trust zones): A boundary inside the architecture (reasoning, control, execution, evidence, evaluation) that limits what each part can see and change, so a compromised agent cannot reach controls or evidence.
- **four rules**: The rules every choice must keep: a proposal is never permission; proof conditions stay out of the testing agent's reach; findings enter the record only after validation and an independent reproduction; acceptance is independent.
- **exposed secret** (also: exposed secrets, time to revoke, revocation check): A live credential found in code, history, logs or tickets, recorded as a finding of its own kind. Deleting the string never fixes it while the credential still works: the owning team revokes and rotates it, a check with no model proves the revocation by the credential type's recipe (the issuer's status by identifier first, else an announced probe repeated over the issuer's propagation time), the detection side reviews its use while exposed, and a kept scan rule blocks its return. Time to revoke runs from detection to the credential failing.
- **finding kind** (also: finding kinds, finding-kind registry, kind of finding): What a finding is, which decides how it closes. The model holds a registry of kinds; each declares the check that closes it, which part judges that check with no model, the gate that keeps it closed, its recovery measure, and what never closes it. The edition ships path, exposed secret and infrastructure misconfiguration; an organization adds its own by patch.
- **infrastructure misconfiguration** (also: infrastructure misconfigurations, time to conform): Live infrastructure configuration that differs from its declared intent, the worked example of a finding kind for infrastructure flaws. It closes only on a read of the live configuration, with no model, that matches the intent; a closed ticket or a code change alone never closes it. Time to conform runs from detection to the first matching read.
- **fix brief** (also: fix briefs, FixBrief): The description of a weakness that a fixing agent or the owning team receives with a confirmed finding. A person writes it, or a rule derives it from the proof condition and the model-free reproduction alone, so it carries no outsider text and no expected outcome.
- **learning store** (also: what the loop learns): Where the loop keeps what it learns from its own confirmed validations. No agent and no part that calls a model writes to it, and every item it hands back is checked again for its outsider label and how that label was cleared.
- **quality debt**: Quality debt: the verified, unfixed shortfalls against the claims a team makes for every quality it answers for (security, reliability, functionality, usability, performance, operability), all paid from one engineering pool. Security debt is the security share; technical debt, in its usual sense of internal code and design quality, is another.
- **debt-service capacity**: Debt-service capacity: the engineering time an owning team has for paying down quality debt of every kind. The team's fix cap is security's agreed share of it: the number of open validated findings the team takes on at once.
- **asymmetric suspicion**: The principle stated beside the four rules: every human gate the rules name (the approver, the proof-condition holder and the decider) is measured with seeded known-bad items the way the agents are checked, because people at the gates drift toward approving. It is a duty to keep measuring, so it adds no fifth rule; a profile check verifies each gate's seeding setup, and the catch rates show whether people stay attentive.
- **exploitable**: Said of a weakness the running system has demonstrated: a test met a written proof condition in the deployed system with its actual controls in place, and a reproduction by someone other than the proposer met the same condition. Its consequence is what the reproduced path reached, at the tier the business owner confirmed for that asset. Two kinds count without a demonstrated path, and only these two: a live exposed secret, while the credential still works, and a live infrastructure misconfiguration, while it still differs from its declared intent. A weakness whose reproduction a control stopped short of the proof condition is a held finding instead.
- **urgency**: How soon an exploitable weakness needs fixing, read only from attacker-side signals on a closed list that each edition versions. This edition's list: a known-exploited listing, an exploit prediction score (EPSS), presence in an exploit kit, and a public proof of concept. A severity score or a model's opinion never sets urgency.
- **held finding** (also: held findings, held weakness, held dependency, held-dependency test): A weakness whose independent reproduction a control stopped short of the proof condition, where the reproduction's receipt shows the control refusing the step. The record names the weakness, the control and the path, and a kept test, owned by the team that owns the control, runs that path against the control on a re-test interval. A held finding is neither exploitable nor closed. When the kept test shows the control no longer stops the path, the finding becomes exploitable at once, with the reach that run showed and the tier already confirmed, and no new triage. A held finding whose test is missing, unowned or past its interval reads as unresolved.
- **paper-slice credit**: Crediting a control that no test observed (a gateway, a firewall rule or sign-in protection named in a ticket, a diagram or a model's reasoning) as the reason a weakness cannot be exploited or may close. Ratchet counts a control only where a reproduction observed it stopping the path, and records the weakness as a held finding with a kept test that exercises the control, so the credit becomes a check that can fail.

<a id="r6-the-four-rules-and-the-three"></a>
## The four rules and the three phase 1 roles

1. A proposal is never permission.
2. Proof conditions stay out of the testing agent's reach.
3. Findings enter the record only after validation and an independent reproduction.
4. Acceptance is independent.

Phase 1 runs with three roles: the test operator, the service owner and an independent reviewer.

## Codes

| Pattern | Meaning |
|---|---|
| `PH-[1-5]` | Phases: points where the evidence lets Ratchet say something new. PH-1 the loop closes once; PH-2 the evidence can be trusted; PH-3 it is measured against today's process and a no-agent baseline; PH-4 a second team runs it; PH-5 it works in production. |
| `STEP-(?:1[0-2]\|[1-9])` | Steps of the validation loop (seams), from choosing a scenario (STEP-1) to learning and expanding (STEP-11), plus hardening the road (STEP-12). |
| `RULE-[1-4]` | The four rules, in order: a proposal is never permission; proof conditions stay out of the testing agent's reach; findings enter the record only after validation and an independent reproduction; acceptance is independent. |
| `APX-[1-6](?:\.\d)?` | Sections of the six-pager's appendix on diagrams and system design: the loop, the five phases with table APX-2.1, the control boundary, the planes, what an outage means for the teams that ship, and losing a model provider. |
| `U-\d{2,3}` | Work units: one step up the fidelity ladder at one activity, with a check that runs. |
| `S[1-7]` | The seven logical systems: S1 trusted context, S2 durable workflow and producers, S3 exact-action authorization and execution, S4 model gateway, S5 protected proof and evidence, S6 deployed closure and regression, S7 qualification, economics and operations. |
| `F\d{2}` | Failure scenarios: what breaks, what must happen, which rule it protects and the test that proves it. |
| `T[0-3]` | Quality tiers: T0 control safety (fails closed), T1 evidence integrity, T2 orchestration, T3 best effort. Targets are defaults a profile overrides. |
| `I(?:[1-9]\|1[01])` | Invariants: the rules a failure scenario protects, starting with I1 a proposal is never permission. |
| `CL-\d{2}` | Claims-ledger entries from the diligence pass: each statement Ratchet rests on, with evidence, strength, falsifier and verdict. |
