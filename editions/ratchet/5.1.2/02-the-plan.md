# Each phase ends on evidence before the next widens the loop

*Ratchet: closed-loop security validation for AI-assisted engineering. Part 2 of 4. Edition 5.1.2, Thesis 1.4.2, 2026-10-30, build 13fabeae+local.*

Part 1, *The strategy, carried forward from the brief and the six-pager*, says what Ratchet is and defines its terms: the loop, the four rules and their exceptions, escapes, phases, the consequence line and the design model. This part says how the work gets there: small units shipped continuously, five phases with tests written in advance, the alternatives weighed at each major choice, and the risks with the measures that show them early.

## Work ships in small units, and five phases mark what the evidence lets Ratchet say

The work is cut into 318 **work units**. A unit moves one step of the loop up one level, from a person doing it by hand (a manual stand-in) to an existing tool to a built part, and the loop keeps working throughout. Of the 318, 194 are code, 53 are agreements between teams and 71 are measurements; 134 give feedback within minutes through a check that runs in the pipeline.

Each unit is tagged as feature, defect, risk or debt, so the status report can show how much work reduces risk. Reference R4 gives the classification rule. An organization can reclassify a unit by recording a **design change**, a change to its own copy of the design model (part 3).

A unit can also say which kind of **manual work** it removes or reduces, chosen from a fixed list of kinds that the editions ship with no shares or numbers attached. Each such mark names the assumption (premise) it rests on and is graded the way premises are graded, never above that premise. The tool that checks the unit plan refuses a mark that names no kind from the list, rests on no premise or on a dropped one, or is graded above its premise.

Units ship on the organization's own release rhythm, continuously or in batches. A phase is complete when its units have landed and its test passes. Phases mark evidence; they are separate from releases. Jig's units belong to Jig and sit in Jig's five stages. Ratchet's phases and Jig's stages are ordered separately. When a Jig stage waits on a Ratchet phase, that wait is reported on its own, and the edition's automated checks confirm that no chain of waits loops back on itself.

### Phase 1 runs on existing tools, and phase 2 builds the first shared controls

Before phase 1 starts, the organization names the roles, fills in the first profile sections and sets its review date. Setup and loop effort are estimates based on the chosen weakness and existing tools. Phase 1 is a feasibility test: it proves the loop can close, and whether the loop works at scale is for later phases to show. Phase 1 uses the organization's tracker, pipeline, identity system and change approval. Three roles carry it: the test operator, the service owner and an independent reviewer. Before it starts, the organization maps how its loop works today, in the profile's current-practice section: most already run discovery, often senior red teamers or security engineers pointing agents at repositories or infrastructure, and the map shows where each step starts. 

The edition's **ratchet-tools** bundle checks and tailors the design. It needs Bun and no npm packages. It does not replace the operational tools that run the security loop. Every bundled tool must pass the edition's test cases before release. Part 4 explains the bundle and its specifications.

Phase 1 tests one weakness, and where it comes from is the organization's choice: a seeded path to a practice target the team wrote, a finding from its existing discovery practice, or a recent finding. With a practice target, the agent sees a synthetic context and no text written by outsiders. A real finding cannot keep real data and outsider text away from the agent, so with one the agent only drafts: it holds no tools, its only way out is the approved model route, and people run every approved action. The independent reviewer confirms this boundary, what the agent can and cannot reach in phase 1, before phase 1 starts, because the control that checks what agents send out arrives only in phase 2. 

What limits the runner in phase 1 depends on the organization's maturity. A scoped cloud role is the common stand-in, and an organization that already has a mechanism bound to the exact approved action uses that instead. The profile records which; with a scoped role the profile checker in ratchet-tools reports the gap, because the role is neither tied to the approved action nor used up when it is used, and phase 2's authorization service replaces it.

Its most useful output is the record of every handoff and how long each one waited, because those waits show where the real constraint sits. No later phase can claim a lower escape rate or a shorter time to remediate without a measured starting point. Phase 1 handles one weakness, which cannot set an escape rate, so the escape rate's starting point comes from the historical findings and incidents gathered in the current-practice map. The people who keep the map gather them during phase 1, so the starting point exists before phase 2 begins.

A scripted test with no agent runs each case beside the agent. Before phase 1, the decision owner names a scorer who is not the test operator. The success criteria say what the comparison measures and how it is scored. The scorer records a verdict for each case. A verdict against the agent does not fail phase 1.

Phase 2 starts only when the decision owner accepts the phase 1 report, judged against criteria written before phase 1 began. Those criteria name the three checks phase 1 must pass (the loop closed, an independent reviewer verified the fix, and the regression test held), the scorer who gives each case its verdict of the agent against the scripted test, and the scale and dimension of that verdict. Phase 1 passes when the three checks hold and the map, the scripted test's results and the per-case verdicts exist. The criteria also include an estimate of effort, the organization-set review date, the expected wait at each handoff, and each phase 1 role's written account of every step done differently from the plan. The report also carries the build estimates for phase 2. 

Phase 1 closes too few cases to set numeric thresholds, so the decision owner sets them from the phase 1 map before phase 2 starts: the thresholds that stop the work and those that grant each step of trust. Phase 2 then builds what phase 1 showed it needs: an authorization service that binds approval to the exact action, a durable record of each run, separate consoles for approvers and reviewers, and the regression test promoted from advisory to blocking after a run of clean passes.

### Phase 2 defines what counts as an escape

Phase 2 needs the organization's operational definition of an escape, recorded in the profile's `escapes` section: where escapes are detected and by which role, the window after a deployment within which an escape counts toward that deployment, and the role that confirms each escape, which must differ from whoever detected it, from the team that runs the agents (the producer team) and from the decision owner. It may also set how long an escape can stay unconfirmed before the security risk owner is alerted, because an unconfirmed escape counts nowhere. 

Each escape record names who traced it to a deployment and how. An escape that no deployment shipped, such as configuration drift, a newly disclosed weakness in a dependency that did not change, or a change made outside the pipeline, goes in a bucket of its own, reported apart. The authors expect most escapes found through bug bounty to arrive after the window and count as late, so the report shows the escape rate both without late escapes and with them included. 

From phase 2 on, the report shows each count of escapes with its consequences beside it: the consequence tiers of the assets reached and the services affected, the time to recover, and how many fixes removed the weakness class against one instance.

### Attack injection starts before deploy and moves out only under a declared notice policy

When the service owner estimates beforehand that an experiment costs a day or less, phase 1 also reintroduces the weakness it just fixed. The experiment names the detection layer expected to catch that class and times how fast it notices. The available layers are:

- **Workstation:** Jig's checks as code is written (secure creation), run in a test harness that stamps start and finish. It never runs on a developer's own machine.
- **Pull request:** CI checks before merge. The injection opens as a draft or on an isolated branch behind a status check that blocks merge.
- **Pipeline:** the kept regression test, run by the pipeline stage that replays kept tests, on its branch with the fix reverted.
- **Deployed test environment:** monitoring and scheduled discovery, available from phase 2 under the notice policy below.
- **Production:** runtime detection and incident response, also requiring the production-effects module, an approved production profile naming attack injection, and a maximum exposure window.

Phase 1 uses the cheapest layer that should catch the class, usually a pull request or the pipeline. It never injects past the pipeline. These changes never merge or deploy and need no notice. Time to recovery is recorded only after deployment, because before then nothing was merged or deployed. A costlier experiment moves to phase 2. From phase 3, pre-deploy experiments repeat as routine re-proof and count against the service's regression time budget.

Injection after deployment follows the notice policy in the profile's injection section: announced, unannounced, or the recommended briefed detection lead mode. The lead is a person on the detection side, told in advance and able to stop the exercise. The profile names this mode `trusted-agent`, a term from exercise practice for that briefed person; it never means an AI agent. It also names the allowed environments and the longest time from a stop to the environment restored. The section is optional only while no injection reaches a deployed environment.

The notice agreement is recorded in the tracker before the first deployed-test injection. The briefed lead confirms notice and the ability to stop. Under announced or unannounced notice, a named detection owner acknowledges the policy. Without the section, nothing is injected past the pipeline. The authorization service refuses an injection outside the declared policy before requesting approval.

Each injection includes an approved restore, held locally before it starts. A stop revokes injection authority and starts restore without further approval. In the current design, restore also starts when the injection's authority expires, but the restore's own authority expires at that same moment. So the design does not establish that the restore keeps its authority until it completes, or that the environment is restored by the deadline. Part 3 records this design gap.

### Later phases bring in each control before the automation that depends on it

Phase 3 automates verification and evaluation. Before it starts, the organization names the evaluation team. That team must be separate from whoever owns verification, shared secure defaults, security tools and tool-investment decisions. An organization that needs to start differently records an exception, with a named risk owner, an expiry and compensating controls. Phase 3 is also where models first make triage decisions from the registry of approved model routes. The lock that stops anyone changing that registry outside **promotion review**, the decision that approves a model or route for use, therefore arrives in phase 3 as well. The restore game day, an exercise that checks evidence restored from an old backup still matches the record, sits in phase 4 beside the routine restore drill it depends on.

### Each phase reports green, yellow or red

A phase ends when its required work is complete and its exit test passes. It can finish before its review date. The organization sets that date before work starts. At review, the decision owner records continue, change or stop and the next review date for any continuing work. A review never replaces the exit outcome or extends an exception.

Expected elapsed time and handoff waits are estimates. A slip against an estimate is counted in days or weeks. Ratchet does not time-track people. Cost figures use estimated effort, for example from the organization's rates for each kind of engineering work. Reports label that effort as an estimate. The decision owner sets each phase's status, and the independent reviewer confirms it.

- **Green:** the phase is on course toward its exit outcome, its review is current and no stop condition is near.
- **Yellow:** progress or a handoff is behind the organization's estimate. Or an early sign of a stop condition is moving, such as a delivery metric drifting toward the owning team's tolerance. Or a premise the phase relied on turned out false. The decision owner names a recovery step and a date.
- **Red:** a stop condition has fired, the exit test has failed with no recovery run planned, or a review is due without a recorded decision and next review date for continuing work. The work pauses until the decision owner records what happens next. A decision cannot waive a safety rule or renew an exception.

Phase 1 ends when its exit checks pass and its required records exist. It may close before its review date. Its independent reviewer may hold the proof condition and decide the outcome only while phase 1's exception to the rule that acceptance is independent is current. That exception ends at phase 1's exit or the risk owner's recorded review date, whichever is first. Reaching that date without the exit outcome stops work under the exception until full separation is in place or the named risk owners accept a standard exception.

### Quarterly status reports come from the work's own records and need no separate plan

For a multi-year program, leaders need a regular account of progress. Ratchet produces it as a dated snapshot of the same records the work already keeps: units landed since the last report, phases completed and the status of the current one with its reason, risk reduced (attack paths to the most important assets broken, weakness classes prevented by shared secure defaults, regression tests current), effect on delivery, cost, and what is next in line. It also carries the regime check: arrivals of validated findings against verified fixes for each weakness class over a window, with the ratio's trend, placing each class in one of the three regimes of part 1 by thresholds the organization derives from its own records. A class with too few findings to read reports too few to call, and until the thresholds are set the report shows the counts alone. The same snapshot can be taken on any date, so the reporting rhythm is the organization's choice.

|---|---|---|---|
| **Do nothing**: keep scanners, reviews and periodic tests as they are | No new cost or change. | Findings keep queuing; fixed weaknesses can return unseen; agents arrive anyway through vendors and teams, with no controls around them. | Rejected. Risk grows where nobody measures it. |
| **Periodic engagements**: internal or external red teams a few times a year | Skilled, independent and familiar to auditors. | Point in time; findings arrive in batches into a full fix queue; nothing keeps a fix in place between engagements. | Kept for formal and held-out exercises. They cannot keep a fix fixed between visits. |
| **Build the Ratchet loop** from bought and built parts (chosen) | Every step measured; fixes verified in the deployed system and guarded by a test; starts on existing tools. | Needs agreements across teams; value unproven inside an enterprise until phase 3. | Chosen. It finds out at a cost bounded by the first two phases, and it can be stopped at each one. |
| **Ratchet without agents**: scripted tests only | Avoids model-specific risk. Full cost is measured beside the agent arm. | Relative discovery yield is unmeasured. The comparison tests whether agents find paths the script misses. | Runs beside the agent from phase 1 as the comparison, and becomes the plan if agents add nothing. |

*How continuous validation happens. Building the loop wins because the comparison with no agent is built in.*

| Option | Strengths | Weaknesses | Decision |
|---|---|---|---|
| **Do nothing**: each team adopts agent tools on its own | Fast, no coordination. | No shared authorization or evidence rules; the team being checked runs the checks. | Rejected. Independence fails by default. |
| **One central function**: a validation platform group, standing joint attack-and-defense groups at each critical boundary, and a separate red team | Consistent standards and deep expertise. | Becomes a bottleneck; one group tends to propose, run and judge, which breaks independence; reads as new headcount. | Available as a profile choice, provided the separation rules hold. |
| **Fully federated**: every product team runs its own loop | Scales and stays close to the code. | Authorization and evidence standards drift between teams. | Rejected as a default. |
| **Shared rules, federated work**: one control plane and evidence rules; teams run the loop for their services; verification sits outside the team (chosen) | Scales without giving up independence. | Coordination cost: across the 64 combinations of ownership options tested (which team holds which function of the loop), cross-team handoffs range from 30 to 52, and only 8 combinations make every check fully independent. | Chosen. The handoff count is measured from phase 1. |

*Who runs it. Two ownership choices break separation of duties: one team running both the agents and the checks, or the evaluation team approving its own results for use. Together they rule out 28 of the 64 combinations. Of the rest, 8 keep every check fully independent; the others separate the checks by team but share a leader on some of them. In all of the rest the loop itself stays the same, and the number of handoffs varies.*

| Option | Strengths | Weaknesses | Decision |
|---|---|---|---|
| **Self-validating agents**: an agent proposes, runs and judges | Fastest; least human time. | Prompt injection is unsolved; a manipulated agent could act and grade itself; model-level defenses cannot be the primary control. | Rejected. It breaks the first two rules. |
| **Human-approved exact actions** (chosen) | Rests on the strongest evidence in the review. | Approvers drift toward approving more over time. | Chosen as the default, with approval health measured and approvers rotated on drift. |
| **Pre-authorized runs inside design limits** (chosen) | Reviewed tests, kept regression tests first, run without approval load. | Needs a trust gate to earn and keep the standing permission (the evidence a test must show first, such as a run of clean passes), and a consequence register, the list of assets rated by consequence, good enough to rate each action. | Chosen for reviewed tests inside the limit the design sets for their agent and below the organization's consequence line; a run steps down automatically after any harmful or out-of-scope result, and everything outside the limit goes to a person. |
| **Trust that grows with the agent's accuracy alone** | Simple to measure. | A long run of correct calls says nothing about how much damage the next wrong one can do, and attackers adapt to what the record rewards. | Rejected as the only gauge. Phase 2 notes each route's recent accuracy and how far its limit reaches before every agent action, measures each wrong action's cost on its own, and reports which better forecast that cost. |

*What an agent may do on its own. Agents propose. The design limits what each agent can touch. People approve any action outside those limits. Inside them, reviewed tests earn standing permission through a trust gate.*

<a id="part-02-six-risks-remain-and-each-has"></a>
## Six risks remain, and each has a measure that shows it early

| Risk | What Ratchet does about it | What shows it |
|---|---|---|
| **The value case fails.** No published enterprise study counts full cost, including verification hours. | Runs the no-agent comparison from day one; counts estimated verification effort as cost. | The early stop rule in part 1; phase 3's comparison. |
| **Fix capacity saturates.** All quality work draws on finite engineering time. The authors' weak, untested bet is that validating beyond fix capacity increases time lost without reducing exposure. Phase 3 tests it. | Opens no new run against a team without booked fix capacity. Holds each team to the fix cap it set with security (or the decision owner's default). Findings above the cap are logged with reasons for a monthly review security co-signs. Findings at or above the consequence line, findings with a sourced exploitation signal (a cited report of active exploitation) and findings with an external disclosure deadline enter regardless. A sourced exploitation signal also starts the organization's response window, and security hears ahead of an outside disclosure deadline. The control plane applies the cap. A finding held at two reviews goes to the security risk owner, who sends it or accepts the risk until a set date. Inside a consequence tier, internet exposure and end-to-end automatability order the work. These signals never lower a gate's outage posture (what the gate does while Ratchet is down) or count as evidence. A temporary mitigation is replayed, names its owner and expiry, and leaves remediation time running. Security co-creates each fix with the owning engineer and an agent in one pull request, including a component-local regression test the owning team keeps in its suite. While saturation lasts, investment shifts to the paved road. | Queue age, refusals per team, the saturation signal per team, and each team's time lost to security debt, from a periodic survey of the team with the flow record beside it. |
| **Approvers drift.** Approval rates rise with familiarity. | Measures approval health, seeds known-bad proposals to measure it, shows each approver the outcome of every run they approved, and on drift first checks whether proposal quality changed, then recalibrates, rotating approvers only as a last step. Approvals narrow to boundary crossings. | Approval-rate trend per approver and action class. |
| **Prompt injection stays unsolved.** | Contains it structurally: no agent holds authority, outsider text is quarantined, and a design check flags any route that combines untrusted text, private data and a way to send data out. | The design check fails the design if a new path reopens the combination. |
| **The design is large.** | Phase 1 builds none of it. It runs on existing tools, and anything that cannot show value by phase 2 waits. | Handoffs per closed loop, with a ceiling per phase. |
| **The regression gate slows delivery.** The literature never isolated a gate's own effect. | Advisory first; a time budget per service; replays selected by declared dependency. A kept test leaves the blocking path once a cheaper kept check covers its weakness class and itself fails against the test's reverted fix. A quiet test, one that has gone its set quiet period without failing, moves only its extra time-based runs to a slower lane and still blocks changes that touch its declared dependencies. A flaky one is quarantined as an exception under a cap. Each is re-proved on a schedule against its fix reverted, and leaves the blocking path on a "no longer fails" result only once the verifier confirms it. | The five DORA delivery metrics against each service's baseline. |

*Remaining risks. Each is contained or watched; none is claimed solved.*

The stop conditions in part 1 apply to phases 1 and 2. Every later phase has its own test in the phase table above, and failing it stops further widening until the cause is fixed or the plan changes. All 138 failure scenarios, the ways the design itself can fail (reference R3), have a test; 110 run in the pipeline and the rest as exercises.
