# Specification: Impact report

The impact report derives the risk and threat-model delta of one organization patch. It compares the organization's model before the patch with the model after it, looks up every touched part in the quality, failure, rule and work-unit data, and writes the factual half of the patch's "Risk and threat-model delta" section. The judgment half stays as explicit slots for the organization's agent and people: what an attacker gains, new failure modes, compensating controls, technical and organizational feasibility. The organization's agent runs it on every patch before proposal and again before acceptance.

## Ideal state

- IR-1. The report lists every element, relationship and contract the patch adds, removes or changes, found by comparing the before and after models, so side effects of an op are included.
- IR-2. Each changed item names every changed field with its before and after value; provenance fields (`source`, `patch`, `patch_op`, `patches`, `retired_by`) are ignored.
- IR-3. The report lists every trust-zone crossing created or removed, including those caused by an element changing zone.
- IR-4. The report lists every touched element with an enforcement mark before or after, and every mark gained or lost.
- IR-5. The report lists every separation of duty in scope of the change, with the reason.
- IR-6. The report lists every failure scenario naming a touched element, and flags scenarios naming a removed element.
- IR-7. The report gives tier, failure behavior and critical paths of every touched element, and flags an added element that needs a tier and has none.
- IR-8. The report lists every should-never code the patch could trip, each with the trigger that selected it.
- IR-9. The report lists work units building touched elements, units building removed elements, and added elements outside the systems EXT and PEOPLE that no unit builds.
- IR-10. Five judgment slots, holding seven values (each feasibility slot holds a grade and a note), start as `FILL`; the two feasibility grades accept only holds, bet, unknown or blocked.
- IR-11. The same content appears as Markdown sections ready for the patch and as one fenced YAML block, both in the layouts given under Outputs.
- IR-12. Output is deterministic: lists in the natural order defined below, no timestamps.
- IR-13. Check mode fails when the patch's recorded delta differs from a regenerated one, and says whether the facts changed or only the stamp (the model hashes and the layout) or the edition's wording; regeneration keeps filled judgment slots byte for byte.
- IR-14. A patch that does not apply produces no report and exits non-zero.
- IR-15. Every touched relationship that joins two planes is listed with its contract or its `no_contract` reason; one with neither is a direct finding `model.plane-join`.
- IR-16. Two tools built from this specification give the same model hashes, and the same YAML block text, for the same inputs.
- IR-17. The report lists every part whose account class the patch changes (from, to, and whether the part enforces a rule) and every account class the patch adds, changes or removes, found by comparing the compiled overlay before and after the patch.
- IR-18. The report lists every part that gains or loses exposure to untrusted content, with the relationships that expose it.
- IR-19. A recorded block written in an earlier layout, or differing only in the edition's wording, is a restamp when it holds the same facts; it never sends an accepted patch back through acceptance.
- IR-20. Check mode skips a rejected or withdrawn patch. In every mode, a run with a profile warns when an accepted patch has no named accepter in that profile.
- IR-21. The report lists every finding kind the patch adds, removes or changes, found by comparing the before and after models' `finding_kinds`: an added kind with its closure check's check type and judging part, a changed kind with each changed field before and after.
- IR-22. When the profile gives teams stable ids, a separation cites the id, and renaming a team that keeps its id is a restamp, never a fact change.
- IR-23. A finding kind the patch adds, removes or changes in any field touches the part that judges its closure check, before and after, so that part's separations and should-never codes come into scope like any other touched part's.
- IR-24. A key a patch takes away with `unset` is a changed field of its item, with its value before and null after, so the item is listed as changed and touched like any other changed item.

## Inputs

The bundled CLI uses `--data <full baseline folder> --patches <folder> --patch <id>`. Writing mode replaces the patch's generated risk section. `--check` compares it without changing it. `--print` prints the generated Markdown without changing the patch; `--report <path>` still writes JSON when requested. Give all modes the same profile, source shared document and source organization exceptions.

For the ratchet, jig and core compositions, add `--mode ratchet`, `--mode jig` or `--mode core`, with `--print` and a separate JSON report path. Full is the default. Lone modes require print without check so they cannot replace or check the full acceptance block. Replay the original patches and expects values on the full baseline first, then compose both snapshots and their layers and units in the selected mode before deriving the delta. Projection failure is IR-E-input. Do not replay full patches on projected models or strip operations for absent parts. The pin command's output supplies a verified full baseline with the required data. The exact commands are in workflow-build-tools.md. Keep lone outputs as composition review evidence beside the full risk section.

An unanswered profile team, including literal FILL, an empty string or null, is represented as null in teams and rendered as not set. A stable team id is never assigned to an unanswered team.

- The edition's data: `model.yaml`, `rules.yaml`, `quality.yaml`, `failures.yaml`, `realization.yaml`, `units.yaml` and the worked-example overlay `overlay-aws.yaml`.
- The starting design layer is the unpatched layer for the same model in the data folder. An optional `--layer` supplies that starting layer, including any organization baseline. Read realization.yaml, quality.yaml and failures.yaml there when present, otherwise from the data folder. Replay the included patches once into copies of that layer. Read planes, tiers and quality from the result after the target patch. Keep the before-target failure inventory beside newly added scenarios so removals still report their scenario impact. Do not pass a layer already compiled through the target or later patches.
- The patches. The patch under report is `org/patches/O<n>-<slug>.md`, with one fenced yaml ops block inside its `## Ops` section. Only that section is searched for the ops block, as the patch applier does, so the block this tool writes under the Risk heading never counts as a second one. Its **base model** is `model.yaml` with every earlier patch (`O01` to `O<n-1>`) applied in order, accepted and proposed alike, except a patch whose Status line starts with `rejected` or `withdrawn`, and except a patch named by a preview withdrawal. Its **after model** is the base with `O<n>` applied. A writing run or a print run applies `O<n>` whatever its own Status says; only check mode skips a rejected or withdrawn patch under report (behavior 16), and the Status filter above applies to earlier patches.
- **Preview withdrawals** (`--preview-withdraw <ids>`): each names an earlier patch to leave out of the base as if it were withdrawn, so a replacement can be reported together with the withdrawals it implies before anyone decides them. The option takes one patch id or a comma-separated list of ids and may be repeated, and every id given counts, as the patch applier reads its own `--preview-withdraw` (spec-patch-applier.md, PA-26). A name that is not a patch before the one under report is IR-E-input. A later patch that depends on a left-out one usually fails to apply (IR-E-apply), which says it must be withdrawn too.
- **The overlay.** The tool compiles the overlay alongside the models: it applies the same patches, with the patch applier's layer semantics, to a starting overlay, giving the overlay before and after the patch. The starting overlay is found the way the patch applier and the upgrade tool find it: an explicit overlay option wins; else the file the version record names (`overlay.file` in `org/version.yaml`, resolved beside that file); else the edition's worked example, `overlay-aws.yaml`. Whenever the file in use is the recorded one, however it was found, its SHA-256 over its bytes, as 64 lowercase hex digits, must equal the recorded `overlay.sha256`, or the run stops with IR-E-input at that file, located at the name the version record gives it, also when the overlay option names that same file. The option names the recorded file when the two paths, each made absolute against the directory the tool runs in, are the same text; links are not followed. The version record is `version.yaml` beside the patch directory unless an option names it; "beside the patch directory" means in the folder that holds the patch directory, the way `org/version.yaml` sits beside `org/patches/`; with no version record, or one with no `overlay`, the worked example is used. The comparison names no op, so every op that changes the overlay is covered, those that add or change account classes included. The patches are applied to the whole layer as read (realization, quality and failures as Inputs above finds them, with the starting overlay), so every layer refusal of the patch applier, `op.layer-incomplete` on a `set_layers` that starts an entry included, stops the run with IR-E-apply; read realization, quality and overlay back from the result after each patch.
- **The organization's units**, `org/units.yaml` (beside the patch directory unless an option names it), when present: the three lists the unit graph specification defines, `add` (whole units), `modify` (`id` and a `set` mapping merged over the unit's top-level keys) and `remove` (ids), applied in that order to the edition's units. An `add` whose id is already a unit, shipped or added earlier in the same file, is IR-E-input at that id. The tool reports one error for each such `add`, in file order, and then stops with no report: a shipped id added once gives one error, and a new id added three times gives two, one for each `add` after the first. A shipped unit is changed with `modify`, and the unit graph and the status report refuse a duplicate `add` the same way. A `modify` or `remove` naming a unit that does not exist is skipped here; the unit graph reports it. A file that is not a mapping of those lists is IR-E-input.
- **Ops only.** The tool reads each patch's ops block and Status line, and applies the ops with the op semantics and namespace rules of the patch applier specification (`spec-patch-applier.md`). It does not run the applier's file-level checks: required and empty sections, `depends_on`, previews and the Status form. Those checks belong to acceptance, and this tool is what fills the Risk section they check. So an accepted earlier patch with an empty Risk section still enters the base model here, while the applier refuses it. Both specifications hold.
- `quality.yaml`: `elements` (id to `[tier, failure_mode, note]`) and `critical_paths.paths`, a mapping from critical path id to an entry whose `must_answer` lists element ids. The path ids are the names the Quality section prints.
- `failures.yaml`: `scenarios[*]` (`id`, `elements`, `invariant`, `test.kind`).
- `realization.yaml`: `elements` (id to an entry whose `plane` names the element's plane).
- `rules.yaml`: `families` (a mapping whose keys are the card ids; each card's `codes`, a mapping from code to its text whose keys are the codes, and `failure_scenarios`), and `rule_enforcing_parts.parts` (part id to the invariants it enforces). A `rules.yaml` without a `rule_enforcing_parts.parts` mapping is an input error.
- `units.yaml`: a list of units, or a mapping with a `units` list, each with `id`, `phase`, `elements[*]` (`id`, `fidelity_from`, `fidelity_to`), and optionally `independence_sensitive` and `separates` (pairs of role names such as proposer and approver). Many shipped units carry neither: an absent `independence_sensitive` reads as false, and an absent `separates` as `[]`.
- Optional `org/profile.yaml`, read only when the profile option names it (the tool never looks for one by itself): team names printed beside each affected separation, and `separation.security_risk_owner_role`, the role that accepts patches. The team names are facts of the recorded block, so check mode must be given the same profile as the run that wrote the block: without it, or after a team is renamed, every patch that brings a separation into scope is stale (IR-E-stale), and an accepted one goes back through acceptance. The profile may give each team a stable id in `separation.team_ids`, a mapping from the team name as the role fields write it to an id that never changes; a renamed team keeps its id under its new name. Where both the recorded and the regenerated block carry an id for the same side position of the same separation, the id is the fact and the name is wording, so the rename is a restamp (IR-22); where either lacks one, the name stays the fact. Give check mode the same layer, overlay and units too.
- Options: the edition directory, the patch directory, the patch id, the optional profile, the optional layer directory, the optional overlay file, the optional version record, the optional organization units file, preview withdrawals, `--check`, a print mode that writes no patch file and prints the section instead, and an optional path for a JSON report. The JSON report is written in every mode whenever its option is given, print and check modes included, and on errors too. A path given as an option is read relative to the directory the tool runs in. The patch id is matched against the part of each patch file name before its first hyphen, exactly as written (`O03` matches `O03-merge-approver-roles.md`); no match is IR-E-input at the patch id. Earlier patches are those whose number has a lower integer value.

The layer option supplies realization, quality and failures. It does not select an overlay from that folder. Overlay selection follows the explicit option, version record and edition fallback above.

## Outputs

**Markdown.** Thirteen sections in this order, each written as `### <name>`, a blank line, its lines (or the single line `None.` when it has none), and a blank line: Summary; Elements, relationships and contracts; Trust-zone crossings; Plane joins; Placement; Untrusted-content exposure; Enforcing parts; Separations of duty; Failure scenarios; Quality; Should-never codes that may need an exception; Work units; Judgment. In the line forms below, `<x>` is a field value, `[...]` is present only when its condition holds, a list is joined with ", " unless stated, and `<json x>` is the value written as JSON (strings in double quotes, `null` for none).

| Section | Lines, in this order |
|---|---|
| Summary | when anything changed (the negation of the IR-W-empty condition in behavior 3: an element, relationship, contract or finding kind added, removed or changed, or a placement or account class changed): `This patch adds <n>, removes <n> and changes <n> elements; adds <n>, removes <n> and changes <n> relationships; and adds <n>, removes <n> and changes <n> contracts. It creates <n> and removes <n> trust-zone crossings, touches <n> enforcing parts, and brings <n> separations and <n> should-never codes into scope.[ It adds <n>, removes <n> and changes <n> finding kinds.][ It changes the account class of <n> parts and adds, changes or removes <n> account classes.][ <n> parts gain and <n> lose untrusted-content exposure.]`, the first bracket present when the block holds `finding_kinds`, the second when either placement count is above zero and the third when either exposure count is, then a blank line, then `Every code below is a candidate. The model checks and the profile checker, run on the after model, decide whether a rule is broken.` |
| Elements, relationships and contracts | ``- Element added: `<id>` (system <system>, zone <trust_zone, or none>, <role_class>)``; the same with `removed`; ``- Element changed: `<id>` <field>: <json before> to <json after>`` per field; ``- Relationship added: `<id>` <from> to <to> (<kind>[, carries <carries>][, content <content>])``; ``- Relationship removed: `<id>` <from> to <to> (<kind>)``; ``- Relationship changed: `<id>` <field>: <json before> to <json after>``; `- Contract added: <name>`; `- Contract removed: <name>`; `- Contract changed: <name> <field>: added <json added>, removed <json removed>` for a set field, else `: <json before> to <json after>`; ``- Finding kind added: `<id>` (closure check <check_type>, judged by <judged_by>)``; ``- Finding kind removed: `<id>` ``; ``- Finding kind changed: `<id>` <field>: <json before> to <json after>`` per field |
| Trust-zone crossings | ``- Created: `<relationship>` <from_zone> to <to_zone> (<kind>)[, into a protected zone]``, then ``- Removed: `<relationship>` <from_zone> to <to_zone> (<kind>)`` |
| Plane joins | ``- `<relationship>` <from> (<from_plane>) to <to> (<to_plane>): `` then `carries <carries>`, or `no contract: <no_contract>`, or `no contract and no no_contract reason` |
| Placement | ``- `<id>` account class <from, or none> to <to, or none>[, enforces a rule]``; then per account class, ``- Account class added: `<name>` for zones <zones, or none>: <json text_after>``, ``- Account class removed: `<name>` ``, or ``- Account class changed: `<name>` `` followed by `text <json text_before> to <json text_after>` when the text changed and `zones <json zones_before> to <json zones_after>` when the zones changed, joined "; " |
| Untrusted-content exposure | ``- Gained: `<id>` through <via>``, then ``- Lost: `<id>`, which was exposed through <via>`` |
| Enforcing parts | ``- `<id>` (<how_touched>)``, then `: loses <lost>` when it lost marks, `; gains <gained>` (`: gains` when nothing was lost) when it gained some, `: keeps <marks_after>` when neither, then `. Invariants <invariants>.` |
| Separations of duty | `- <id>[ (<rule>)]: <side a fields joined " or "> and <side b fields joined " or ">[ (now <teams a joined " or "> and <teams b joined " or ">)]. Because <reasons joined "; ">.`; a team that is not set reads `not set`; the teams appear only with a profile |
| Failure scenarios | `- <id> (<invariant>, <test_kind> test): touches <touched_elements>[. Names a removed element; the scenario needs revising].` |
| Quality | ``- `<id>`: needs a tier and has none`` when `tier_missing`, else ``- `<id>`: tier <tier, or none>, <failure_mode, or no failure behavior>``; then, after either form, `; critical paths <critical_paths>` when there are any |
| Should-never codes that may need an exception | ``- `<code>` (basis <basis>[; trade-off card <card>]): <triggers joined "; ">`` |
| Work units | ``- <unit> (phase <phase>) builds `<part>` from <fidelity_from> to <fidelity_to>[, independence sensitive][; separates <pairs, each "a and b">]``; then `- <unit> builds a removed element and needs revising`; then ``- `<id>` is added and no unit builds it`` |
| Judgment | the five lines under behavior 13, never `None.` |

A changed set field (behavior 3) is written two ways on purpose. An element or relationship line writes every changed field as its whole value before and after, because a reviewer reads those fields as one value, such as a relationship's `carries`. A contract line writes a set field by the members it gained and lost, because a contract's producer and consumer lists are long and change a member at a time. The YAML block holds both forms for every set field.

Each line ends at its last visible character. The code spans in the table above are padded only where Markdown needs a space beside a backtick, so the removed account class and removed finding kind lines end at the closing backtick of the name or id, with no trailing space. A changed account class line has one space after the name's closing backtick, then the parts that changed, for example ``- Account class changed: `org-admin` text "old" to "new"; zones ["control"] to ["control","execution"]``.

**YAML block.** After the Judgment section, one fenced block, opened by a line of three backticks followed by `yaml` and closed by a line of three backticks, holding one mapping, `impact_report`, with these keys in this order. Tools compare a recorded block with a regenerated one by parsed value (behaviors 15 and 16), never as text; the text layout below is still fixed, so two tools write the same bytes and a person editing a judgment slot knows what to find.

```yaml
impact_report:
  patch: O03-merge-approver-roles          # the patch file name without .md
  layout: 2                                # the layout this specification defines
  base_model_hash: <sha256>
  after_model_hash: <sha256>
  elements: {added: [{id, system, trust_zone, role_class}], removed: [...], changed: [{id, fields: [{field, before, after}]}]}
  # a set field (carries, aliases, produced_by, consumed_by, partitioned_by) also lists added and removed members;
  # any other field carries neither key, in elements, relationships and contracts alike
  relationships: {added: [{id, from, to, kind, carries, content}], removed: [...], changed: [...]}
  contracts: {added: [name], removed: [name], changed: [{name, fields: [{field, before, after}]}]}
  finding_kinds: {added: [{id, check_type, judged_by}], removed: [id], changed: [{id, fields: [{field, before, after}]}]}  # only when a kind changed
  crossings: {created: [{relationship, from_zone, to_zone, kind, into_protected_zone}], removed: [...]}
  plane_joins: [{relationship, from, to, from_plane, to_plane, carries, no_contract, uncovered}]
  placement: {parts: [{id, from, to, enforces_rule}], account_classes: [{name, change, text_before, text_after, zones_before, zones_after}]}  # change: added | changed | removed
  exposure: {gained: [{id, via: [relationship]}], lost: [{id, via: [relationship]}]}
  enforcing_parts: [{id, how_touched, marks_before, marks_after, gained, lost, invariants}]
  separations: [{id, rule, reasons: [text], sides: {a: [field], b: [field]}, codes: [code], teams: {a: [name], b: [name]}, team_ids: {a: [id], b: [id]}}]  # teams only with a profile; team_ids only when it keeps them
  failure_scenarios: [{id, invariant, test_kind, touched_elements, names_removed_element}]
  quality: [{id, tier, failure_mode, critical_paths, tier_missing}]
  should_never_codes: [{code, card, basis, triggers: [text]}]      # basis: direct | card
  units: {building_touched: [{unit, phase, part, fidelity_from, fidelity_to, independence_sensitive, separates}], building_removed: [unit], unbuilt_added_elements: [id]}
  judgment:
    attacker_gain: FILL
    new_failure_modes: FILL
    compensating_controls: FILL
    technical_feasibility: {grade: FILL, note: FILL}
    organizational_feasibility: {grade: FILL, note: FILL}
```

A missing value is `null`, an empty list is `[]`. `finding_kinds` is the one conditional key: it is written, after `contracts`, only when the patch adds, removes or changes a finding kind, so a block recorded before the registry existed, or for a patch that touches no kind, holds the same facts without it. A changed item's `fields` are in natural order of field name, over the keys either version of the item holds. `separates` in a unit row is a list of strings, each pair written `a and b`. `content` in a relationship row is the relationship's `content` marking, or null.

**Order of lists.** Every list in the block is in natural order (behavior section, first paragraph), each by the key named here: added, removed and changed elements, relationships and finding kinds by id, and contracts by name; a set field's `added` and `removed` members by value; crossings by relationship, then from zone, then to zone; plane joins by relationship; placement parts by id and account classes by name, each class's zones by zone name; exposure rows by id, and each row's `via` by relationship; enforcing parts by id, and each part's `marks_before`, `marks_after`, `gained` and `lost` by mark name, with its `invariants` by invariant and without duplicates; separations by id, and each separation's `reasons` by text without duplicates; failure scenarios by id, and each scenario's `touched_elements` by id; quality rows by id, and each row's `critical_paths` by path id; should-never codes by code, and each code's `triggers` by text without duplicates; unit rows as behavior 12 gives, `building_removed` and `unbuilt_added_elements` by id. Three lists keep a fixed order instead: a separation's `sides`, `teams` and `team_ids` follow its profile fields in the id table of behavior 8, its `codes` follow that table's codes column, and a unit row's `separates` keeps the unit's own order.

**Edition wording.** The reasons and triggers are edition wording (behavior 15), and two tools still write them alike, since the exact-output fixture compares the block's text. **Text layout of the block** (layout 2). The block is written as these rules give it, with no anchors, aliases, flow collections other than `[]` and `{}`, comments or blank lines:

- Indentation is two spaces per level, starting at zero for `impact_report:`. No line has trailing spaces.
- A mapping writes each key on its own line, in the order above. A scalar value goes on the key's line after `: ` (colon, one space). An empty list is `[]` and an empty mapping is `{}`, on the key's line. A non-empty mapping or list goes on the following lines, after the key and a colon with nothing after it, one level deeper than the key.
- A list item is written `- ` at its list's indentation. A scalar item follows the dash on the same line. A mapping item writes its first key on the dash line, right after `- `, and its other keys on the following lines, aligned under the first key.
- A string is written as a JSON string: double quotes, with backslash escapes only where JSON requires them, other characters, accented ones included, as they are. `null`, `true`, `false` and numbers are written as JSON writes them.
- A key is written as it is when it starts with a letter or `_`, holds only letters, digits, `_`, `-` and `.`, and is not `true`, `false` or `null` in any case; any other key is written as a JSON string.

The exact-output fixture holds a whole block in this layout. The judgment lines a person has filled are carried over as they were written (behavior 14), so they may use any YAML that parses to the same values.

For every changed field, write keys in order `field`, `before`, `after`, then, only for a set field, `added`, `removed`. Removed relationship rows carry the same factual keys as added relationship rows, including `carries` and `content`; removed crossing rows likewise include `into_protected_zone`. Model hashes include the patch core's `patch`, `patch_op` and `patches` on touched items and `retired` only after a removal, with no newly generated `meta` stamp. YAML core numbers normalize before hashing and date-shaped strings stay strings. Unit `separates` pairs are written as `a and b` in the unit's own pair order. A check-mode stale/restamp error does not suppress the seven per-slot `IR-W-unfilled` warnings. Exposure `via` includes every qualifying incoming relationship after fixed-point propagation, not only the first exposing edge. Team ids compare at each separation/side/index as behavior 15 states, including across layouts. For a layout migration, remove stamp, judgment and wording keys, compare only keys shared at each path with list positions merged, normalize `unmapped:<id>` to `unmapped`, and normalize a two-role list to `a and b`. First generation and a stamp-only rewrite raise no `IR-W-reaccept`. Preview-withdraw values split on commas and accumulate across repeated options.

**JSON report.** With the report option the tool writes one JSON object with these keys in this order: `patch` (the patch file name without `.md`, or null when no patch file matched), `impact_report` (the object above, or null when there is none), `markdown` (the text the tool writes under the Risk heading, or null), `messages` (a list of `{level, code, location, text}` in printed order) and `written` (true whenever a writing run with no error writes the patch file, even when the bytes it writes equal the file's bytes before; false in check mode, print mode and on any error). The `markdown` text is the thirteen Markdown sections, then the fenced YAML block. It starts with `### Summary`, with no blank line before it. Each section ends with its own blank line, so exactly one blank line, the Judgment section's, sits between the last judgment line and the fence line that opens the block, and the text ends with the closing fence line, with no line break after it. Print mode still writes this report when the option is given, so a caller previews the section and its facts without touching the patch file.

**Messages** are printed to standard output one per line, errors first and then warnings, each group sorted by code and then location in natural order. In print mode the Markdown is printed first, then the messages.

## Behavior

**Natural order.** Ids and every other listed string sort the same way in this tool, the status report and the unit graph. Split each string into runs of digits and runs of other characters. Compare the runs pairwise from the left: two digit runs by numeric value, and on a tie the shorter run first; any other pair by code point. When every pair is equal, the string with fewer runs comes first. So U-27 comes before U-172, and U-1 before U-01.

1. **Models.** Build base and after models. If any included patch fails to apply, stop with an error and write nothing.
2. **Hashes.** `base_model_hash` and `after_model_hash` are SHA-256, written as 64 lowercase hex digits, of the UTF-8 bytes of the model's canonical JSON, per the JSON Canonicalization Scheme (RFC 8785): object keys sorted by UTF-16 code units, no whitespace, numbers in shortest round-trip form (so `2.0` is `2`), and strings escaped only where JSON requires. What is hashed is the model as the ops leave it: the parsed `model.yaml` (YAML 1.2 core schema, so a date such as `2027-01-15` stays a string), with each included patch's ops applied as the applier's op table says. Provenance fields and `retired` lists are included; the applier's `meta` stamp is not. The model has no `retired` key until an op removes something: the first removal creates `retired` with both lists, `elements` and `relationships` (one stays `[]` when nothing of that kind is removed), and each removed item is appended, in op order, as it stood with `retired_by` set to the removing patch. A patch that removes nothing leaves the key absent, and that absence is part of the hash. The hash covers the model only, never the design layer.
3. **Diff.** Match elements and relationships by `id`, contracts by `name`. Present only after: added; only before: removed; both, with a non-provenance field different: changed. A field one version holds and the other lacks reads null on the side that lacks it, so a key the patch takes away with `unset` is a changed field from its value to null (IR-24), and taking away a key that held null changes nothing. Match finding kinds (the model's `finding_kinds`, present in editions that carry that field; a model without it has no finding kinds) by `id` the same way; a kind's fields (`closure_check`, `never_closes` and the rest) compare as whole values. Compare `carries`, `aliases`, `produced_by`, `consumed_by` and `partitioned_by` as sets, and list the members each set gained and lost. A contract whose only change is losing, from `produced_by` or `consumed_by`, elements the patch removed is not changed: the applier cleans those lists when it removes an element, and the cleanup changes no contract. A patch that adds, removes and changes no element, relationship, contract or finding kind, and changes no placement or account class (behavior 18), raises IR-W-empty. A patch that changes only a failure scenario still raises this warning. Its Failure scenarios section is populated, while Summary follows the same empty condition.
4. **Touched set.** A touched relationship is one the patch adds, removes or changes. A touched contract likewise. An element is touched when added, removed or changed (`how_touched` added, removed, changed); when it is an endpoint, before or after, of a touched relationship (`via-relationship`); when it produces or consumes a touched contract in the base model or in the after model, so a part a patch drops from a contract's `consumed_by` is touched too (`via-contract`); when it is the judging part, `closure_check.judged_by` before or after, of a finding kind the patch adds, removes or changes (`via-finding-kind`, IR-23); or when the patch changes its account class (`placement`, behavior 18). The first that applies, in this order, is its `how_touched`. A judging part the model does not hold is not touched.
5. **Crossings.** A relationship crosses when its endpoints sit in different zones; a null zone counts as `people`. Diff the sets of (relationship id, from zone, to zone, kind) over all relationships. `into_protected_zone` is true when the target zone is control, execution or evaluation and differs from the source zone. Sort by relationship, then from zone, then to zone.
6. **Plane joins.** For each touched relationship present in the after model: skip it when either endpoint is an element in system `PEOPLE`, before or after (people are roles, not planes). An endpoint's plane is the `plane` of its entry in `realization.yaml`; an endpoint with no plane is on its own plane, written `unmapped:<id>` with the endpoint's id, the same spelling the model checks use, so it differs from every plane, another unmapped endpoint's included. The relationship joins planes when its two planes differ or either is unmapped. List each join with its `carries` and its `no_contract` reason (null unless a non-empty string). `uncovered` is true when it carries nothing and has no reason; each uncovered join adds the direct code `model.plane-join` (behavior 11). Removed relationships are not listed. A patch that only moves a part to another plane touches no relationship, so its joins surface in the model checks, not here.
7. **Marks,** each with the invariants it implies:
   - `enforces-rule`: a part listed in `rules.yaml` `rule_enforcing_parts.parts`, with the invariants listed there.
   - `control` (role_class control) and `control-zone` (trust_zone control): I1, I6. `t0` (tier T0): I6. `load-bearing`: I7. `model-boundary`: I7, I1. `decides:<type>`: I1, I3, I4. `isolated-draft`: I2. `holds-nonpublic`: I7. `context-builder` (a producer of the ContextSnapshot contract): I7. `partitioned` (`partitioned_by` set): I5.
   The flags `load_bearing`, `model_boundary`, `isolated_draft` and `holds_nonpublic` mark only boolean true; `decides` contributes its value, `partitioned_by` must be a non-empty list, `context-builder` is membership in ContextSnapshot's `produced_by`, and T0 comes from quality as read, without compiling a new tier. List a touched element when it has any mark before or after, with its invariants (the union over both models). Each touched element that loses a mark raises IR-W-mark-lost.

A pair the table does not list selects nothing, so the ids whose pairs cell reads "none" (security-risk-owner among them) come into scope only through the selector table. Every selector that fires adds one line to `reasons`: an invariant selector adds one line for the invariant, naming every touched element whose marks imply it (for example `invariant I1 (<ids in natural order>)`), and every other selector adds one line per element, relationship or unit row that fires it. `reasons` is in natural order with duplicate lines dropped. The selector is deliberately wide; judgment narrows it.

   Each separation carries its `rule` label, its profile fields as `sides` (`a` and `b`, each a list of field names), the profile codes it adds (behavior 11), and, with a profile, the team names in `teams`, one per field and null where unset. When the profile's `separation.team_ids` is a mapping, the separation also carries `team_ids`, with the same shape as `teams`: each name's id, null where the name is unset or has no id (an id that is not a non-empty string counts as none). A side with two fields lists both, in the order the table gives, and the Markdown joins them with " or ".

9. **Failure scenarios.** Select scenarios whose `elements` meet the touched set, plus every organization scenario the target patch adds or modifies. Flag those naming an element this patch removes, each with IR-W-scenario-orphan. For an added or modified organization scenario, `touched_elements` is the union of its before and after named parts in natural order. For other scenarios it lists only the scenario's elements in the touched set, in natural order.
10. **Quality.** For touched elements present after, read tier and failure behavior and list critical paths whose `must_answer` contains them. `tier_missing` applies to added elements with no tier that the model checks' quality coverage requires a tier for (validation parts, and organization parts whose role class is neither `human` nor `existing`), each with IR-W-tier-missing. The test reads the part's id and role class only: a validation part is one whose id starts with `s`, a digit and a dot (`s2.`), and an organization part is one whose id starts with `org.`. The system a part sits in plays no part, so an `org.` part with role class `existing` in a validation system such as S6 needs no tier.
11. **Should-never codes,** `basis: direct`:
   - `model.boundary`: a touched element has the model-boundary mark before or after, or a touched relationship starts at one.
   - `model.advisory`: a touched relationship ends at a deciding part or carries TypedDecision, or an element gains or loses `decides`.
   - `model.trifecta`: a touched producer, load-bearing or holds-nonpublic element, where a producer is an element whose role class is `producer` in the base or after model (the contract sense of the word, used for context builders below, plays no part here); or a touched relationship with `content: untrusted` (trigger `relationship <id> has content: untrusted`), carrying ContextSnapshot, or leaving a producer toward system S4, system EXT or with kind inference; or an element whose role class after the patch is `producer` that gains exposure (behavior 19), with the trigger `<id> gains untrusted-content exposure`.
   - `model.quarantine`: a touched context builder, or a context builder (a producer of the ContextSnapshot contract) that gains exposure (behavior 19).
   - `model.ai-free-control-plane`: a touched relationship, in its base or after version, with an endpoint that sits in the control or execution zone before or after the patch and is not a model-boundary part, when either the other endpoint is on the model path or the relationship is of kind inference (whatever the other endpoint). Each endpoint that qualifies adds its own trigger. The model path is a fixed list, the model gateway, request-data gate, response and proposal gate, route and budget broker, inference endpoints and hosted frontier endpoint (`s4.model-data-gateway`, `s4.request-data-gate`, `s4.response-proposal-gate`, `s4.route-budget-broker`, `s4.inference-endpoints` and `ext.hosted-frontier-endpoint`, the model checks' list), less any of them that has `model_boundary: true` in the base or after model. In the shipped design the two gates carry that flag, so the path is the other four; the subtraction keeps the rule right when an organization's patch sets or clears the flag.
   - `model.plane-join`: each uncovered plane join (behavior 6).
   - `model.t0-placement`: a T0 element added or changing zone.
   - `admin.control-plane-operator`: a touched T0 control-zone or model-boundary part. `bought.without-org-controls`: a touched `enforces-rule` part.
   - Each in-scope separation adds its profile code, for example `sep.producer-approver`, or `admin.cpo-is-platform`, `admin.cpo-is-producer` and `admin.cpo-is-verifier`.

   Every code records each trigger that selected it; `triggers` is in natural order with duplicate lines dropped. One part can select two codes with the same selector: a model-boundary part, for example, raises both `model.boundary` and `admin.control-plane-operator`, each with its own trigger. That is intended; each code is a separate candidate. Then add, with `basis: card`, every code of each card whose `failure_scenarios` contains a selected scenario, with the trigger `scenario <id> on card <card>`; a code found both ways stays direct and keeps only its direct triggers. `card` names the card whose `codes` holds the code, whatever its basis, so a direct code a card holds names that card too; when two cards hold it, the first in file order; when none does, null. A fixture that brings its own `rules.yaml` with no cards gets null for every code. All codes are candidates: the model checks and the profile checker on the after model decide whether a rule is broken, and the Summary says so.
12. **Units.** Select units whose `elements` contain a touched id. `building_touched` has one row per unit and touched part that the after model keeps, sorted by unit and then by part, both in natural order (the unit's phase plays no part in the order); a unit that builds a removed element goes into `building_removed` instead (IR-W-unit-orphan each), and also keeps its rows for its other touched parts. List added elements outside EXT and PEOPLE that no unit names (IR-W-unbuilt each).
13. **Judgment slots.** First generation writes `FILL` in each. The Markdown shows them as these five lines: `- Attacker gain (what someone controlling a touched input or identity can now do): <attacker_gain>`; `- New failure modes (and whether a new failure scenario is needed): <new_failure_modes>`; `- Compensating controls (each tied to a code above): <compensating_controls>`; `- Technical feasibility (holds, bet, unknown or blocked; note the known limits): <grade>. <note>`; `- Organizational feasibility (holds, bet, unknown or blocked; note who must staff, agree to or sustain the change): <grade>. <note>`.
14. **Writing.** The tool replaces the content under the patch's "Risk and threat-model delta" heading, up to the next level 2 heading, with a blank line, the Markdown sections and the YAML block, and a blank line. When the heading is missing it is added before "Feasibility note". The recorded YAML block is the first fenced yaml block under the heading that parses to a mapping holding `impact_report`; a block that does not parse is skipped. It is the source of the judgment: when it holds one, the tool keeps its `judgment` lines verbatim, so filled slots survive byte for byte, and renders the Markdown Judgment section from it. The judgment lines are the line `  judgment:` (two spaces of indent) and every following line of the block indented by three spaces or more, or blank, with trailing blank lines dropped; they replace the generated judgment lines at the end of the block. A recorded feasibility grade outside holds, bet, unknown and blocked (FILL aside) is IR-E-grade in every mode, and nothing is written. The tool raises it after regenerating, so the run also raises every warning regeneration raises, and the JSON report keeps `impact_report` and `markdown`.
15. **Facts, stamp and wording.** Comparing a recorded block with a regenerated one ignores `judgment`. The stamp is the two model hashes and `layout`; a recorded block with no `layout` key is layout 1. The edition-authored wording keys are `reasons` (separations), `triggers` (should-never codes) and `rule` (separations): their text belongs to the edition, never to the patch, and is not a fact. Team names are wording too, at each position where both blocks carry a team id (IR-22): a position is a separation id, a side and an index in that side's list, and both blocks' `team_ids` hold a non-null id there. At such a position the id is the fact and the name is not compared as a fact. At every other position the name is the fact, and the ids there are not compared at all; a block with no `team_ids` on a separation compares that separation's names only. Every other key is a fact. Facts are compared by parsed value with the wording keys removed and the order of every list ignored. When both blocks have the same layout, every key either block holds is a fact, so a key only one block holds is a differing fact: a block written with a profile holds `teams`, and regenerating it without the profile drops them, which is stale. When the two layouts differ, only the facts both layouts hold are compared: the top-level keys both blocks have and, at every depth, the keys both blocks use there. "The keys a block uses there" is, for each path with list positions merged (so every item of a list shares one path), the union of the keys that block's mappings at that path hold; a key is compared when it is in both blocks' unions for its path (so a key a later layout added, such as `placement` or a relationship's `content`, is left out), and the unmapped plane is read as one value whether written `unmapped` or `unmapped:<id>`, and a unit row's `separates` pair `[a, b]` (layout 1) as the string `a and b`. A layout number changes whenever this specification changes the block's keys, their meaning or their text layout.
16. **Check mode** (`--check`): regenerate, compare with the recorded block, and write nothing. Regenerating raises every warning a writing run raises (IR-W-tier-missing, IR-W-unbuilt, IR-W-mark-lost and the rest), so check mode reports them too. A missing block, or any fact that differs, is IR-E-stale; when the recorded block holds team names and no profile was given, the message says to run check mode with the profile the block was written with. A recorded block that differs from the regenerated one only in list order, with the same stamp, matches: check mode raises neither error. When the facts agree but the stamp or the wording differs, it is IR-E-restamp: the models changed (an earlier patch was edited, or the edition was upgraded), or the edition changed the layout or its wording, but this patch's delta did not. A patch whose Status starts with `rejected` or `withdrawn` is never applied, so check mode skips it: it raises IR-W-skipped, compares nothing and exits 0. Each slot still `FILL` (the two notes and two grades count separately) raises IR-W-unfilled.
17. **Regenerating an accepted patch.** A stale section is fixed by running the tool again, which rewrites it. When the patch's Status is accepted and a recorded block exists whose facts differ from the regenerated ones, the tool still writes, and raises IR-W-reaccept: the patch goes back through acceptance (set its Status to proposed, review the new delta, accept it again). When only the stamp or the wording changed, the tool writes with no warning, and the acceptance stands. A first generation, with no recorded block under the heading yet, raises no IR-W-reaccept: there is no earlier delta to differ from, even for an accepted patch.
18. **Placement.** Compare the compiled overlay before the patch with the one after it (Inputs). A part's account class is the `account` of its entry under the overlay's `elements`, or none. List every element of the base or after model whose account class differs, an entry added or dropped included, with `from`, `to` and `enforces_rule` (the part is in `rule_enforcing_parts.parts`), in natural order of id. A removed element is included: removing it drops its overlay entry, so it is listed from its class to none, and it counts in the Summary's placement clause. Its `how_touched` stays `removed` (behavior 4). An account class is a key of the overlay's `account_classes`; its text is that key's value, and its zones are the keys of `zone_accounts` whose list names it, in natural order. List each account class present only after (`added`), only before (`removed`), or in both with a different text or zones (`changed`), in natural order of name, with its text and zones before and after (null and `[]` where absent). A part whose account class changes is touched (behavior 4), so its marks, separations, scenarios, quality, codes and units are reported like any other touched part's.
19. **Untrusted-content exposure.** Compute the exposed parts of the base and the after model with the model checks' propagation rule: seed with the target of every relationship whose `content` is `untrusted`, whatever its kind; then, to a fixed point, a relationship of kind data, inference, feedback or observation whose source is exposed and whose `content` is not `structured` exposes its target. An exposed part's `via` is every relationship that exposes it in that model: marked untrusted, or propagating from an exposed source. `gained` lists parts of the after model exposed after and not before, with their `via` in the after model; `lost` lists parts of the after model exposed before and not after, with their `via` in the base model. Both in natural order of id; `via` too. An exposure that stays gated is still listed: the section reports reach, the model checks judge it.
20. **Accepter.** In every mode (writing, check and print), with a profile, a patch whose Status starts with `accepted` raises IR-W-accepter when the profile's `separation.security_risk_owner_role` is missing, empty or `FILL`: the role that accepts patches is not named, so nobody named could have accepted this one.

The finding-kind touched selector reads only `closure_check.judged_by`, not `held.judged_by`. A profile team value that is empty, blank or `FILL` is unset: write null in `teams` and `not set` in Markdown. The unit-pair separation selector uses `building_touched` rows for parts retained after the patch; a unit building only removed parts has a `building_removed` warning but supplies no such pair selector. The Summary exposure sentence uses the literal wording in its output template. `requires_ops` is a fixture prerequisite: skipped cases are reported and never counted as passing.

Known limitations: the separation selectors may over-include; codes that depend only on profile values surface only through separations and cards; the caller declares the starting model and layer baseline, whose patch history the tool does not infer; exposure gained far from the patch is listed but does not make the exposed part touched.

## Errors, warnings and exit status

Message shape: `<level> <code> <location>: <text>`, for example `error IR-E-apply O03 op 4: unknown element s3.approval-svc`. The location is the patch id (with `op <i>` for an op error), an input file name for an input error, the bare patch id for a message about the patch as a whole (IR-W-empty, IR-W-accepter, IR-W-reaccept, IR-W-skipped, IR-E-stale, IR-E-restamp), an element, unit or scenario id for a warning about it, or `<patch> judgment.<slot>` for a slot, where `<slot>` is the dotted path under `judgment` (`O01 judgment.attacker_gain`, `O01 judgment.technical_feasibility.grade`); IR-E-grade and IR-W-unfilled both use it. An input error is located at the file's base name as the tool knows it: the edition data file (`rules.yaml`, `model.yaml`), the overlay file as the version record names it (`overlay-hybrid.yaml`), `overlay` for an overlay given as an option that is not the recorded file (the recorded file keeps its recorded name however it was found), `version.yaml`, `org units.yaml` for the organization's units file, `profile.yaml`, or `patches` for the patch directory; a reused unit id at that id, a patch id with no file at that id, and a bad option or preview withdrawal at `options`.

| Code | Level | Condition |
|---|---|---|
| IR-E-ops | error | the patch under report has no fenced yaml ops block, more than one, or one that does not parse as a mapping with a list under `ops` |
| IR-E-apply | error | an op in this or an earlier included patch fails to apply (located `<patch> op <i>`, or at the bare patch id for a failure no op owns, such as a reference left dangling at the end of the patch); or an earlier included patch's ops block cannot be read for one of the IR-E-ops reasons (located at that patch's id) |
| IR-E-input | error | a data file missing or not parsing, `rules.yaml` without `rule_enforcing_parts.parts`, an overlay the version record names that is missing or no longer matches its recorded sha256, an organization units file that is not a mapping of lists, an `add` in that file reusing a unit id (located at that id), a patch id that matches no patch file, or a preview withdrawal naming no earlier patch |
| IR-E-stale | error | check mode finds no recorded block, or a fact that differs |
| IR-E-restamp | error | check mode finds the facts agree and only the stamp (model hashes, layout) or the edition's wording differs |
| IR-E-grade | error | a feasibility grade outside holds, bet, unknown, blocked |
| IR-W-empty | warning | the patch changes no element, relationship, contract, finding kind, placement or account class, even if it changes a failure scenario |
| IR-W-scenario-orphan | warning | a scenario names a removed element |
| IR-W-tier-missing | warning | an added element needs a tier |
| IR-W-unit-orphan | warning | a unit builds a removed element |
| IR-W-unbuilt | warning | an added element has no unit |
| IR-W-mark-lost | warning | a touched element loses a mark |
| IR-W-unfilled | warning | check mode finds a slot still `FILL` |
| IR-W-reaccept | warning | rewriting an accepted patch whose recorded block holds facts that changed |
| IR-W-skipped | warning | check mode on a rejected or withdrawn patch, which it skips |
| IR-W-accepter | warning | an accepted patch, with a profile whose `separation.security_risk_owner_role` is not filled |

Exit 1 on any error, else 0.

## Acceptance fixtures

If the environment denies the required `trash` cleanup of a fixture scratch folder, report that denial and the retained path separately from fixture assertions. Preserve the fixture result and exit status based on assertions; do not substitute another deletion mechanism or count a skipped case as passed.

Concrete input ids, names, prose, profile values, hashes and exact graph counts in these fixtures are supplied test vectors. Apply the rules to those inputs; do not hardcode fixture identities or infer organization facts from expected output.

Each fixture is the shipped data plus the patches described, unless it brings its own data or a compiled layer.

The fixtures ship as one file, `fixtures-impact-report.yaml`, a mapping whose `fixtures` key lists one entry per row below and whose `namespace_reports` key supplies the namespace cases described under Namespace identities. A runner must understand these keys, and a fixture holding any key the runner does not know fails.

- **Fixture keys.** `name`, `description` and `source` (where the expected result came from; not checked). `files`: path to content, written into the fixture's own organization folder (a string as is, a mapping as YAML); patches sit under `patches/`, and `profile.yaml`, `version.yaml`, `units.yaml` and overlay files sit at the top of the folder, beside `patches/`. `data`: file name to content; when present, these files alone make up the edition directory for the fixture, in place of the shipped data. `layer`: for each of `realization`, `quality` and `failures`, entries merged into that file of the edition data (into its `elements` mapping, or appended to the failures file's `scenarios`), written whole to a layer folder that is passed as the layer option. `requires_ops`: op names the tool's op core must have; a tool that lacks one reports the fixture as skipped, and a skipped fixture does not count as passed.
- **How a fixture runs.** Once, with `options` and `expect`; twice, with `runs: 2`, `options` and `expect`; or as `steps`, a list run in order, each item either `{run, expect}` or a `replace` holding `{file, from, to}`: an edit to a file of the organization folder whose `from` text must occur in it exactly once (otherwise the fixture fails). Every run and edit of one fixture works in the same folder, so a later run reads the patch an earlier run wrote; with `runs: 2` the second run reads the patch the first wrote.
- **Run options** (`options`, or a step's `run`): `patch`, the patch id; optional `check` and `print` (true for check mode or print mode), `overlay` (an overlay file path, relative to the organization folder), `preview_withdraw` (a list of patch ids, one preview withdrawal each) and `no_profile` (true to run without the profile although `profile.yaml` exists). The runner runs the tool from the organization folder with the edition directory, `patches` as the patch directory, the profile option set to `profile.yaml` whenever that file exists and `no_profile` is not set, the layer option when the fixture has `layer`, and a JSON report path. The version record and the organization units file are found by the tool's own defaults, beside the patch directory.
- **Expect keys.** Every key given is checked. `outcome` is `ok` for exit 0 and `error` otherwise; `exit` is the exit status. `errors` and `warnings` list every message of that level, compared as a multiset with order ignored: an entry is a code, or `{code, location}`; each entry consumes one matching message, and a message left over fails the fixture. `report` is a partial match on `impact_report`: a mapping checks only the keys it names, at every depth; a list of scalars must equal the reported list, in order; a list holding mappings or lists must have the same length and match item by item. `report_contains` is the same, except that every list, at any depth, matches when each expected item matches some reported item, and an expected empty list requires an empty list. `codes` maps a code to its basis, and the code must be in `should_never_codes` with that basis; `codes_exclude` lists codes that must be absent. `sections_none` lists sections whose body is exactly `None.`. `markdown_contains` lists strings that must occur in the JSON `markdown`, block included. `markdown_equals` is the Markdown sections alone: the JSON `markdown` from its start through the line break that ends the last Judgment line. The blank line that follows it and the block are not part of it, so the text ends with exactly one line break. `yaml_equals` is the block's text between its opening and closing lines (a final line break in the expected text is ignored). `message_lines` are the printed lines that start with `error ` or `warning `, exactly and in order; `json_keys` the JSON report's top-level keys, in order. `no_report` is true when `impact_report` is null and the patch file is unchanged; `patch_unchanged` is true when the patch file has the same bytes before and after the run, and false when its bytes differ; `patch_contains` lists strings the patch file holds after it. `outputs_byte_identical`, with `runs: 2`, is true when both runs leave the same patch file bytes and write the same JSON report bytes.

Two message texts are fixed, because the exact-output fixture prints them: IR-W-tier-missing reads `an added element that needs a quality tier and has none` and IR-W-unbuilt reads `an added element that no work unit builds`. Other message texts are free; their codes and locations are not. An op error's location counts ops from zero (`O01 op 0`), and a preview withdrawal naming no earlier patch is located at `options`.

## Not in scope

Deciding whether a rule is broken (model checks and profile checker); filling judgment slots; drafting exceptions; applying ops for the organization (patch applier); compiling the design layer (patch applier); changes to the profile alone; the work-unit graph (unit graph tool).

For default file lookup, both the version record and organization units sit in the parent directory of the patch directory: for `patches/` they are `version.yaml` and `units.yaml`; for `org/patches/` they are `org/version.yaml` and `org/units.yaml`. Report `patch` uses the file stem; message locations use the bare patch id. The core natural ordering tie is U-1, U-01, U-001. A direct code retains the first card declaring it even though its basis is direct.

## Namespace identities

- **IR-25** Read the actual composition's model, layers, failures and units. Match and report the full identity of every part, relationship, contract, failure and unit. Preserve `jig:`, `ratchet:` and `shared:` prefixes. A colon inside an id is part of that identity. Shared systems such as `shared:PEOPLE` and `shared:EXT` retain the same plane and external-system meaning as their bare vocabulary names. When `seams.yaml` sits in the data folder, load it alongside the model and pass it through the patch core so shared crossing and exception ops have the same meaning as in the applier. Merge each namespace's failure records, including the tests attached to shared contracts and premises, into the composition's failure input.

The fixtures file's `namespace_reports` runs on the edition's already composed model and its shipped layers, failures and units, with `seams.yaml` loaded through the shared patch core. Import only missing full identities; preserve existing composed records. Merge attached scenarios as TG-14 defines. Write the target ops into one proposed organization patch. When earlier_ops is supplied, write those ops into an earlier accepted patch. Run print mode with a JSON report. Each case supplies `ops`; `changed_elements` and `changed_relationships` require exactly the changed identity lists; `scenarios` requires the listed full ids as a subset of the reported scenarios, allowing other scenarios. Run each case twice and require identical bytes.

Shared mode accepts `--shared <file>` and optional `--org <file>`. Load the explicit shared file first, otherwise seams.yaml in the starting layer folder, otherwise seams.yaml in the data folder. Pass shared, root exceptions and each patch's acceptance into the same patch core used by the applier. Carry its updated shared and organization documents through earlier patches to the target. Accept `set_seam_exceptions`, `set_seam_exposure` and `jig:` or `shared:` additions with the applier's namespace grammar. The report writes no shared or organization input. `--edition` is an alias for `--data`. Full identity matching and errors are identical in either spelling.

Compute before marks, including the T0 mark, from the layer before the target. Compute after marks and planes from the layer after the target. Removing a part retains its earlier tier in the lost marks even though its layer entry is gone from the result.

Namespace fixtures may additionally provide `earlier_ops`, applied in one accepted patch before the target, `planes`, a mapping from added endpoint id to its expected after plane, and `explicit_shared`, which selects the explicit shared option and edition alias. The target remains O02 when earlier_ops is present. Require changed identity lists to equal their expectations, and check each plane against a reported plane join. These fixtures include a prior exception op and a namespaced organization part whose realization is supplied in its add operation, so neither a bare-id patch copy nor an already patched layer can pass.

## Namespace fixture assertions and scenario changes

Namespace case keys are name, ops, changed_elements, changed_relationships, added_elements, scenarios, earlier_ops, planes and explicit_shared. Require exit 0. Run twice and compare both standard output and JSON bytes. Write all six patch sections with a matching title and status. The target is proposed O01, or proposed O02 after accepted O01 when earlier_ops is present. The accepted status names an owner and calendar day. added_elements equals the exact ids under elements.added. changed_elements and changed_relationships equal the exact corresponding changed lists. Scenario assertions are subsets. For each planes entry, require a plane join whose from and from_plane match the entry, or whose to and to_plane match it.

When interpreting system vocabulary in IR-9 and behaviors 6 and 11, compare the bare name EXT, PEOPLE or S4 after removing a namespace prefix. Preserve complete identities in the result. The trigger phrase `(control or execution zone)` in model.ai-free-control-plane is literal text. In check mode without a recorded block there are no recorded judgment slots, so no IR-W-unfilled warning is raised.

Replay add_failure_scenario and modify_failure_scenario through the patch applier core. Include each added or modified organization scenario in failure_scenarios even when the patch changes no element. Report its invariant and test kind, and the union of its before and after named parts as touched_elements. For ordinary scenarios retain the existing touched-part selection. A modified scenario uses its after definition. A retired scenario stays visible for orphan reporting. This report declares affected tests and never attests their execution.
