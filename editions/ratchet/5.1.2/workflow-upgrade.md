# Upgrade

Take in a new edition without losing the organization's answers or its patches.

1. Check that the held edition is supported. Editions before the base edition require a fresh start from the base. The upgrade refuses them with `version.unsupported`. Apply the held patches and run the model checks, profile checker and unit graph with the held edition's own verified tools. For an edition without a bundle, prove those tools against its specifications and fixtures. Fix what fails first.
2. Read every new changelog entry between the held and target editions. Read the renames and changed meanings, then verify the new bundle and run the upgrade once. Rename nothing by hand. For a Jig re-pin, keep both pinned edition folders under `pins/jig/`, with their recorded hashes. The upgrade validates the files and applies the successor Jig's renames to qualified organization references. Shared-layer changes are compared on their `shared:` identities.
   A changelog item that names a field of a contract, such as `finding_kind` on `FindingDisposition`, describes a record the running loop writes. No profile field holds it, so nothing in `org/` changes for it. Hand it to the people who run the loop, and record the new field in the map or the decision log when the organization starts writing it.
3. Put the new edition in place of `upstream/`, keeping the old one until the upgrade is accepted.
4. Verify every file and run all fixtures in the new bundle (`workflow-build-tools.md`). The upgrade tool includes this edition's model checks. If the organization uses homegrown tools, rebuild changed tools and prove every required fixture. Build the model checks before the upgrade tool and rebuild the upgrade tool whenever its checks change. A homegrown build carries no compatibility promise.
5. Run the upgrade tool (`spec-upgrade.md`). First it applies every intermediate version's renames to `org/profile.yaml`, the unit changes, the organization's own overlay and identifiers inside the patches. It re-applies the patches on the new model and layer, compiles the layer with the overlay `org/version.yaml` records (the shipped example when none is recorded), and runs the model checks after each patch. Each patch is reported as clean, renamed, applies-with-findings or conflicted, with the changelog entry that explains a conflict. A patch is judged at the end of its fix chain: an error it adds counts against it only if it is still present after the last later patch that depends on it, directly or through others, so a patch whose errors a dependent correction removes is clean and lists each such error as `resolved_by` that patch.
6. Check what the upgrade tool does not. It renames the unit changes and runs no unit check. It compares model-check errors; read the remaining warnings by running the checks in its output directory:
   - Run the patch applier with `--layer-out` and the model checks on the result (`workflow-change-design.md`, Check it), and read the warnings. A patch the applier refuses stops the run with no model written (for example a conflicted patch); name it with `--preview-withdraw <id>` to check the others while it is being revised.
   - Run the unit graph on the renamed `units.yaml` against the after model, and the status report when the organization keeps one. Fix what they refuse before step 8 (the units file, in step 7).
   - A protected evidence-store removal may first conflict because the successor changed `r042` and `r071`. Reopen the same patch and id, restate its removals against the successor and preview it before a person accepts again. With no partitioned replacement it applies with `evidence-unpartitioned` as an error; decide where the records land.
   - Read the report's voided closure sign-offs and the emitted grid. A reworded shipped rule invalidates the old mark; its cells are proposed unless another valid mark reviews it. Review the successor wording before replacing the hashes and signing off again. Keep the closure files when promoting the output.
7. Act on every result that is neither clean nor renamed, and on every finding from step 6:
   - **Conflicted** (any code but `conflict.enforcement-change`, which has its own item below): from `conflicts/O<NN>.md`, draft a revised patch that keeps the organization's intent on the new design, for a person to accept again. The tool never changes what a patch means. Revise the conflicted patch itself by the reopen path of `workflow-fix-patch.md`: the same file and id, Status back to `proposed`, the ops rewritten on the new design. A reopened patch is proposed, so the applier leaves it out and the output carries none of its intent until a person accepts it again by that path (regenerate its risk section, run the checks with `--preview <id>`, then `workflow-change-design.md`, Accept it, and record the new acceptance in `org/decision-log.md`). The ids it added, and every record that cites them, then stay as they are. Write a new patch and withdraw the original only when the organization's intent itself changed. A correction that lists the conflicted patch in `depends_on` does not work here, because the conflicted patch no longer applies. Give each modify op in the revised patch `expects`, hashed from the new edition's value (`spec-patch-applier.md`, Declaring what a modify replaces), so that the next upgrade or a later patch that changes the field stops the patch loudly.
   - **A field the new edition changed:** the upgrade tool reports `conflict.changed-upstream`, with the held, new and patch values of each key, whether or not the op carries `expects`. Its pre-checks compare each key a modify op sets or unsets between the held and the new edition before the applier runs, and the applier runs only when no pre-check found a conflict, so for a field the edition changed `expects` is never reached. That includes a value that differs only because this upgrade renamed an identifier inside it: the two editions' values differ, so the patch reports `conflict.changed-upstream` even though the rename changed nothing it meant. Revise the patch as for any conflict, restating the new value where the patch should keep it, and hash the new value.
   - **A refused `expects`** (`conflict.invalid` with applier code `op.expects-mismatch`): the field is the same in both editions, but an earlier patch of the organization's, or an earlier op in the same patch, changed it after this patch's hash was taken, or the hash was computed wrong. Read the field's value as the earlier patches leave it, restate in the revised patch whatever of it should survive, and hash that value.
   - **Adding `expects` to an accepted patch that has none:** this changes the patch's ops, so it goes through the reopen path of `workflow-fix-patch.md` (Add `expects` to an accepted patch).
   - **A correction patch the upgrade wrote** (`written_by_upgrade: true`, `patches/O<NN>-upgrade-<version>-mechanical-fixes.md`): it holds only the two mechanical fixes, the broker's administrative session for a control-zone part the organization added and the removal of a shipped reason beside partition keys the organization added, and the run applied it as a preview, so each error it fixes is listed as resolved by it. Read it, then generate its risk section with the impact report and fill the judgment slots, as for any patch (`workflow-change-design.md`, Check it, step 4), whatever the upgrade wrote under that heading. Then have a person accept it with the rest of the promotion (`workflow-change-design.md`, Accept it). Until its Status line says accepted, the applier leaves it out and the errors return.
   - **A judgment call** (a finding with `sort: judgment`): the findings report says what a person must decide. The upgrade never names a clearing, writes a partitioning reason, draws a restore grant, declares a broker, writes a measure (`measures`), draws a feedback relationship, writes partition keys, names a contract a relationship carries, adds a consumer to a restricted contract, or writes a `harness` key or a `not_harness` reason on the organization's behalf, because each of those asserts a control the checks cannot see. Draft the correction with that person's answer.
   - **`conflict.enforcement-change`:** the patch takes shipped items (its `items`) out of what a rule judges (its `target` set and `rules`), so the rule would pass them unjudged. Nothing the organization accepts locally clears it, since the change lowers what the edition enforces. The guard judges only items the patched model still holds, so a part or relationship the patch removed never counts; the report lists it on that patch under `removed_from_judged`, which a person reads before accepting the patch. A removal still counts when a part that stays in the model leaves a set because of it, such as the readers of a removed exposed store. The guard also covers untrusted fields, typed fields, held declarations, evidence custody, restricted audiences, coding-agent controllers and seam crossings. Restore a shipped item that left scope or send the case upstream. Replacing `fields` blocks only when the replacement drops a judged field or its untrusted mark; retaining them is allowed. Revise the patch to keep the items in scope and declare the organization's design the way the rule reads it (`workflow-change-design.md`, Check it), or, when the edition itself is wrong for the organization, send the case upstream (`workflow-send-upstream.md`) and keep the patch out until an edition carries the change.
   - **Applies-with-findings:** from `findings/O<NN>.md`, write a correction as a new proposed patch that lists the original in `depends_on`, often giving the organization's own parts the layer entries the new edition expects; once it removes the errors, the original is judged clean. Or withdraw the original (`workflow-fix-patch.md`). A patch with findings is not done just because its ops apply.
   - **`checks.baseline` warnings:** the new edition fails the checks before any patch, which means the organization's own overlay lacks something the new edition needs, usually a part upstream added. Place it with a patch (`set_layers` with the part's `overlay` entry), never by editing the recorded baseline file.
   - **`overlay.unrecorded-file` warnings:** the upgrade did not read that overlay file, so every part was placed by the record or, with no record, by the shipped example. If the file is the organization's real placement, stop: record it as the baseline (`workflow-start.md`) and run the upgrade again before promoting anything.
   - **The units file:** an `add` whose id is already a unit, shipped or added earlier in the same file, is refused by the unit graph, the impact report and the status report, and while it stands the impact report writes no risk section for any patch. Fix the units file before step 8. Move each such change to `modify` with the unit's id, and set only the keys the organization changes: `modify` replaces each key it sets whole. Before setting `requires`, `provides`, `separates`, `entry_checks` or `elements`, read the unit as the new edition ships it (its entry in the new `units.yaml`, or its row in reference R4) and compare it with the held edition's: the set list must carry every entry the shipped unit now has, plus the organization's own. Restating the whole held unit drops anything the edition added to it. The upgrade tool has no `changed-upstream` check for units, so this comparison is the only place a dropped prerequisite shows.
   - **New parts and the organization's own overlay:** an organization with its own overlay places every part the new edition adds (the changelog's Added list), or the baseline check reports it (`checks.baseline`, finding `overlay-missing`). Place each with a patch, `set_layers` with the part's `overlay` entry: account, services, fit, portability, and `keeps` for a part that enforces a rule, which every part in the control zone does.
   - **Old wording and unknown profile fields:** reword the prose the report lists, and move or drop each field the new schema no longer defines.
   - **A profile entry the new edition reads as its own field:** when the changelog says a new field's name may collide with one the organization already used for its own purposes (a key, or a dial id, which is a value the upgrade tool never treats as a key), rename the organization's entry in the output's `profile.yaml` before running the new profile checker, for example with an `org_` prefix. Renaming a profile key or dial id is a profile edit: no patch carries it, since patches change the design, and `renames` lists only what the edition renamed. Record it in `org/CHANGELOG.md` with what the entry means.
8. Regenerate the risk sections (`workflow-fix-patch.md`, Regenerate stale risk sections), once the units file passes; the impact report refuses to run on any patch until it does. A restamp needs no new acceptance, and that includes a change to the section's layout alone; a stale section, or `IR-W-reaccept`, sends the patch back through acceptance. Give check mode the same profile every time. New work units and failure scenarios that name a part a patch touches add rows to its section, so expect stale sections after an edition that adds them even when no shipped unit changed. While a patch is reopened for re-acceptance, the applier refuses every accepted patch that depends on it (`depends.unmet`) and writes no model, so re-accept patches in dependency order, and name a reopened one with `--preview <id>` to check the others meanwhile.
9. Where a version changed a rule's meaning or a profile field's requirements, run the profile checker and readiness again, and walk the person through what changed.
10. Check the tailored narrative against renamed terms and changed meanings; update the premise ledger where a premise moved. Rebuild table APX-2.1's cells from the new edition's rows (`workflow-tailor-narrative.md`), including cells whose citations changed while their text did not.
11. A person promotes the output directory into `org/`: the profile, the patches, the unit changes, the overlay and `version.yaml`, whose overlay record must match the promoted overlay file byte for byte. The upgrade tool wrote the record as `<new upstream version>+<org>.1`, with `n` at 1. Every act after the run that raises the version raises `n` by one, in the output directory before promotion as in `org/` after it: each patch accepted or withdrawn (the correction patch the upgrade wrote and each revised patch included) and each change to the profile. So the record a person promotes reads `.1` only when nothing was accepted, withdrawn or changed after the run; with the correction patch and two revised patches accepted first, it reads `.4`. Add an entry to `org/CHANGELOG.md` that cites the promoted version and says how each conflict and finding was resolved. Each patch accepted after promotion raises the version as usual.
   A patch reopened in step 7 may be promoted while it is still `proposed`. Nothing makes it accepted again but a person: the upgrade tool never changes a Status, and promotion copies the patch as it is. Until it is accepted again, the design in force carries none of its intent, so the `org/CHANGELOG.md` entry lists each reopened patch as open and says what the organization's design does not do until it is accepted. Accept it again by the path in step 7, in the output directory before promotion or in `org/` after it: regenerate its risk section, run the applier and the model checks with `--preview <id>`, then `workflow-change-design.md`, Accept it. Record the acceptance in `org/decision-log.md`; like any acceptance it raises `n` by one. Withdraw it instead (`workflow-fix-patch.md`) when the organization no longer wants the change. The upgrade is complete when every reopened patch is accepted again or withdrawn; until then, tell the person you work with which patches are still open.

When a checker a step needs is missing, or has not passed its fixtures on the edition in question, the item it covers is unchecked. Say so plainly to the person you work with, record it in `org/CHANGELOG.md`, and promote nothing on it: an upgrade whose profile or patches went unchecked waits until the checker is built (`workflow-build-tools.md`).

If a major version changes something the organization relies on, that is a conversation for the decision owner before the upgrade is accepted.

Keep the held dependency at `held/pins/jig/` and the successor dependency at `new/pins/jig/`, the same layout used by startup under `upstream/pins/jig/`. Verify the pinned edition records and equality of each dependency's shared bytes with its containing edition before applying re-pin renames.

## Shared agreement owners

Before changing a shared contract, its quality entry or a shared premise, load its per-side `owners` records from the organization's dependency layer, even when adopting one design alone. The edition supplies roles and null identities; the organization binds each role to an identity with an identity-only change accepted by those identities. Keep every side, including absent designs. For a later content change or reassignment, record `acceptance` with `accepted: true` for each before and after identity. A role label alone, a missing identity or false acceptance is refused by MC-114. During an upgrade, retain those bindings only while their sides and roles still match, and obtain both former and replacement owners' acceptance when they change.
