# Reference R3: Quality, dials, failure scenarios and metrics

*Ratchet: closed-loop security validation for AI-assisted engineering. Reference R3. Edition 5.2.0, Thesis 1.4.3, 2026-10-31, build 5842e9bf+local.*

<a id="r3-quality-tiers"></a>
## Quality tiers

| Tier | Intent | When a dependency fails | Default availability |
|---|---|---|---|
| **Control safety** | Authorization, grants, credentials, audit and live prerequisite checks. Wrong answers are worse than no answer. | fail closed | 99.9% monthly (unavailability blocks actions, never permits them) |
| **Evidence integrity** | Intake, verification, disposition, ledger, evidence and closure. Losing or altering evidence is the failure that matters. | queue and retry | 99.5% monthly |
| **Orchestration** | Requests, workflow, dispatch, test-drafting agents, context build and model access. Delays are acceptable; duplicate or phantom effects are not. | queue and retry | 99.5% monthly |
| **Best effort and analytics** | Evaluation, telemetry, sampling and dashboards. Gaps reduce what can be claimed; they never change what can be done. | continue without | 99% monthly |

## Critical paths (design estimates, not measurements)

| Critical path | What must answer | When a part is down | Availability (design estimate) |
|---|---|---|---|
| **Approve and run one test** | 10 parts must answer, 2 co-deployed units | nothing runs; the request waits | 99.75% against a 99.90% target (about 108 minutes a month); 99.05% if the co-deployed parts fail independently |
| **Record and verify evidence** | 2 parts must answer | evidence waits in the outbox; nothing is lost | 99.00% against a 99.50% target (about 431 minutes a month) |
| **Regression gate in the deploy path, blocking mode** | 4 parts must answer, one co-deployed unit; given the pipeline reached the stage | the stage applies its pre-decided posture | 99.90% against a 99.90% target; 99.60% if the co-deployed parts fail independently |

<a id="r3-a-regression-gate-s-outage-behavior"></a>
## A regression gate's outage behavior

- **applies to:** The regression stage that s6.enterprise-adapters places in each owning service's pipeline.
- **failure mode:** posture-from-policy
- **dependency grain:** A regression test declares its dependencies at this grain: the artifact digests it exercises, each library it exercises at its resolved version, each configuration key it reads, each policy id and each identity. A change touches the test when it changes any of these; a change to the service's deployable alone touches only tests that declare that artifact's digest. A declaration that names only the deployable makes every deploy of it a replay, so the test costs its full time on every deploy and saves nothing by scoping.
- **scope when unavailable:** Only deploys that touch a regression's declared dependencies (artifact, policy, identity) are subject to the posture, reusing the dependency-scoped invalidation rule. Every other deploy proceeds while the gate is unavailable and is recorded, with its replay owed after recovery only if a later check finds it touched a dependency.
- **core posture defaults:** Fail-closed when the demonstrated path reaches a crown-jewel or critical asset; fail-open-with-record for standard. Ship-through on a critical or crown-jewel path is a short-lived acceptance by the business risk owner with security risk owner concurrence. A path reaching the ship-through renewal cap (default 2 consecutive acceptances, a dial) refuses another until its posture review, fed by gate outcomes, is recorded. Profiles may override with attribution.
- **unknown consequence:** No core default. Each organization profile must set unattested_default (crown-jewel | critical | standard); the unattested count is reported as a register-gap metric. truly unattested assets should be rare, because someone in the organization usually knows roughly how critical an asset is.
- **service level owed to service teams:** availability: 99.9% during the service's deploy windows (default), given the pipeline reached the stage; composed in critical_paths.deploy-gate from the execution cell alone, counting the four co-deployed cell parts as one unit; if they fail independently the same path composes to about 99.6%, and phase 2 measures which holds; the figure excludes the staging target's own availability; added deploy latency p95: 10 minutes (default; the organization sets it in its profile, gate_failure_policy.added_latency_objective_minutes, beside the regression time budget dial, also 10 minutes by default). The stage stops waiting at the budget and applies the posture; an objective below the budget is refused unless the organization records dependency-scoped or post-deploy handling; blast radius: an outage holds only deploys inside a regression's declared dependency scope; the program reports how many deploys an outage held and how many it let through; decision: the program publishes this SLO and reports against it monthly; breaching it is a program incident

<a id="r3-availability-assumptions"></a>
## Availability assumptions

Each path figure multiplies the default availability of every part the path waits on, counts parts deployed together as one unit, and assumes parts fail independently. Counting co-deployed parts as one unit is a modeling convention: where a path has them, the table also gives the figure if they fail independently, and phase 2 measures which holds. External dependencies are assumed:

- Identity provider (outside the design): 99.95%, assumed: enterprise identity provider; set in the profile's infrastructure_dependencies

<a id="r3-operating-ratchet"></a>
## Operating Ratchet

- **on call:** control plane: control-plane operator; orchestration and cells: platform operator; evaluation: evaluation engineer
- **runbooks:** Every failure scenario has a runbook RB-<scenario id>, owned by the on-call role of its first part; the model check refuses a scenario without one.
- **game days:** Every game-day scenario runs at least twice a year; control-plane region loss and key compromise at least once a year.
- **change freeze:** A burned error budget freezes Ratchet's own policy and software releases until the budget recovers or the security risk owner records an exception; product deploys are never frozen by Ratchet's budget. Two kinds of change still release during a freeze, each recorded with its direction and still through the deny-diff, the policy unit tests and the staged rollout: a change whose deny-diff newly allows nothing (a narrowed limit, a revoked policy, a removed allowlist entry) and a security fix to Ratchet's own parts.
- **postmortems:** Each of these triggers opens a postmortem, decided before any incident: an effect outside an approved scope or with no approval; a closure contradicted by a later confirmed escape on its path key; evidence lost or unreadable; one incident using more than 20% of an objective's error budget over its rolling window; the loop canary's dead-man alarm; a seeded proposal or seeded change that reached execution or merged; and a request from any role. The on-call role of the first failing part owns it. The review is blameless: it states contributing causes as conditions of the system, never as a person, and turns each action item into a design change, a profile change or a work unit with an owner. The security risk owner reads and signs each one, and an open postmortem stays on the status report until every action item has landed or been declined with a reason.

## Metrics

Untested leads never count as false; associations with delivery metrics are correlational, never causal.

### Tool metrics

| Metric | Definition |
|---|---|
| lead yield | Share of sampled leads the loop demonstrates when tested, per tool, rule family and tool class. Untested leads are outside the sample and never count as false. |
| miss rate | Demonstrated paths inside a tool's declared scope that no lead from that tool pointed at, per tool class. |
| review claim contradictions | Threat-model and review invariants contradicted by a demonstrated path, per review practice. |
| developer queue toil | Leads reaching developer queues per service-month and triage hours per item, before and after the confidence bar. |
| delivery impact per tool | Side-quest metric. Direct: stage time and queue time attributable to each tool gate, deploys blocked or delayed by the tool, developer triage time per lead, all from pipeline timings and tracker data. Associated: DORA's five metrics (change lead time, deployment frequency, failed deployment recovery time, change fail rate, deployment rework rate) by tool configuration, reported as correlational, never causal, with the comparison set named. Only metrics the profile lists as collected. |
| held lead sample outcomes | Demonstration rate among sampled held-back leads; a rise means the bar is too high. |
| typed route calibration | Per typed route and decision type, on the organization's sampled ground truth: expected calibration error over ten equal-width probability bins, and its one-sided 90% upper confidence bound from a basic bootstrap over the labeled sample, which also removes the estimate's upward bias at small samples. A route qualifies for a decision type when the bound is at or under typed_route_max_calibration_error and it has at least the labels the dial register lists for that ceiling. Below that count the report says sample too small, the type stays on its declared fallback, and nothing is said about the model. Typed routes pay off where labels are cheap and plentiful, such as lead triage at high volume, and rarely where reproduced outcomes arrive a few dozen a quarter. |
| catch layer per accepted defect | For each accepted finding, two layers (agent-edit, stop-gate, commit, push, pr, post-merge, external, or none): where it was caught, the earliest layer at which any lead pointed at it, supplied only by the leads' detection_layer; and where it should have been caught, assigned by the evaluation group, which is independent of the secure-creation loop and of the road owner, so neither grades its own layers. Reported per failure class and tool. The secure-creation loop logs each derived check it drops or disables, and evaluation reports each such drop against the catch layer of the later findings in that check's class. |

### Road metrics

| Metric | Definition |
|---|---|
| road answer share | Share of accepted findings whose failure class has at least one road entry with a verified (constraint-enforced) retirement claim. |
| adoption | Share of in-scope services the road conformance check finds on-road, per entry, from deployed state. |
| escape hatch rate | Escape-hatch uses per on-road service per month, per entry and per hatch; a rise under deadline pressure is read as drift (F27). |
| reintroduction on vs off road | Findings in a retired class per service-month, on-road versus off-road. A road entry whose on-road rate is not lower than off-road loses its retirement claim for that class. |
| findings per change on vs off road | Accepted findings per merged change, on-road versus off-road, split by human-written and agent-generated changes where the organization can label authorship, and further by tool and model where change provenance carries them. Counted on the reproduced tier only (see record_tiers), with the check-confirmed tier beside it; unlabeled changes stay in the denominator as their own row. Reported per lagged cohort (see lagged_cohorts). This is the measurable form of 'engineers can build however they like on the road, and it matters less'. |
| record tiers | Every defect in the shared record carries one of two labeled tiers. Check-confirmed: a deterministic check confirmed it. Reproduced: Ratchet's independent verifier, or a person outside the authoring team, reproduced it against a proof condition. Shared measures count the reproduced tier; the check-confirmed tier is reported beside it and never merged into it, because the classes deterministic checks see best are the secure-creation loop's own targets. |
| self validated findings | While any earned-autonomy grant is active, every measure that counts findings is reported twice: with the findings the system validated itself under a grant, and without them. A self-validated finding carries its label and grant id in the record, is never counted in the reproduced tier, and each grant's honesty and correctness records are reported beside the measures it touches. |
| lagged cohorts | Every defect-based measure (findings per change, reintroduction per retired class, catch layer) is reported only for cohorts of changes merged in a period whose reproduction window has closed; each report shows, beside the value, the count of candidate findings for that cohort still pending reproduction. A cohort inside its window is shown as pending, never as a value. |
| reviewer approval drift on agent changes | Reported per period. Approval rate per reviewer on agent-authored changes (an agent together with the person whose session produced the change) against that reviewer's trailing baseline and against the same reviewer's rate on human-written changes, with the accepted findings later traced to the changes each approved. The baseline includes seeded known-bad agent-written changes from the sampling and seeding service (s7.sampling-service), the same way it seeds known-bad proposals for approvers (seeded_proposal_rate, approval_gate_health). Seeds go only into sandbox branches the reviewer cannot tell apart from real ones, never onto the protected branch, so a seed approved by mistake can never merge. A seed's approval rate is the drift signal that does not wait for findings to be traced. Seed results are read pooled per change kind with a confidence interval, and per reviewer only once that reviewer's own interval is narrower than approver_drift_threshold_pp. A rise in approvals with no fall in traced findings, or a rise in seeds approved, opens a recalibration task; it is never a performance rating. |
| tailoring return | Scanner findings, triage time and analysis effort removed at covered-by-road call sites, against escapes found by testing the pre-registered sample of covered call sites (F36). A rising escape rate withdraws coverage for that entry and class. |
| vetted version share | Share of on-road call sites running an entry version with a current road assurance record; unvetted versions confer no coverage. |
| test load avoided | Per-service regressions replaced by inherited road-level regressions, net of reinstatements; the program's testing-toil return on the road. |

### Remediation metrics

| Metric | Definition |
|---|---|
| escape rate | Security weaknesses that reached production, per deployment (the denominator DORA's change fail rate uses), by weakness class, read against the organization's own starting point, naming the version of the frozen baseline it read (the freeze at phase 2 entry, or a later dated amendment). An escape is an accepted finding whose demonstrated path runs through the running system; one a kept or pipeline test stopped before it shipped is a catch. Numerator from the finding ledger (accepted findings found in production, by weakness class and path key); denominator from deploy records. The starting point comes from the historical findings and incidents gathered in the current-practice map, because phase 1 handles one weakness. |
| time to remediate | An analogue of DORA's failed deployment recovery time for security: elapsed time from a reproduced finding to a fix verified in the running system, median and spread per weakness class and owning team. Start from the finding ledger (reproduction recorded), the waits in between from the tracker, and the end from deploy records and the closure record of the independent retest. |
| remediation change fail rate | DORA's change fail rate restricted to deployments of security fixes: the share that cause a failure in production (a rollback, hotfix, incident or failed replay). As discovery slows, remediation may become the main change stream and this may become the main source of new defects. |
| cost per validated novel finding | Full cost (agent, model and runner spend plus verification hours) divided by validated findings that are novel, meaning no earlier record in the finding ledger has the same path key (weakness class plus the defined path the ledger records). A rising value with a flat novel count is the signal that discovery is reaching diminishing returns. |
| arrivals vs verified fixes | Per weakness class and period: validated findings arriving against verified fixes (independently retested and accepted). Arrivals above fixes for a sustained period is the backlog signal; the fix-capacity saturation signal reads the same queues per team. |
| validated finding queue age | Age of open validated findings, median and oldest, per weakness class and owning team, with the trend; the flow-time view of the remediation queue. |
| novel vs recurring share | Share of validated findings in a period that are novel against recurring (the same path key as an earlier finding in the finding ledger, or a class a road entry claims to retire). A rising recurring share points at class-level fixes; a falling novel share with steady cost points at saturation of discovery. |
| weakness classes retired | Weakness classes retired per period (by a vetted road entry or a constraint-enforced closure), net of classes reinstated after an escape. Classes that new technology brings start a count of their own. |
| time to revoke | For a finding of kind exposed secret, reported in place of time to remediate: elapsed time from detection to the first revocation check that records the old credential refused, median and spread per owning team, still running while the old credential authenticates. Removing the secret from code, history, logs or tickets does not stop it. From the SecretRevocation record and the closure record; an escape whose finding is an exposed secret reports it as its time to recover. |
| time to conform | For a finding of kind infrastructure misconfiguration, reported in place of time to remediate: elapsed time from detection to the first read of the live configuration that matches the declared intent, median and spread per owning team, still running until a read matches. A merged or applied change to the infrastructure code does not stop it. From the ConformanceRead record; an escape whose finding is of this kind reports it as its time to recover. |
| kept test suite health | Kept regression tests per lane (blocking, scheduled) and status (active, quarantined, retired); quarantine count and oldest age against the organization's caps; re-proof results, with tests that no longer fail against their reverted fix and whether the verifier confirmed each, and tests not re-provable (the revert conflicts, or the copy no longer builds or starts) by fix age, which never count as no longer failing; retirements by covering check; blocking-lane stage time against the regression time budget. |
| team time lost to security debt | Owning-team time lost to security debt, the interest on that debt, reported beside the counts per owning team and period: the share of the team's engineering time it reports losing to open security findings and to the workarounds, rework and extra testing they cause, from a short periodic survey of the owning team at an interval the organization sets; beside it, what the flow ledger shows of the same team's time on security work (queue waits, hours on the fix path, reopened fixes and failed security fixes). The survey reading leads, because at scale engineers' own reports have proved more tractable than code metrics for measuring debt; the two sources are labeled and never merged. Where the organization surveys the same team's time lost to the rest of its quality debt (reliability, performance, operability and the rest), it is shown beside, since security debt is one share of quality debt and all of it draws on one engineering pool. Read against the team's open findings above its fix cap: findings validated beyond fix capacity that raise this measure without a fall in escapes add interest without reducing risk. No measure carries a target the edition set. |
| contributed test survival | For a named contribution cohort and assessment window, contributed instance tests still enabled and passing at the assessed revision, configuration and scope divided by every contributed test in that cohort. Removed, skipped, failing and retired tests remain in the denominator. Unknown observations are listed separately with observation coverage, so a missing source is never counted as passing. Report numerator, denominator, cohort and window. An empty cohort reads not measured. No edition-set target. |
| instance to class promotion | For the same named contribution cohort, instance tests linked to an accepted security-owned class guardrail with passing independent class validation divided by all contributed instance tests in that cohort. Record class and guardrail versions and acceptance. Count each instance at most once and report distinct promoted classes separately. Retain retired instances in the cohort and list pending and unknown promotion evidence. An empty cohort reads not measured. No edition-set target. |
