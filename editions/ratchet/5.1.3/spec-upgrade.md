# Specification: edition upgrade

The upgrade tool moves an organization from the edition it holds to a newer one. It applies every intermediate version's renames from the new `CHANGELOG.md` to the organization's `profile.yaml`, its unit changes, its recorded overlay and the identifiers inside its patches. It re-applies the patches on the new `model.yaml` and design layer with the patch applier's rules, runs the model checks after each patch, and reports each patch as clean, renamed, applies-with-findings or conflicted, citing the changelog entry behind each. It changes identifiers only and leaves each patch's meaning as written. A conflict or a finding gets a report the organization's agent uses to draft a revised patch for a person to accept. The agent runs the tool when a new edition arrives; a person promotes the result.

## Ideal state

- **UP-1** The tool selects every version in the new `CHANGELOG.md` that is newer than the organization's edition and no newer than the target edition, and processes them in ascending semantic-version order.
- **UP-2** Each selected version's `renames:` block is parsed into entries with `kind`, `from` and `to`. An unknown kind is an error.
- **UP-3** Renames apply version by version and, within a version, in listed order, so a chain (a to b in one version, b to c in a later one) ends at c.
- **UP-4** A `profile-field` rename moves the key at its path in `profile.yaml`, including every item of an array marked `[]`, and keeps the value.
- **UP-5** An identifier rename rewrites a scalar only when the whole scalar equals `from`, in `profile.yaml` values, in a patch's ops block and, for a capability, in the `provides` and `requires` lists of the organization's unit changes and, for a step code, in each unit's `seam` there, and rewrites a code span in a patch's Markdown only when the whole span equals `from`.
- **UP-6** Renames of kind `term` and `rule-name` are never applied. The tool reports every place the old wording appears. It also reports any occurrence of an old identifier in text it does not rewrite (inside longer text, or a whole profile value that no rename rewrites), and leaves that text unchanged.
- **UP-7** An uppercase `N` that stands alone between non-letters in `from` matches any decimal integer, and the same digits replace the `N` in `to`.
- **UP-8** After renaming, the tool re-applies the organization's accepted patches on the new `model.yaml` and design layer with the patch applier's rules and classifies each patch as `clean`, `renamed`, `applies-with-findings` or `conflicted`. Proposed, rejected and withdrawn patches are renamed and never re-applied.
- **UP-9** A patch conflicts when an op targets an element, relationship, contract, view or finding kind that no longer exists, when a modify (a `set_layers` included) sets a key whose upstream value changed between the two editions, when a remove targets something that changed upstream, when an add collides with a new upstream identifier, or when a patch it depends on conflicted.
- **UP-24** Finding kinds (the model's `finding_kinds`, in editions that carry them) re-apply with the applier's rules, `expects` on `modify_finding_kind` included: a `modify_finding_kind` that sets a key whose value changed upstream conflicts, an `add_finding_kind` whose id the new edition adds and the held one lacks collides, and a kind that no longer exists is a removed target, exactly as for contracts.
- **UP-29** An `unset` re-applies like a `set`. Each key a modify op takes away is compared between the held and the new edition, and a key whose value changed there, a key the new edition removed included, conflicts with `conflict.changed-upstream`. An `unset` that takes a shipped item out of a judged set is blocked like any other switch-off (UP-27).
- **UP-10** Every rename applied and every conflict reported cites the version and changelog section that explain it, or says that no entry does.
- **UP-11** The tool never changes an op's type, changes an op's targets and `set` values only where a whole scalar equals a rename's `from`, leaves free text inside them unchanged, and never changes the first line of a patch's Status section.
- **UP-12** For each conflicted patch the tool writes a conflict report with enough detail for an agent to draft a revised patch.
- **UP-13** The upgraded layer records the organization's version as `<upstream version>+<org>.<n>`, with `n` starting at 1 on each new upstream version and `<org>` kept from the version record.
- **UP-14** The tool writes the upgraded layer to a new directory and leaves the organization's current layer untouched.
- **UP-15** The report lists each selected version's "What an agent ... should do" steps and "Changed meaning" items for the agent to work through.
- **UP-16** Profile keys that the new `profile-schema.yaml` does not define are reported as warnings.
- **UP-17** Upgrading to the edition already held does nothing and exits 0. A target older than the held edition, or a held edition missing from the changelog, is an error.
- **UP-18** A patch is `clean` or `renamed` only when its ops apply and the model checks on the model and compiled layer through that patch report no error that the state before it lacked and that is still present at the end of its fix chain (UP-22). A patch whose ops apply but which keeps such an error is `applies-with-findings`, lists those errors, and gets a findings report. The checks also run on the new edition before any patch, and errors there are reported as warnings.
- **UP-19** A `set_layers` op conflicts when its target was removed upstream, or when a layer key it sets changed between the held and the new edition's shipped layer files. A `modify_account_class` on a class of the shipped overlay conflicts the same way, when the class was removed upstream or the description or zones it sets changed.
- **UP-20** The tool compiles the organization's design layer as the applier does: the new edition's layer files, with the organization's recorded overlay in place of the shipped one when it has one, plus every applied patch's layer changes, plus the new edition's `modules.yaml` when it ships one.
- **UP-30** The tool runs the model checks with `--shipped` naming the new edition's `model.yaml`, so their judged-set check (MC-109) compares each state with the same shipped model the switch-off guard reads. A state the guard lets through then holds no `judged-set-shrunk` error, and a state it blocks is not judged on its errors.
- **UP-22** A fix chain is judged at its end. An error a patch adds counts against it only if it is still present after the last later applied patch that depends on it, directly or through others. A patch whose added errors are all gone by then is `clean` (or `renamed`) and lists each as resolved, naming the patch that resolved it. An error no later dependent removes keeps the patch `applies-with-findings`. A later patch is still judged on the errors it adds itself.
- **UP-23** The tool finds the organization's overlay by the applier's rule (spec-patch-applier.md, Finding the overlay) without an explicit option: the file the version record records, else the new edition's shipped example. A recorded overlay whose hash differs from the record stops the run with `overlay.unrecorded-change`. The upgraded version record carries the overlay record forward with the hash of the renamed file.
- **UP-25** A `finding-kind` rename rewrites the `id` of each `modify_finding_kind` op and whole code spans in patch Markdown, and maps the held model's finding kinds through it before comparing, so a patch on a renamed kind follows the rename and is never reported as a removed target. It rewrites no other scalar, because a kind id can be a plain word (`path`) that other fields hold as a value.
- **UP-26** Sort errors of MC-86 to MC-93 and MC-95 to MC-107 into mechanical corrections and judgment calls, equally for shipped and organization items. Only two corrections are mechanical: adding the broker's administrative session for an organization control-zone item, and dropping a shipped partitioning reason beside keys an organization patch added. Write one proposed correction patch and apply it as a preview. Every other error of these rules is a judgment call with what a person must decide. The switch-off guard (UP-27) blocks changes to the scope of judged shipped items.
- **UP-27** After each patch, the tool compares what each of those rules judges (the model checks' `judged` sets, MC-94) with the shipped model's, item by item, and judges only the items the patched model still holds. A shipped item that the patched model still holds and that leaves a set blocks the patch with `conflict.enforcement-change`, naming the set, its rules and the items, even when no rule then reports an error: a flag cleared, a kind changed, a session made optional or a broker moved out of the control zone each switch a rule off for the items it no longer sees. For MC-98, whose judged sets are `controllers` and `controller_feedback`, a shipped role leaving `controllers` (its control relationship recast, or removed while the role stays) or a shipped relationship leaving `controller_feedback` (its kind changed, marked optional, or its contract's `measures` removed) is `conflict.enforcement-change`. The same holds for the judged sets of MC-99 to MC-101: a shipped harness that loses its `harness` key (`harnesses`) or whose compensating relationship is marked optional (`harness_compensations`), a shipped part whose `assumptions` key is removed (`assumption_holders`), and a shipped router whose `routes_by_rule` mark is removed (`rule_routers`, and its model inputs leave `router_model_inputs`). The guard covers the judged sets of MC-102, MC-91's held check and MC-104 to MC-107 too. In those sets a patch is blocked by any of these on a shipped item:

    | Set | Rule | What blocks |
    |---|---|---|
    | `untrusted_fields` | MC-102 | `untrusted: false` set on a marked field, or the contract's `fields` replaced by a list that drops a marked field or its mark |
    | `typed_contracts` | MC-102 | the contract's `fields` key taken away, by an `unset` or by a null value, which the model checks read as no key (their null rule) |
    | `agent_reach_inputs` | MC-102 | a relationship into an agent-reachable part that stops carrying a typed contract, or whose target loses `agent_reachable` |
    | `held_kinds` | MC-91 | the kind's `held` weakened so it fails the held check, such as `judged_by` naming a part that is not model-free |
    | `evidence_contracts` | MC-104 | an evidence-content contract that loses its producers or its `evidence_content` mark |
    | `evidence_sinks` | MC-104 | a relationship that stops carrying the evidence contract into a partitioned store, or whose store loses its partition keys |
    | `evidence_store_inputs` | MC-105 | a relationship of kind evidence into a store recast as another kind, or whose target stops being a store or registry |
    | `restricted_contracts`, `restricted_deliveries` | MC-106 | `audience` cleared on a restricted contract, which takes the contract and every relationship that carries it out of both sets |
    | `coding_agent_controllers` | MC-107 | a part's control relationship to the coding agent marked optional or recast, or the part recast as a person |
    | `seam_crossings` | MC-108 | a relationship across a module's seam whose ends no longer sit on two sides of it: a part's module tag taken away or changed, or an end retargeted |

    A shipped item that leaves a set because a patch removed it is listed on that patch as `removed_from_judged` and never blocks by itself. The rules judge the remaining design and report any error it now has. Removing the protected evidence store without a partitioned replacement leaves `evidence-unpartitioned` as an error, so the result is `applies-with-findings`.
- **UP-28** A judged item is an element id or a relationship id, and also a contract name (`typed_contracts`, `evidence_contracts`, `restricted_contracts`), a field path written `<contract name>.<field path>` (`untrusted_fields`) or a finding kind id (`held_kinds`). An item is still present when the model through the patch holds an element or a relationship with that id, a contract with that name or a finding kind with that id. A field path is still present while the model holds the contract it names, the text before its first dot. No op removes a contract or a finding kind, so these items never leave a set by removal, and dropping an untrusted field or clearing its mark from a replaced `fields` list is a switch-off. Replacing the list while retaining every judged field and mark is allowed.
- **UP-21** A field rename (`report-field`, `work-unit-field`) moves only a key that equals `from`, and only in the organization's unit changes. A generic identifier (one plain lowercase word) inside text matches only as a whole code span, in the prose search and in citations alike, so an ordinary word in a sentence is never rewritten, reported or cited.

- **UP-31** A held edition before the base edition is unsupported: report `version.unsupported` before making any output directory. The minimum held edition is `5.0.0`. Fixture successors may use a semantic-version prerelease suffix, such as `5.0.1-fixture`; compare all versions by semantic-version precedence.
- **UP-32** Read re-pins from the two edition records' `pins` lists. A changed Jig pin requires both `pins/jig/` folders. Validate each pinned record's hash, namespace, version, file listing digest and each listed file hash before using it. Refuse an unreadable pin, mismatch, downgrade or incomplete changelog history. Read the successor Jig changelog between its old and new pin versions, in order, after Ratchet's selected renames. Qualify bare element, relationship, contract and view identifiers with `jig:` and apply these renames to organization patches and held comparisons as usual. Report each re-pin as `{namespace, from, to}`.
- **UP-33** A successor's changes to `shared:` items are compared with the held items under the same qualified identities. A patch setting a shared part or crossing field changed upstream conflicts by UP-9; importing a layer never hides that comparison.
- **UP-34** Read organization closure files (YAML maps holding `closures` or `sign_offs`) with the threat grid's reader. Run the grid on the held and upgraded models with their shipped closure rules and those organization files. List every previously valid sign-off the successor voids in `voided_sign_offs`, with file, contract, letter, formerly closed and now proposed cell counts. Write the successor grid as `threat-grid` with the JSON extension and preserve each organization closure file byte for byte in the output. The grid determines whether cells are proposed or closed; the upgrade grants no review mark. Invalid closure data is `closures.invalid` and permits only the reports.
- **UP-35** Keep nested changelog list indentation in `agent_steps`; the readable report renders each child below its parent. Render each item with its preserved leading indentation, then `- `, then its text. Join wrapped text to its owning item without flattening the list.

## Inputs

- From the held edition: `model.yaml` (the edition the patches were written against) and its edition (the top-level `edition` field, or `meta.edition` on a compiled organization model); and, when present, its `realization.yaml`, `quality.yaml` and `overlay-aws.yaml`, read only to compare layer keys (UP-19).
- From the new edition: `CHANGELOG.md`, `model.yaml`, `profile-schema.yaml`, the four design layer files `realization.yaml`, `quality.yaml`, `failures.yaml` and `overlay-aws.yaml` (each required: present and parseable as YAML, else `input.unreadable`; a file that parses but lacks the entries the model checks need is theirs to refuse, which this tool reports as `checks.unrunnable`), and `modules.yaml` when it ships, which the model checks read.
- From the organization's layer: `profile.yaml`; every patch `O<digits>-<slug>.md`; the version record `version.yaml`, with its optional `overlay` record (`{ file, sha256 }`, as in the applier specification); its unit changes `units.yaml` when present (`add`, `modify`, `remove`, as in `spec-unit-graph.md`); the overlay file the record names; and, read only for reporting, the premise ledger, decision log, status reports and any other text file. Another `overlay-<name>.yaml` in the layer is not read as an overlay; it gives warning `overlay.unrecorded-file`.

The upgrade reads `upstream`, `org`, `version`, `history` and `overlay` from a version record when present. It does not require a `version` key to read that record. Held-version discovery and mismatch checks still apply. This differs from the patch applier's input requirement for a version record.
- The reporting-only files are every file in the organization's layer, in any subfolder except `patches/`, whose name ends `.md`, `.yaml`, `.yml` or `.txt`, other than `profile.yaml`, `version.yaml`, `units.yaml` and the recorded overlay. An overlay file the record does not name is one of them. They are searched (rule 12). Organization closure files are read by UP-34 and copied byte for byte; other reporting files are not copied.
- The organization's model checks (`spec-model-checks.md`), run with `--model` and `--layer` on a scratch copy of each state, outside every input and output directory, and with `--shipped` naming the new edition's `model.yaml` (UP-30). Their JSON report must hold the `judged` sets (MC-94) as well as the errors.
- When a pin changes: both edition records and the pinned Jig folders described in UP-32. For closure review: both shipped closure files and failures, and the organization closure files described in UP-34.
- Options: held edition directory, new edition directory, organization layer directory, output parent directory, an optional target version (default: the newest version in the new changelog), and an optional report path where the JSON report is also written, even when the run stops on an error before the output directory exists.

### Pins

Validate only a changed pin (version or record hash differs); an unchanged pin does not require its frozen folder in this run. The pin `sha256` hashes the exact `pins/<namespace>/edition.yaml` bytes. Missing required pin values, including a null hash or absent old pin, are `pin.unreadable`. A missing folder, edition record or listed file is `input.unreadable` with exit 2 under the input reader. Available record bytes with a different hash, namespace or version, a changed listed file hash, an invalid manifest digest or a frozen shared document at `pins/<namespace>/seams.yaml` unequal to that edition's root `seams.yaml` are `pin.mismatch`. Sort manifest entries by path, then hash concatenated `<sha256>  <path>\n` lines, never sort by hash. After validation, reject a lower new pin version as `pin.downgrade`; require the successor pinned changelog to have headings for both old and new versions, else `pin.history`. Apply Ratchet renames first, then Jig renames in selected version order. Qualify bare from/to identifiers only for element, relationship, contract and view kinds; other kinds keep their written values. Read each edition's root `seams.yaml` for the shared-byte comparison.

### The changelog

Each version is a level 2 heading `## [X.Y.Z] - <date>`; a semantic-version prerelease suffix is allowed after the patch number, and the trailing date text is optional for fixture editions. Within it, the renames sit in the first fenced `yaml` block after a level 3 heading `### Renamed identifiers`, as:

```yaml
renames:
  - { kind: profile-field, from: checkpoint_1_boundary, to: phase_1_boundary }
  - { kind: duration, from: "duration:checkpoint-N", to: "duration:phase-N" }
```

Other level 3 sections ("What an agent holding X should do", "Changed meaning", "Added", "Changed", "Fixed", "Unchanged") are read as text for citations and for UP-15.

### Kinds

| kind | rewritten where | example |
|---|---|---|
| `profile-field` | keys in `profile.yaml` at the path; whole code spans in patch Markdown | `exceptions[].checkpoint_1_only` |
| `exception-policy`, `rule-code`, `trade-off-card`, `separation`, `delivery-point`, `duration`, `capability`, `step-code` | whole scalar values in `profile.yaml` and in ops blocks; for `capability`, also whole entries of `provides` and `requires` in the organization's `units.yaml`; for `step-code`, also each unit's whole `seam` value there; whole code spans in patch Markdown | `model.cp1-boundary-unconfirmed` |
| `element`, `relationship`, `contract`, `view`, `claim`, `failure`, `plane`, `seam`, `system`, `trust-zone`, `unit` | whole scalar values in ops blocks (ids, `from`, `to`, `parent`, view member lists) and in `profile.yaml`; keys under `elements` in the organization's recorded overlay (elements only); whole code spans in patch Markdown | `s2.old-part` |
| `finding-kind` | the `id` of each `modify_finding_kind` op in ops blocks; the held model's `finding_kinds` ids before comparing (rule 17); whole code spans in patch Markdown | `config-drift` |
| `work-unit-field` | a key equal to `from` in each `add` item and each `modify` item's `set` in the organization's `units.yaml`; whole code spans in patch Markdown | `checkpoint` |
| `report-field` | whole code spans in patch Markdown only (a report the organization kept records what was said) | `next_checkpoint` |
| `term`, `rule-name` | nowhere; reported only | "answer key" |

A field kind never rewrites a value: `checkpoint` as a profile value stays `checkpoint`. The premise ledger, decision log and status reports record what was said at the time; the tool reports occurrences in them and rewrites nothing.

## Outputs

The output directory holds:

```
upgrade-<held>-to-<target>/
  profile.yaml          # renamed
  patches/O01-<slug>.md # identifiers renamed; Status gains an upgrade line when anything changed
  patches/O07-upgrade-<target, dots as hyphens>-mechanical-fixes.md
                        # only when the sort found mechanical fixes: the correction patch, proposed
  version.yaml
  units.yaml            # renamed, when the organization has unit changes
  overlay-<name>.yaml   # renamed, when the version record records an overlay
  model.yaml            # the new edition plus every patch that applied, written by the applier rules
  layer/                # the compiled design layer: realization.yaml, quality.yaml, failures.yaml,
                        # overlay-aws.yaml or the organization's overlay-<name>.yaml, and modules.yaml
                        # when the new edition ships it
  upgrade-report.md     # readable summary
  upgrade-report        # the same content as a JSON report (named with the usual JSON extension)
  conflicts/O04.md      # one file per conflicted patch
  findings/O02.md       # one file per patch that applies with findings
```

The model and the layer are written only when no patch conflicted; otherwise both are omitted and the report says so. A patch with findings does not stop them: the agent needs the model to revise the patch. A layer file no patch changed is written with the bytes it was compiled from, as the applier writes it.

`version.yaml`:

```yaml
version: "2.1.2+example.1"
upstream: "2.1.2"
org: example        # set once when the workspace starts; kept from the record
n: 1
overlay: { file: overlay-onprem.yaml, sha256: "<hex>" }  # only when the record had one; the renamed file's hash
history:
  - { version: "1.0.0+example.4", upstream: "1.0.0" }
```

`output_dir` is the output directory's path relative to the directory the tool runs from. A `patches` entry always has `id`, `file`, `status` (null when the Status line cannot be read) and `result`; `renames` (the count of places rewritten), `notes`, `removed_from_judged` (rule 20), `conflicts`, `findings` and `resolved` appear only when they have content, and `reapplied: false` only on an organization's own patch that is not accepted and has no conflict; the upgrade's correction patch carries `written_by_upgrade: true` instead (rule 22a). A conflict that comes from the applier (a reader error, `depends.unmet`, or an applier error after the pre-checks) also carries `applier_code`, the applier's own code. The report also holds `repins` (namespace, from, to) and `voided_sign_offs` (file, contract, letter, before_closed_cells, proposed_cells), both empty when none changed. With organization closure files the output includes `threat-grid` with the JSON extension. The two reports are always named `upgrade-report.md` and `upgrade-report` with the JSON extension, whatever else the directory holds.

A conflict report (`conflicts/O04.md`) gives, for each conflict, a section headed `## op <i>: <op> <target>` (or `## Patch level: <code>` for one no op owns), then: the op's text, the conflict code, the target, the held edition's value and the new edition's value for each key involved, the patch's own value (for a key the op takes away, a line saying the patch takes the key away), the citation, and one question for the person on a line starting `Question for the person: ` and ending with a question mark, for example "The new edition now says X here; does the organization's change still apply, and how should it read?" It ends with the instruction to reopen the same patch file and id with Status proposed, restate its ops against the new edition, regenerate its risk section and preview it before a person accepts it again. A new patch and withdrawal of the original are appropriate only when the organization changes its intent.

A findings report (`findings/O05.md`) lists each new model check error on its own line, ``- `<code>` at `<location>`: <message>``, and under each judgment call (UP-26) the line "What a person must decide:" with its `decide` text; lists each resolved error with the patch that resolved it; asks the person whether the patch should add what the new edition expects (for example its own parts' layer entries), change, or be withdrawn; and ends with the same instruction.

A conflict report for `conflict.enforcement-change` names the set, its rules and the items that left it, and asks: "This patch takes these items out of what the rule judges; can the organization's design be declared in a way the rule reads instead, or does it go to the edition's authors?"

## Behavior

Unsupported held versions fail as `version.unsupported` before changelog membership is checked; a missing old heading cannot replace that refusal with `version.unknown`.

### Selecting versions (UP-1, UP-17)

1. Read the held edition from `version.yaml` `upstream`; when absent, from the held `model.yaml` (`meta.edition`, or the top-level `edition` that the shipped model carries); when both are present and differ, error `version.mismatch`.
2. Parse every `## [X.Y.Z]` heading in the new changelog. The held version must appear; otherwise error `version.unknown`. A target that does not appear is error `version.unknown`.

### Reading renames (UP-2)

5. For each selected version, find `### Renamed identifiers` and the first `yaml` fence after it. A version with no such heading gives warning `changelog.no-renames`, with `file` `CHANGELOG.md` and the version as `location`, and contributes no renames. ### Applying renames (UP-3 to UP-7, UP-21)

6. Work on copies of `profile.yaml`, the patches, `units.yaml` and the organization's recorded overlay. Keep each file's comments and layout: edit the text in place, and fall back to re-serializing a file or an ops block only when the edited text would not parse to the renamed structure. Apply versions in order and, within a version, entries in order. Each entry sees the result of the ones before it. The edited text is right when it parses to the renamed structure with the same key order; when it does not, the tool writes the renamed structure as YAML, and the exact bytes of that fallback are its own choice (the fixtures compare parsed structure, key order included).
7. `profile-field`: the path is dot-separated; a segment ending `[]` means every item of that array. If the key named by the last segment exists at the path, rename it in place, keeping key order. If the new key already exists beside it, error `rename.collision` at the old key's profile path (`checkpoint_1_boundary`, `exceptions[0].checkpoint_1_only`) and leave both. A missing path is not an error.
8. Identifier kinds (`exception-policy` to `capability`, `step-code`, `element`, `relationship`): replace a scalar in `profile.yaml` values or in an ops block when it equals `from` exactly. Mapping keys in ops blocks are left alone. An `element` rename also moves a key under `elements` in the organization's overlay that equals `from`; a key whose new form already exists there is error `rename.collision` at `elements.<old id>`, and both keys stay. A `capability` rename also replaces each whole entry equal to `from` in the `provides` and `requires` lists of each `add` item and each `modify` item's `set` in `units.yaml`, so a unit change keeps naming the capability by its current id. A `step-code` rename also replaces the `seam` of each `add` item and each `modify` item's `set` in `units.yaml` when it equals `from` whole, so a unit change keeps naming its step of the loop by its current code.
   A `finding-kind` rename (UP-25) replaces only the `id` of each `modify_finding_kind` op in an ops block when it equals `from` whole, recorded at `section Ops, op <i>`. It rewrites no other scalar in an ops block and nothing in `profile.yaml`, `units.yaml` or the overlay. An `add_finding_kind` adds an organization kind, whose id starts `org-` and is never an upstream rename's `from`.
9. Field kinds: a `work-unit-field` rename moves a key equal to `from` in each `add` item and in each `modify` item's `set` of `units.yaml`, keeping its value and key order (`rename.collision` at `add[<i>].<old key>` or `modify[<i>].set.<old key>` when the new key exists beside it). A `report-field` rename changes nothing outside code spans. Neither ever rewrites a value.
10. Every kind except `term` and `rule-name`: in patch Markdown outside the ops block, replace a code span (text between single backticks) when its whole content equals `from`. For a `profile-field`, the span must hold the whole path as `from` writes it (`exceptions[].checkpoint_1_only`), and it becomes the whole `to`; a span naming only the last key is left as it is, and rule 12 reports it.
11. Placeholder `N` (UP-7): in `from`, an uppercase `N` with no letter immediately before or after it matches one or more digits. The matched digits replace the `N` in `to`. `duration:checkpoint-N` turns `duration:checkpoint-3` into `duration:phase-3`.
12. After the renames, search the profile's string values, every patch's Markdown and the reporting-only files for each `term` and `rule-name` `from`, case-insensitively as a whole phrase (no letter, digit or underscore immediately before or after it, so a hyphen, a space or punctuation is a boundary), and for each other `from` (for a `profile-field`, its last segment) as a token anywhere it is left after the renames: in every profile string value, the whole value included, on every line of a patch, the ops block included, and on every line of a reporting-only file, so an ops value still equal to an old finding-kind id (`description: config-drift`) is reported at `section Ops`. An identifier occurrence has no letter, digit, underscore, hyphen or dot immediately before it. It has no letter, digit, underscore or hyphen immediately after it, and no dot followed by a letter, digit or underscore immediately after it. A backtick, a space or a sentence's closing period is a boundary. A profile string value that still equals a `from` whole after the renames (a field kind's or a `profile-field`'s `from` used as a value, which no rename rewrites) is reported too, unless that `from` is a generic identifier. A generic identifier, one made only of lowercase letters such as `checkpoint`, matches only as a whole code span, in a whole profile value as in longer text, so a profile value `checkpoint` is never reported. Record each hit once per rename entry (its version, kind and `from`), file and location in `prose_occurrences`, with the version, kind, `from`, `to`, file (relative to the layer) and location: a profile path such as `exceptions[0].reason`, `section <name>` in a patch (`title` before its first level 2 heading), or `line <n>` in a reporting-only file. Change nothing. The search runs before rule 14 adds its Status line. `units.yaml` and the organization's overlay are rewritten files and are not searched.
13. Record every rewrite in `renames_applied` with the version, entry, file and location (profile path, `section Ops, op <i>`, `section <name>` for a code span, `add[<i>].<key>` or `modify[<i>].set.<key>` for a moved key and `add[<i>].provides[<j>]` or `modify[<i>].set.requires[<j>]` for a capability entry in `units.yaml`, `add[<i>].seam` or `modify[<i>].set.seam` for a step code there, `elements.<id>` in the overlay). A moved key, in the profile, `units.yaml` or the overlay, is recorded at its old key's path, as a collision is (`checkpoint_1_boundary`, `add[0].checkpoint`, `elements.s2.a`). A chain records one entry per version. A patch's `renames` count is the number of distinct places in it that changed, so a chain that rewrites one place twice counts once. A place is one scalar of the ops block, named by its path in the block, or one code span, named by its section, its line's position among that section's lines and its position on the line. A place whose final form equals its original (a chain that comes back) is not counted.
14. When a patch's text changed, append one line after the last non-blank line of its Status section: `identifiers renamed for <target>: <from> to <to>, ...`, where `<target>` is the target edition's version (`identifiers renamed for 2.1.2: ...`), naming each distinct pair of an original identifier and its final form once, in the order its first place was rewritten. The first line of Status, which the applier reads, is unchanged.

Search renamed patch text, including Ops, before appending rule 14's Status note. That generated note never creates a prose occurrence in the same run.

### Re-applying patches (UP-8, UP-9, UP-19, UP-20)

15. Rename every patch file whatever its status, but re-apply only accepted patches, as the applier does by default. A proposed, rejected or withdrawn patch is reported with its `status`, `reapplied: false` and a result of `clean` or `renamed`. A patch file the applier's reader rejects (title, sections, Status line, ops block), whatever its status, conflicts with one `conflict.invalid` per reader error, each with `op: null`, the patch's id as `target` and the reader's code as `applier_code`; two patch files with the same number both conflict with `applier_code` `file.duplicate-id`. The reader's warnings pass through as warnings with their own codes. Apply them in order on a fresh copy of the new `model.yaml` and of the layer (rule 16) with every applier rule (sections, ops parsing, preconditions, layer keys, end-of-patch references, atomicity, provenance, namespaces).
16. The layer starts as the new edition's `realization.yaml`, `quality.yaml`, `failures.yaml` and `overlay-aws.yaml`, with the organization's renamed recorded overlay in place of `overlay-aws.yaml` when the version record names one (UP-23). Any other `overlay-<name>.yaml` in the organization's layer is not read as an overlay and gives warning `overlay.unrecorded-file`, so an organization that never recorded its file sees that the shipped example was used.
17. Before applying each op, compare against the two shipped models, after mapping the held model's identifiers (and the held layer's element keys) through the element and relationship renames (each rename entry in order rewrites every whole string scalar anywhere in the held model that equals its `from`, as rule 8 does in an ops block, and leaves mapping keys alone), and the `id` of each kind in the held model's `finding_kinds` through the finding-kind renames (a kind the new edition renamed is then held by both editions, so its keys are compared under the new id):
    - `modify_element`, `modify_relationship`, `modify_contract`, `modify_finding_kind` (a finding kind matched by `id` in each edition's `finding_kinds`): for each key in `set` and each key in `unset` (UP-29), if the target's value under that key differs between held and new editions, the op conflicts with `conflict.changed-upstream`. A key one edition holds and the other lacks differs, so an `unset` of a key the new edition removed conflicts too. Keys the patch neither sets nor unsets may change freely; list them as notes on the patch.
    - `set_layers`: for each key it sets under `realization` or `overlay`, and for `quality` as a whole, if the target's entry in the held edition's shipped layer file differs from the new edition's under that key, `conflict.changed-upstream` with keys written `realization.<key>`, `overlay.<key>` or `quality`. A role is compared only when the held edition ships its file, and `overlay` is never compared when the organization has a recorded overlay, since that file is not upstream's.
    - `modify_account_class`, when the organization has no recorded overlay and the held edition ships an overlay: a class in the held overlay and absent from the new one is `conflict.target-removed`; for `description` and `zones`, each one the op sets whose value differs between the held and new overlays (zones read as the sorted list of zones whose `zone_accounts` hold the class) is `conflict.changed-upstream` with key `account_class.description` or `account_class.zones`. Against a recorded overlay nothing is compared, and an applier `op.target-missing` or `op.exists` on an account class is `conflict.invalid`. A zone the new model no longer has is `conflict.reference-removed` naming that zone.
    - `remove_element`, `remove_relationship`: if any key of the target differs between editions, `conflict.changed-upstream`.
    - Any `modify_element`, `modify_relationship`, `modify_contract`, `modify_finding_kind`, `remove_element`, `remove_relationship`, `add_to_view` or `set_layers` op whose target is absent from the model as the patch has built it so far (the new model, plus the earlier patches that applied, plus every id an earlier op of the same patch added, minus every element or relationship an earlier op of it removed, so an `add_element` followed by a `modify_element` of the same part, or an `add_view` followed by `add_to_view`, finds its target): `conflict.target-removed` when the held model, after renames, has the target and the new model lacks it; otherwise `conflict.invalid` with `applier_code` `op.target-missing` (an earlier organization patch that added it did not apply, or it never existed). Such an op gets no other pre-check.
    - The key comparisons above run only for a target that both the held model, after renames, and the new model hold.
    - `add_element`, `add_relationship`, `add_contract`, `add_view`, `add_trust_zone` or `add_finding_kind` whose id (a contract's `name`) exists in the new edition and not in the held one: `conflict.collision`.

    Every pre-check runs on every op, so the report shows all of a patch's conflicts. The pre-checks run only when the patch-level checks (the reader, a duplicate number, rule 18's dependencies) found nothing; a patch that fails those reports only those conflicts. The applier runs only when no pre-check found a conflict. Its errors then map as follows, each carrying `applier_code`:
    - `ref.dangling` or `op.bad-reference` (a reference that no longer resolves at the end of the patch): `conflict.reference-removed`, with the identifier that no longer resolves as `target` (for an account-class op, the first zone it names that the model lacks).
    - `op.target-missing` on an op other than an account-class op: `conflict.target-removed`.
    - `op.exists` on a target the new model holds: `conflict.collision`.
    - Any other applier error, `op.target-missing` or `op.exists` on an account class included: `conflict.invalid`.

    The `target` of a conflict raised on an op is the op's target: the `contract` or `id` of a `set_layers`; the `name` of an account-class op; the id (a contract's `name`) of the item an `add_*` op adds; the `view` of an `add_to_view`; the `id` (a contract's `name`) of any other modify or remove. An applier error that names no op, or an op with no target, takes the patch's id. Each conflict carries `op`, `code`, `target`, a `text`, and for `conflict.changed-upstream` the `keys` and a `values` map from each key to its `held` and `new` values (null for a key that edition lacks) and, for an op that sets a value (a modify, a `set_layers` or a `modify_account_class`), the `patch` value, which is null for a key the op takes away with `unset`; a conflict on a remove carries only `held` and `new`. A modify that does not conflict lists keys that changed upstream but that it neither sets nor unsets as `notes` (`op`, `target`, `keys_changed_upstream`). The model key comparisons in this rule skip the provenance keys `source`, `patch`, `patch_op`, `patches` and `retired_by`. A modify's `keys` follow the order of its `set`, then of its `unset`; `keys_changed_upstream`, and a remove's `keys`, hold the held edition's keys in their order, then the keys only the new edition has.
18. A conflicted patch is not applied (atomicity). A patch whose `depends_on` names a conflicted patch is reported conflicted with `conflict.dependency`, with that patch as the target and `op: null`. A dependency that is neither conflicted nor an earlier applied patch, a withdrawn or proposed patch included, is `conflict.invalid` with `applier_code` `depends.unmet`, `op: null` and the dependency's id as `target`. Each conflicted dependency and each unmet one gives a conflict of its own, the `conflict.dependency` conflicts first, each kind in the order `depends_on` lists them. Later patches still run, so the report shows every conflict.

### Running the model checks (UP-18)

19. Before any patch, run the model checks on the new `model.yaml` and the starting layer (rule 16), with the new edition's `modules.yaml` in the layer folder when it ships. This is the baseline. Each error it reports is one warning `checks.baseline`, with the finding's location and its code under `finding`, and the whole list is the report's `checks.baseline`. Stamp the baseline with organization metadata (`organization_version` and `organization_patches`) before checking. The bare edition's null-ended shared exception therefore becomes `seam-exception-invalid` in this organization context, even with the shipped overlay; record it as a `checks.baseline` warning. Baseline findings can also come from the organization's own overlay.
20. After each patch that applies, run the model checks on the model and layer as they stand through that patch. First the switch-off guard (UP-27): for each set in the baseline's `judged` map, the items the baseline holds that this run's set lacks have left it. An item is still present as UP-28 says: an element or relationship by its id, a contract by its name, a finding kind by its id, and a field path while its contract is held. Each set that lost items still present is one conflict `conflict.enforcement-change` on the patch, with `op: null`, the set's name as `target`, its rules as `rules` (from the table in spec-model-checks.md, Outputs), those items as `items` (sorted by code unit), and `citation: null`; conflicts are listed in set-name order, set names sorted by code unit. An item that left a set and is no longer present was removed, and never makes a conflict. When the model before this patch still held it, this patch removed it, and the patch's `removed_from_judged` lists it: one entry `{ set, rules, items }` per set that lost removed items, with the same orders, whether or not the patch then conflicts for another reason. A later patch never lists it again. A patch with such a conflict is conflicted and is not applied (rule 18: the next patch starts from the state before it, and a patch that depends on it is `conflict.dependency`), and its errors are not compared. Otherwise, compare its errors with the previous state's (the baseline for the first applied patch) by code and location, counting repeats. Errors the previous state lacked are the patch's `findings`, sorted by code, then location. When more than one check component reports `overlay-missing` at the same location, retain just the first; they describe the same missing placement. Other errors retain repeats. Warnings are not compared.
21. When the checks cannot run, the tool raises error `checks.unrunnable`, runs no further check, and writes only the two reports. The rest of the run goes on, as the Errors section says: patches are still renamed and re-applied, so the report lists their conflicts. The checks cannot run when a check prints no JSON report holding an `errors` list, or when the model checks' report holds no `judged` map of lists; the model checks exit 2 with no report on a layer file they cannot read. A check's exit status alone decides nothing: a report with errors in it is a run. After a `rename.collision` the checks do not run at all (`checks.ran` stays false), while the patches are still re-applied so the report lists their conflicts.
22. Judge each fix chain at its end (UP-22). For a patch P with findings, its dependents are the later applied patches whose `depends_on` reaches P, directly or through other patches (every link names an earlier applied patch); let L be the last of them. With no dependent, P's findings stand. Otherwise, for each code and location among P's findings, the errors still owed are the count after L minus the count before P (never below zero), at most the number P added; the first that many of P's findings at that code and location, in rule 20's order, stay findings, and the rest move to P's `resolved` list, each with `resolved_by`: the earliest dependent D such that, after D and after every later dependent through L, the count (the errors at that code and location then, minus those before P, never below zero) stays at or below what is owed. Findings and resolved entries keep rule 20's order. Each dependent keeps the findings rule 20 gave it.

### Removals and the switch-off guard (UP-27)

The guard judges an item only while the patched model holds it. These cases follow from rule 20 and the applier's rules; `fixture-up-removal-upstream.yaml` and `fixture-up-removal-restated.yaml` cover these cases.

- **A removed part or relationship.** A patch that removes a shipped part first removes every relationship that names it, since the applier refuses the removal otherwise. The part and those relationships leave every judged set they were in without blocking, and `removed_from_judged` lists them. The rules still judge everything that remains, so the removal can still block through a part it leaves behind: a part that stays in the model and leaves a set because of the removal (a reader no longer exposed once the exposed store it read is gone) is a switch-off. A patch that removes one part and clears a flag on another is blocked for the flag alone.
- **A removed broker.** The broker and its administrative sessions leave `brokers` and `admin_sessions` by removal. `admin_parts` still holds every control-zone part, since MC-92 counts them whether or not a broker exists. The people who open sessions on the broker lose those authorization relationships with it, so a role whose only control or authorization action was a session (the control plane operator) stays in the model outside `controllers`, and its measured feedback leaves `controller_feedback`: that is a switch-off, and the patch is blocked. A patch that removes the broker together with that role and every relationship naming it, or that draws the role's session to the part that replaces the broker, is not blocked: MC-92 then reports `admin-broker-missing` on its own, a judgment call (rule 22a), so the patch applies with findings and the tool never declares a broker. Other checks report what the removal breaks in the same run, such as a module interface point that names a removed session.
- **A removed controller or feedback relationship.** A role removed with its relationships leaves `controllers`, and its feedback relationships leave `controller_feedback`, by removal, so nothing blocks. A removed feedback relationship leaves `controller_feedback` by removal too, and when it was the role's only measured feedback, MC-98 reports `controller-feedback-missing` at the role, a judgment call, so the patch applies with findings. A removed control or authorization relationship is different: the role stays in the model and leaves `controllers`, a switch-off, exactly as when the relationship is recast as data.
- **A part replaced by another under a new id.** The guard cannot tell a replacement from a removal. The old id leaves its sets by removal, and the new part, an organization part, joins the sets its own marks put it in and is judged by the rules like any part the organization adds: a replacement store that states no partitioning is a `store-partition` finding. A replacement that leaves out a mark the old item carried, such as a learning-store mark on a part or `restore_use` on a relationship, is not caught by the guard. `removed_from_judged` names the sets the old item was in, so the person comparing the two sees what the new one must carry.
- **A removal and a re-add in the same run.** An organization patch cannot add a shipped id again: the applier's namespace rule gives every added element an `org.` id and every added relationship an id that starts with its patch's id, so a re-add is always a replacement under a new id. Each patch is judged on the state through it, against the shipped model's sets. When one patch removes a session and a later patch that depends on it adds a replacement session, the removing patch's `admin-unbrokered` finding is resolved by the later one (rule 22), and only the removing patch lists the removed session. When the replacement is optional, MC-92 still reports `admin-unbrokered` at the part, as a judgment call.

### Citations (UP-10, UP-21)

24. Citations serve two uses: the citation each conflict carries, and the one a `profile.unknown-field` warning carries (rule 27, where an empty citation raises no `changelog.uncited`). A rename cites the version whose block holds it. A conflict cites the first selected version whose entry mentions the target identifier, or one of its renamed forms, as an exact token in any level 3 section outside fenced blocks, with the section name and the line holding it, list marker removed and trimmed. The search takes the selected versions in ascending order, each version's level 3 sections in file order (text before a version's first level 3 heading is never cited) and each section's lines in order, and stops at the first line that matches. A token match uses rule 12's identifier boundaries, so a backtick is a boundary. A generic identifier counts only as a whole code span. A `conflict.invalid` is cited the same way and never raises `changelog.uncited`. When none does, the citation is `{ "version": null }`, with no other key; for the four upstream-change codes (target removed, changed upstream, collision, reference removed) the tool then raises warning `changelog.uncited` carrying the `target`, with the patch file as `file` and `section Ops, op <i>` (or `section Ops` for a patch-level conflict) as `location`, because an upstream change that breaks an organization patch ought to be in the changelog. A `conflict.dependency` has `citation: null`, since the other patch explains it, and so does a `conflict.enforcement-change`, since the patch itself made the change.

### Recording the version (UP-13, UP-14)

25. Write `version.yaml` with `upstream` set to the target, `org` kept from the version record (when the record has none, taken from `profile.profile.name`, lowercased, each run of characters other than letters and digits turned into one hyphen, hyphens at either end trimmed, and `organization` when neither gives a name), `n: 1`, the `overlay` record when the held record had one (same `file`, `sha256` of the renamed overlay written beside it, so promotion keeps the hash and the file in step; a rename is mechanical and records no new baseline), and the previous version appended to `history` as `{ version, upstream }`: `version` is the record's `version`, or the held edition when the record has none, and `upstream` is the held edition. The entry is appended in every upgrade. Within one upstream version, the organization's process raises `n` by one each time a patch is accepted or withdrawn or the profile changes; the upgrade tool only resets it.
26. Write everything to `upgrade-<held>-to-<target>/` under the output parent directory. An existing output directory is error `output.exists`. Promoting the directory into the organization's layer is a person's act.

### Profile against the new schema (UP-16)

27. Walk the renamed profile against the new `profile-schema.yaml`, a JSON-Schema-style document, from its root. At a schema node that is a mapping: a list value is walked item by item against the node's `items`, with `[]` added to the path; a mapping value is checked only when the node has a `properties` mapping and no truthy `additionalProperties` (`true` or a schema both stop the check), and each of its keys absent from `properties` is unknown, while each other key is walked against its own property node. Any other value, or a schema node that is not a mapping, is not checked. Paths join keys with dots, so a key under list items reads `exceptions[].legacy_field`. An unknown key gives warning `profile.unknown-field` with its path and the citation rule 24 finds for the key's own name (the last segment of its path, never the whole path); an empty citation here raises no `changelog.uncited` warning. The tool does not run the readiness check.

### Agent steps (UP-15)

28. For each selected version, in ascending order, `agent_steps` holds one entry `{ version, should_do, changed_meaning }`. `should_do` reads the level 3 section whose heading matches "What an agent ... should do" (case-insensitive) and `changed_meaning` the section "Changed meaning"; a version without one of them gives an empty list. Within a section, lines inside fenced blocks and blank lines are skipped. When the section holds list items (a line starting with `-`, `*`, `+` or a number and a period, then a space), each list item is one entry with its marker removed and its original leading indentation kept, a nested item included; an indented line that is not a list item continues the last item whose text starts at or before that line's indent (the column after the item's marker and its spaces), joined to it with one space, so a wrapped item and a paragraph indented under an item, even after a nested list, stay part of it. Entries keep the order of their markers: when a line continues an item that already has nested items under it, the item keeps its place ahead of them and only its text grows. An unindented line that is not a list item is skipped. Otherwise each remaining line is one entry, trimmed.

A voided closure sign-off appears only in `voided_sign_offs` and readable report text, never as an upgrade warning. Discover closure files among reporting YAML files outside `patches/`, preserving relative paths and bytes; a mapping with a closures or sign_offs list is a closure file. Compare the held grid with held failures/rules and the upgraded grid with successor failures/rules. `before_closed_cells` and `proposed_cells` use the corresponding rule's held closed count and successor proposed count. A conflict with no field keys, such as enforcement or dependency, reports its set/rules/items or dependency instead of inventing held/new field values. Resolved findings sort by code, then location.

### Known limitations

- Conflict detection compares the two shipped models, and the two shipped layers, key by key. A semantic change upstream that leaves the keys a patch touches unchanged is reported only through "Changed meaning", which the agent reads (UP-15).
- Findings compare errors by code and location. A patch that changes what an existing error says at the same location adds no finding.
- The switch-off guard compares sets and cannot read intent. A patch that clears the outsider label further upstream on a valid clearing takes the parts below it out of `exposed` and is blocked too, and so is a removal that leaves a part still in the model outside a set it was in (the readers of a removed exposed store). Both are changes to what the edition enforces, and they go to the edition's authors rather than through a local acceptance.
- The guard reads ids. It cannot tell a part replaced under a new id from one removed, so a replacement that drops a mark the old item carried passes it; `removed_from_judged` shows the person accepting the patch what the old item was judged under.
- The sort reads codes, locations and the two shapes rule 22a names. A finding that a person would call mechanical in some other shape is still reported as a judgment call.
- Every applier `ref.dangling` or `op.bad-reference` is reported as `conflict.reference-removed`, even when the identifier never existed in either edition (a typing slip in the organization's patch). Its citation then comes back empty and raises `changelog.uncited`; the conflict report's text, the applier's own, shows which reference failed.

## Errors, warnings and exit status

Each message has `code`, `file` (or null), `location` (profile path, patch section and op index, changelog version, or a finding's location) and `text`. A `changelog.uncited` warning also carries `target`; a `profile.unknown-field` warning also carries its `citation`; a `checks.baseline` warning also carries `finding`.

Errors: `version.unsupported`, `pin.unreadable`, `pin.mismatch`, `pin.downgrade`, `pin.history`, `closures.invalid`, `version.mismatch`, `version.unknown`, `version.downgrade`, `changelog.parse`, `changelog.kind`, `rename.collision`, `checks.unrunnable`, `output.exists`, `overlay.unrecorded-change`. All `changelog.parse` and `changelog.kind` errors are collected before the run stops. An error's `file` is the organization's file as the layer names it, with no folder: `overlay.unrecorded-change` carries the overlay file name as the version record gives it (`overlay-onprem.yaml`), and `rename.collision` carries `profile.yaml`, `units.yaml` or that overlay file name, whichever holds the colliding key. Errors stop the run before anything is written, except `rename.collision`, `checks.unrunnable` and `closures.invalid`: the run continues so the report lists everything, then writes only the two reports to the output directory.

Conflicts (reported per patch, exit 3): `conflict.target-removed`, `conflict.changed-upstream`, `conflict.collision`, `conflict.reference-removed`, `conflict.dependency`, `conflict.invalid`, `conflict.enforcement-change`.

Warnings: `changelog.no-renames`, `changelog.uncited`, `profile.unknown-field`, `checks.baseline`, `overlay.unrecorded-file` (its `file` names the unread overlay file).

Exit 0: upgraded with every patch clean or renamed. Exit 3: upgraded layer written with one or more patches conflicted (no model) or applying with findings. Exit 1: an error, also when patches conflicted or applied with findings in the same run (a run that continues past `rename.collision`, `checks.unrunnable` or `closures.invalid` exits 1). Exit 2: an input cannot be read or the options are invalid, with code `input.unreadable` or `options.invalid`.

## Acceptance fixtures

Delete each fixture scratch folder with whatever deletion the environment allows. If the environment refuses the deletion, report the refusal and the retained path separately from fixture assertions. Preserve the fixture result and exit status based on assertions, and never count a skipped case as passed.

The full fixture content is in `fixtures-upgrade.yaml`, with complete held and successor file maps supplied by `upgrade-editions.yaml`; builders materialize these supplied bytes rather than inventing toy editions. A file given as `{ shipped: <name> }` is this edition's own file of that name, byte for byte, so the rename rules are proven on the real changelog. Outcome `findings` means exit 3 with no patch conflicted.

The file is a mapping. Its `fixtures` key lists one entry per row below; its root `fixtures` list holds all entries and cases, whose file maps may reuse YAML anchors and the supplied edition bundle. An entry has `name`, `description` and `source` (read by people only), then either `files`, optional `options` and `expect`, or `cases`, a list of `{ case, files, options, expect }` run one by one, the fixture passing only when every case passes. `runs: 2` runs the tool twice into the same output parent, and its `expect` holds `first_run` and `second_run`, one block per run. A runner must understand the keys below, and a fixture holding any key the runner does not know fails.

- **Files.** The shipped `upgrade-editions.yaml` maps edition names to complete file maps built from this edition, with every held model either the shipped base or a scripted variant of it. `{ fixture_edition: name }` at a directory path materializes that edition there. `{ fixture_sign_off: true }` materializes the bundle's organization sign-off. These markers are inputs supplied with the fixtures; a builder does not invent a held model. YAML merge keys in fixture mappings are expanded before materialization. For a merge sequence the first mapping wins, and explicit keys override merged keys. This does not alter YAML embedded inside a file-content string. `files` maps a path under a scratch folder of the runner's own (`held/`, `new/`, `org/`) to its content: a string is written as is, a mapping whose one key is `shipped` with a string value is this edition's own file of that name, byte for byte, and any other mapping is written as YAML.
- **Run.** The runner runs the tool from the scratch folder with `held`, `new`, `org` and `out` as the four directories, `options.target` as the target when given, and a report path outside `out`, and reads the JSON report from that path.
- **Expect keys,** each checked when present. `outcome` is `ok` (exit 0), `conflicted` (exit 3 with a conflicted patch), `findings` (exit 3, none conflicted) or `error` (any other exit); `exit` is the exit status. `versions`, `target`, `organization_version`, `model_written` and `agent_steps` must equal the report's value. `errors` and `warnings` list every message of that level, compared as a multiset: an entry is a code alone or a mapping compared on the keys it gives, each entry consumes one message, and a message left over fails the fixture. `output_written` is `false` when the run created no output directory, `"reports only"` when the directory holds exactly the two reports, the Markdown report and the JSON one, and `true` when it holds a top-level `profile.yaml`. The runner lists the entries of `out` before the run (`out` need not exist) and judges only the one directory the run created inside it. `output_dir` names the one directory the run created under `out`. `org_layer_byte_identical` compares every file of the organization's layer before and after the run. `profile_after` is YAML text that the output profile must parse to, key order included; `profile_key_order` and `profile_keys_after` are the output profile's top-level keys in order (`profile_keys_after` reads the organization's own profile when the run wrote no output profile); `profile_values` maps a path such as `exceptions[0].phase_1_only` to its value in the output profile. `renames_applied_count` is the length of `renames_applied`. Each `prose_occurrences` entry must match some reported entry on the keys it gives; no reported entry may match a `prose_occurrences_exclude` entry. `patch_text_contains` maps an output patch's file name to strings it must contain; `patch_ops_after` maps it to the `ops` list its ops block must parse to; `status_section_after` is the text between the `## Status` line and the next level 2 heading or the end of the only patch in the output, trimmed. `unchanged_text` lists strings that each organization file holding one before the run still holds after it, as does the output file at the same relative path when one exists. `patches` lists entries matched by `id` to the reported patch, compared as described below. `model` checks the output model: `element_ids_include` by membership, under `elements` and `relationships`, by id, the fields listed must be equal, and under `absent`, each of `elements`, `relationships`, `contracts` and `finding_kinds` maps an item (by id, a contract by name) to the list of top-level keys it must not hold. `conflict_report` and `findings_report` give a `path` in the output directory, strings it must `contain`, and `ends_with_instruction`, a phrase the file's last non-blank line must contain, ignoring case. `output_values` maps a file in the output directory to `{ path, value }` checks: `path` is a list of keys, so an id with dots stays one key and a list item is selected by its index written as a string, and a `value` of null also matches an absent key. `layer_files` is every file name in the output's `layer/` folder, sorted. `version_yaml` is the output version record, compared whole after parsing. `overlay_record_matches: true` means the output version record's `overlay.sha256` is the SHA-256 of the output overlay file it names.
An entry-level `reopen: true` requires an `expect.reopen` mapping and performs its same-file lifecycle exactly once; any other marker value or missing mapping is a fixture defect. `findings_report` and `conflict_report` both read their explicit `path`, which may be `upgrade-report.md`; their labels do not choose the file. `ends_with_instruction` is checked when supplied even though current entries need not use it. A quoted `"<<"` in a file map has the same first-mapping-wins merge-sequence semantics described for Files. Scripted successor relationship texts, unit/profile renames, closure wording, pin versions and guard mutations are fixture input bytes and expectations, not generator behavior keyed to fixture names.

- **Additional checks.** `checks_baseline` compares the new edition baseline errors exactly. Each `guard_sets` entry requires an enforcement conflict on that set with non-empty items. `repins` and `voided_sign_offs` compare the report lists by partial matching. `preserve_closure_files: true` requires every input closure file byte for byte in the output. `grid_proposed: true` requires a valid emitted grid, at least one voided sign-off with positive formerly closed and now proposed cell counts, and no closed cells or active sign-off on those rules. `reopen` names a conflicted output patch and a finding: reopen that same file and id as proposed; prove the ordinary applier skips it, regenerate its risk section, prove a preview applies it without accepting it and reports the named error, then simulate the fixture person accepting it again and prove its intent applies and its error persists. The separate restated fixture requires that error as a judgment finding from the upgrade. The removal mutation replaces the remove pre-check's changed keys with an empty list and must fail the removal conflict fixture.
- **Partial matching.** Under `patches`, and in `errors`, `warnings` and `prose_occurrences` entries, a mapping compares only the keys it lists, at every depth; a list holding mappings must have the same length and match item by item; any other value, a list of strings included, must be equal. A null there matches only a reported null.

## Not in scope

- Drafting the revised patch for a conflict or a finding (the organization's agent) and accepting it (a person).
- Changing a patch's Status. A conflicted patch the agent reopens in the output directory is `proposed` there, so the applier leaves it out and the written model carries none of its intent; the tool never sets it back to `accepted`, on this run or a later one, which renames it and does not re-apply it (rule 15). It returns to `accepted` only when a person accepts it again, and the upgrade is complete when every reopened patch is accepted again or withdrawn (`workflow-upgrade.md`, step 11).
- Rewriting prose: terms, rule names, the premise ledger, the decision log and status reports.
- Running the readiness check, the profile checker, the unit graph or the impact report on the upgraded layer. The upgrade workflow runs them after the tool.
- Checking the held state. When the new edition's tools cannot check the held edition, the organization checks it with the held edition's own tools before upgrading.
- Downgrading to an earlier edition.
